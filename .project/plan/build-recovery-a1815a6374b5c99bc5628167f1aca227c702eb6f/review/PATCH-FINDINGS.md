### P002 — .browserslistrc is not a cache input of the Nx targets that read it

- **Source**: `.project/review/final-gap-2.md`
- **Locator**: Risk: .browserslistrc is not a cache input of the Nx targets that read it (ngx-yeti:build-storybook, ngx-yeti:test-storybook, ngx-yeti-e2e:e2e and its e2e-ci shards, ngx-yeti:build, yeti-app:build), so a browser-floor change replays results built for the old CSS target
- **Evidence**: Measured. All six cached targets in the risk read the browser floor at run time, directly or through a nested build, and none of them hashes `.browserslistrc`. yeti-app-e2e:e2e has the same gap. If someone raises, lowers or breaks the floor, Nx replays the cached Storybook build and test-storybook pass, the cached ngx-yeti-e2e results (color-scheme-wrappers.spec.ts included, the spec that guards T075's cssTarget fix), the cached ngx-yeti package and the cached yeti-app bundle, all built for the old CSS target. This goes against Lars's ruling of 2026-10-16, "Nx cache/inputs/outputs issues are important", and against AGENTS.md "Run CI locally", which expects every job to pass both locally and in CI. A replayed local run is not proof of the current floor. T075 AC1 still holds, because it runs with `--skip-nx-cache`, but its cached runs are not protected. Inferred, not measured: whether @angular/build:unit-test (ngx-yeti:test) also reads the floor.
- **Fix direction**: In nx.json `namedInputs`, add `"browserFloor": ["{workspaceRoot}/.browserslistrc"]`. Then add `"browserFloor"` to `targetDefaults["@angular/build:application"].inputs`, `targetDefaults["@nx/angular:package"].inputs`, `targetDefaults["build-storybook"].inputs` and `targetDefaults["test-storybook"].inputs`, and to the `e2e` named input. The `e2e` entry covers `e2e` and every `e2e-ci--**/*` shard of ngx-yeti-e2e and yeti-app-e2e. Use a named input rather than `sharedGlobals`: `sharedGlobals` feeds `default`, which every lint, typecheck and unit-test target and every `^default` consumer hashes, so a floor edit would invalidate targets that never read the file. Per-target globs would repeat one path in five places, while one named input keeps a single owner. Check: before the change, a `node --test` file that runs `nx show target inputs <t> --json` for the six cached targets plus yeti-app-e2e:e2e and asserts `.browserslistrc` is in `files` fails. After the change it passes, and a negative control (ngx-yeti:lint does not list the file) still holds. tmp/gap2-inputs.mjs in this sidecar is a working start for that test.

### P003 — control-yeti-app's live down and stopLaunch can kill or report processes it did not start

- **Source**: `.project/review/final-gap-3.md`
- **Locator**: Risk: a control script's kill can reach a process it did not start, because taskkill /T on an identity-checked root selects children by parent PID alone, and control-yeti-app stopLaunch kills and reports a launch that may already have exited
- **Evidence**: blocked. Measured: control-yeti-app's live `down` takes its member list from `tree()`, which matches children by parent PID alone, so a process that started before the recorded root but carries its PID as parent (PID reuse) is listed in `stopped`, survives taskkill /T (which itself filters it out), is written to `state.json` as a survivor, and the "run down again" retry kills it by PID and exits 0. That contradicts SKILL.md's own rule for the dead-root tree (:145-147, processes started before the recorded `start` are left out because Windows hands a dead PID out again) and Storybook's behaviour that Lars's 2026-10-15 ruling adopts. Inferred: on `up`'s launch-exited path `stopLaunch` reports `launchStopped: true` with the launch's surviving children unchecked and removes the state file, so SKILL.md:194's "stops the started tree ... nothing is left for `down`" does not hold, and the PID it kills may by then belong to another process. control-ngx-yeti-storybook passes: its live path uses `treeMembers`, and native taskkill /T spares pre-root processes (measured twice).
- **Fix direction**: In .claude/skills/control-yeti-app/scripts/control.mjs, build the live `down` member list with `treeMembers(table, state.pid, state.start)` plus the root entry instead of `tree(table, state.pid)` (:1164-1167), so a pre-root process is never recorded as a survivor and never reaches the retry's taskkill. In `stopLaunch`, take the launch's start (`live.Start`, when known) and, when the root is already gone, do not taskkill the PID; collect `treeMembers` and report `launchStopped: true` only when no member survives, naming survivors otherwise (as down's dead path does; this also closes part of risk 4). Update SKILL.md:176-179 and :194 to match. Proof in .claude/skills/control-yeti-app/scripts/control.test.mjs, shown failing at d63e7e0 first: the PID-reuse setup from tmp/gap3-spike2.mjs (a bounded spawn loop until a live stand-in root holds an exited parent's PID, a state file with that root's real start and command line), then two `down` runs that must leave the pre-root orphan alive and never list it in `stopped` or `survivors`; and an `up` whose launch exits while a child keeps running must report `launchStopped: false` naming that child.

### P004 — the spec writer's --open and the loop-budget gate's path resolution can check the wrong target

- **Source**: `.project/review/final-gap-5.md`
- **Locator**: Risk: tools/verification/lars-verify-spec.mjs accepts an --open value that changes the url's host or port, and tools/playwright/navigation-budget.test.mjs resolves listed paths with new URL, so a lars-verify spec or the loop-budget gate can check the wrong target
- **Evidence**: The risk holds on both halves, with measured evidence for each. 1. The spec writer accepts an `--open` value that changes the port of a control-ngx-yeti-storybook spec (`1/iframe.html` gives port 44001). It also accepts one that leaves the control-yeti-app `/sub/` base (`../` and `%2e%2e/`). This contradicts the writer's stated guard and the T076 review-fix intent. Such a spec drives whatever listens on the other port, or the server root, so /lars-verify can return a verdict for the wrong target. 2. The loop-budget gate silently skips a listed file whose name holds `#` or `?`. It reads a different file for a `%2e%2e` or `%20` name. A fixed-budget loop in `mutant#x.spec.ts` passed the gate, and the same content under a plain name failed it. Both cases are latent. No committed `--open` example and no file in the repository uses such a value or name today, and the severity is low. They are still demonstrated gaps in guards that exist to stop exactly these cases.
- **Fix direction**: (1) tools/verification/lars-verify-spec.mjs: in the `--open` guard at :244, also refuse a value whose first character is a digit, because only digits can extend a url that ends in a port. Also refuse any `/`-separated segment (before `?` or `#`) that equals `.` or `..` after decoding `%2e`/`%2E`. Add three refusal cases to tools/verification/lars-verify-spec.test.mjs: `--open 1/iframe.html`, `--open ../card` and `--open %2e%2e/card`. Each should expect exit 2, the "is not a path below the app's URL" message, and nothing written. Run them first against the current writer, where they fail.; (2) tools/playwright/navigation-budget.test.mjs: resolve listed paths as file-system paths, not URL references. Use `join(fileURLToPath(root), path)` from node:path and node:url at :282, :335 and :347. Add a test that writes an untracked `apps/.../loop#x.spec.ts` with a fixed-budget `goto` loop and expects the repository scan to flag it. Alternatively, add an inline unit check that the resolved path for `a#b.spec.ts` ends in `a#b.spec.ts`. That test fails first against the current `new URL` resolution, then passes.; (3) Check: `npm exec nx -- run @ngx-yeti/source:test --skip-nx-cache`.
