## Settled

- Order of work — `setup` first, then `generated-ids`, `events`, `fragment-links`, `navigation-close`, then items; per item the level order native, `@angular/aria`, `@angular/cdk`, custom (`.claude/skills/ngx-yeti-specs/SKILL.md` "Order of work"; map.md Inherited preferences, Implementation order)
- Entry points — one secondary entry point per item plus `styles`, `generated-ids`, `fragment-links`, `navigation-close`, type-only `events`; primary `ngx-yeti` is types-only; each created with `nx g @nx/angular:library-secondary-entry-point --library=ngx-yeti --name={item} --skipModule`, never by hand (ADR 0011 clause 10; ngx-yeti-specs SKILL "Where code goes")
- Placeholders — `NgxYeti` and `Highlight` are removed when `setup` makes the primary entry point types-only, and their fixture, story, SSR, and e2e assertions move to the first real item in the same change (ngx-yeti-specs SKILL "One-time tasks")
- Package accessibility stylesheet — the first spec that writes an accessibility rule creates `accessibility.css`, publishes it through ng-packagr assets and the `exports` map, and makes Storybook and `yeti-app` resolve `ngx-yeti/accessibility.css` (ngx-yeti-specs SKILL "One-time tasks"; ticket 50 decision 68; ADR 0060 point 8)
- Item styles — reference-counted head links to the consumer's Yeti build at `yeti-css/` relative to base href, inserted in Yeti's rank order, one presence attribute per item; the package ships no Yeti CSS (ADR 0060; ADR 0045)
- Generated types — `yeti-types.ts` generated from `yeti.d.ts` at the pin; published declarations never import `yeti-css` (ADR 0060 point 10)
- Yeti dependency — vendored at the pin, built by `yeti-css:yeti-build`, no `yeti-css` dependency or peer entry while Yeti is unpublished; pin held per milestone and moved only between milestones through the `yeti-pin` skill (ADR 0006; CHARTER Constraints, Yeti pin)
- Generated ids — per-application counter over CDK `_IdGenerator`, adopted at hydration through `TransferState`, `provideYetiAriaIds()` on `yetiTab`, `yetiTabPanel`, `yetiButtonsItem`; id-shape tests catch a CDK rename (ADR 0042; ADR 0044)
- `@angular/cdk` peer — a peer at the Angular minor the release names, `^22.2.0` (ADR 0042 Consequences; ADR 0017)
- Angular peers and version format — Angular packages peer `^22.2.0`; version `0.{major}{minor:2}{breaking:2}.{patch}-yeti.{Yeti version}.g{SHA}`, published by the user with `--tag latest` (ADR 0017 2026-10-02 notes; setup.md E and its version test; CHARTER vetoes publishing)

- Aria use — only `tabs` (Aria Tabs) and `buttons` (Aria Toolbar), hosted by composition through `hostDirectives`; `accordion` native, `nav` and `dropdown` custom disclosure, carousel picker custom (map.md Standing rulings 2026-10-02 and 2026-10-03; building-blocks.md "Aria decisions (2026-10-03)")
- A5 workaround — `yetiButtonsItem` binds `[attr.tabindex]` to null until a member is active; `tabs` renders every panel with no `inert` and adds `hidden` once live; remove the hand-over only with a test proving server HTML unchanged (ADR 0011 note on ticket 50 decision 113; tabs.md Problem Statement; buttons.md:484)
- A6 workaround — `provideYetiAriaIds()` (ADR 0044; generated-ids.md)
- A9 handling — panel content is projected directly; tests that fail on console warnings allow the one dev message "ngTabPanel must have an ngTabContent structural directive to render." (tabs.md usage rule 7 and Further Notes; upstream-bugs.md A9)
- Upstream reports — no issue or PR filed without the user's confirmation (CHARTER vetoes; map.md Standing rulings, Upstream bugs)
- Rendering modes and JavaScript off — every item specified for SSR, prerendering, full and incremental hydration, event replay, `withI18nSupport()`, `@defer` triggers; readable with JavaScript off under SSR and prerendering; hydration constraints and zoneless hold (ADR 0011 and its 2026-10-03 notes; map.md Standing rulings 43, 54, 55)

## Decisions

### Install and peer ranges for @angular/cdk and @angular/aria

- **Decision**: Add `@angular/cdk` and `@angular/aria` to the root `devDependencies` at exactly `22.2.1` each, matching the exact `@angular/core` `22.2.1` pin in `package.json`, in one commit, in the task that lands `generated-ids` (its Aria-host tests need both). Declare both as required peers of `packages/ngx-yeti` at `^22.2.0`. Every later bump moves the two in one commit to the same version. Rely on aria's own exact `@angular/cdk` peer to keep a consumer's pair aligned; ngx-yeti does not narrow its own ranges.
- **Runner-up**: Peer both at the exact `22.2.1`. Lost: it contradicts ADR 0017 and ADR 0042 (peers from the minor, `^22.2.0`) and would force an ngx-yeti release for every CDK patch, while aria's exact cdk peer already stops a mismatched pair at install. Making aria an optional peer also lost: the records make only `@angular/router` optional (ADR 0041), and the charter's success criterion 6 names `@angular/aria` as a peer.
- **Evidence**: evidence-stack.md § "`@angular/cdk` and `@angular/aria` 22.2.1 are the latest releases and match Angular 22.2.1"; evidence-stack.md § "aria 22.2.1 pins cdk to exactly 22.2.1, so the two must move together"; evidence-codebase.md § "Angular CDK and Angular Aria are not dependencies"
- **Confidence**: high

### Tracking Aria bugs A5, A6, A9 at 22.2.1

- **Decision**: Treat A5, A6, and A9 as present at 22.2.1 and build the records' workarounds unchanged (see Settled). Each workaround carries a test that fails if Aria fixes the bug or moves the seam: A5, a server-HTML assertion on `tabindex` and `inert`; A6, the id-shape server-and-client test of ADR 0044 point 6; A9, a test that the allowed dev message is the only one. On every Aria or CDK bump, run those tests first. Because the research read the shipped code and ran no browser or SSR reproduction, the milestone that first installs Aria runs a wave-1 reproduction at 22.2.1 before building on it.
- **Runner-up**: Wait for or ask for an upstream fix. Lost: no upstream issue, PR, or changelog entry addresses any of the three, 22.3.0-next.0 ships identical Aria code, and filing needs the user's confirmation.
- **Evidence**: evidence-stack.md § "A5 (roving tabindex and `inert` set only in `afterRenderEffect`) is still in the shipped 22.2.1 code and in 22.3.0-next.0"; evidence-stack.md § "A6 (generated ids change at hydration) is still in the shipped code, and the `_IdGenerator` hook that ADR 0044 relies on is unchanged"; evidence-stack.md § "A9 (`ngTabPanel must have an ngTabContent structural directive to render.`) is still logged by 22.2.1 and 22.3.0-next.0"; evidence-stack.md § "no upstream issue, PR, or changelog entry fixes or reports A5, A6, or A9"
- **Confidence**: medium — code read, not run; verify in wave 1 of the first Aria milestone

### How apps/yeti-analog consumes ngx-yeti

- **Decision**: Consume ngx-yeti from source, the way `yeti-app`, Storybook, and the Vitest configs already do: set `resolve.tsconfigPaths: true` in `apps/yeti-analog/vite.config.ts`, add the library sources to the Analog compilation (`analog({ include })` or `tsconfig.app.json` `include`), add `implicitDependencies: ["yeti-css"]`, and reuse the CSS resolution for `ngx-yeti/accessibility.css` that the accessibility-stylesheet one-time task builds for the other two consumers. Success criterion 6 ("every entry point resolves in a consuming build") is proven separately, at release readiness, by a consuming build against the `npm pack` tarball.
- **Runner-up**: Consume the packed output (`dist/` or the tarball). Lost: no evidence shows Vite resolving ng-packagr secondary entry points from `dist/` without linking a tarball into `node_modules` (lockfile churn), it puts a full ng-packagr `nx build ngx-yeti` in front of every Analog dev and e2e run, and it would make the demo the only consumer with that shape.
- **Evidence**: evidence-stack.md § "ngx-yeti's secondary entry points and its CSS export need path resolution and compilation that `apps/yeti-analog` does not have"; evidence-stack.md § "yeti-analog today is generator output that still lacks what the setup spec requires of a consumer"; evidence-codebase.md § "The package has one entry point; the specs require one per item"
- **Confidence**: low — each element read, the combined effect not run; verify in wave 1 of the first milestone that touches yeti-analog

### Analog rendering modes and the e2e that proves them

- **Decision**: One Analog project, two build configurations. The default configuration is the hybrid Nitro build: demo pages listed in `prerender.routes` are prerendered, and the same pages under a `/server/` prefix render on request (SSR), mirroring the Fixture app's per-item pair. A `static` configuration (`static: true`, `ssr: true`) prerenders the same pages with no server output and proves SSG. `yeti-analog-e2e` replaces its dev-server `webServer` with the production outputs (the Nitro server, and a static file server for the `static` output) and runs each mode with JavaScript on and off, axe-clean and with no hydration mismatch. Demo pages are the three groupings the evidence names, each added in the milestone that ships its items: a `shell` page with `stack`, `center`, `cover`, `card`, `badge`; a `tabs` plus `buttons` page; a native-state item inside `hydrate never` plus a client-only `@defer` with `provideYetiStyles({ preload })`. The roadmap places them. Client-only routes (`routeRules` `ssr: false`) are not demonstrated: ADR 0011 makes no promise for client-only rendering, and the charter does not ask for it.
- **Runner-up**: Keep the dev-server e2e and one build, treating prerendering and SSG as one mode. Lost: the dev server exercises neither prerendered output nor a production SSR server, so it cannot prove criterion 5, and the charter names SSR, SSG, and prerendering as three modes.
- **Evidence**: evidence-stack.md § "Analog 2.8.0 server-renders by default and prerenders `/` when no routes are named; extra routes, SSR and client-only routes are one config"; evidence-stack.md § "yeti-analog today is generator output that still lacks what the setup spec requires of a consumer"; evidence-stack.md § "which rendering modes and items a demonstration covers per page, from the specs (checked) and Analog's constraints (inferred)"
- **Confidence**: low — Analog config read, no build run; verify in wave 1 of the first milestone that touches yeti-analog

### Serving Yeti's CSS at /yeti-css/ in apps/yeti-analog

- **Decision**: A small local Vite plugin in `apps/yeti-analog/vite.config.ts` serves `node_modules/yeti-css/dist/css/**/*.css` at `/yeti-css/` in dev and emits the same files into the client output on build, so Nitro serves them and prerendering finds them. No new dependency. A build-output test pins the copied file count, as `yeti-app`'s `build-output.spec.ts` pins 66. The adaptation of setup spec B's `assets` entry to Vite is recorded as a row in the ngx-yeti-specs Departures table in the same change.
- **Runner-up**: A Nitro `publicAssets` entry. Lost: it serves the production server only, so the dev server 404s every item link. A copy into `public/yeti-css` by an Nx target also lost: it writes build output into a source folder that then needs ignoring.
- **Evidence**: evidence-stack.md § "the `assets` entry has no Analog equivalent; there are three candidate places to serve Yeti's 66 CSS files"
- **Confidence**: low — routes read, none tested; verify in wave 1 of the first milestone that touches yeti-analog

### npm allowScripts approvals

- **Decision**: Commit no `allowScripts` policy now. Under npm 11 (CI's Node 24 bundles npm 11.19.0) the feature only warns and the scripts run; with all nine scripts blocked under npm 12.2.0, `nx build ngx-yeti`, `nx build-storybook ngx-yeti`, `nx build yeti-app`, and `nx test ngx-yeti` still passed. Revisit when CI's npm or the contributor baseline moves to 12; the first open path to check then is the floor and Safari WebdriverIO jobs (geckodriver, edgedriver postinstalls). Plans must not build on the codebase map's "withheld" claim; npm 11.16 warned and ran the scripts.
- **Runner-up**: Commit name-only approvals for all nine packages so npm 11 and 12 installs match. Lost: it pre-approves install scripts, a supply-chain surface, to cover a blocking that no CI path in this program hits and that broke nothing measured. A deny-all policy also lost: the floor and Safari driver paths are unverified under blocking.
- **Evidence**: evidence-pitfalls.md § "Under npm 11.16 allow-scripts is advisory; the scripts ran, so the codebase map's \"withheld\" is a misreading"; evidence-pitfalls.md § "npm 12 blocks dependency install scripts by default; npm 12.2.0 is `latest` on the registry"; evidence-pitfalls.md § "CI's npm comes from Node 24; Node 24.21.0 bundles npm 11.19.0"; evidence-pitfalls.md § "With all 9 scripts blocked (npm 12.2.0), build, Storybook build, Nx test, and Playwright CLI all work"; evidence-pitfalls.md § "Webdriver driver packages are in the warning list but are not exercised by the default path"
- **Confidence**: medium

### Playwright webServer failure 'nx' is not recognized

- **Decision**: Treat it as a wave-1 blocker of the first milestone. Before any task Verify depends on `nx e2e`, reproduce `nx e2e yeti-app-e2e` and `nx e2e ngx-yeti-e2e` in a linked worktree at the location the pipeline's isolation helper creates, and in the primary checkout. If it reproduces, fix the `webServer.command` in `apps/yeti-app-e2e/playwright.config.mts` and `apps/ngx-yeti-e2e/playwright.config.mts` (today `npx nx run ...`) so the server starts in both, and apply the same fix to `apps/yeti-analog-e2e`. If it does not reproduce, record that the cause was the scratch location and close it.
- **Runner-up**: Ignore it as an artefact of the C: Temp scratch worktree. Lost: the cause is unknown, it failed under both npm installs and both `npx nx` and `npm exec -- nx`, and GSD Path runs task and review Verify in linked worktrees, so a worktree-only failure would block every e2e Verify.
- **Evidence**: evidence-pitfalls.md § "Playwright e2e could not start in the disposable worktree under either install, so it is not an allow-scripts effect"; evidence-codebase.md checks list (all `e2e` targets not run, `unverifiable`)
- **Confidence**: low — cause not found; verify in wave 1

## For the planner

- **Wave-1 blockers**: (1) First milestone: reproduce or rule out the Playwright `webServer` failure in a pipeline worktree and in the primary checkout, and fix the e2e `webServer.command` if needed, before any Verify uses `nx e2e` (decision "Playwright webServer failure"). (2) First milestone: the first item establishes the secondary entry-point layout with the generator and proves `nx build ngx-yeti`, `nx build-fast ngx-yeti`, `nx typecheck ngx-yeti -c src`, the Storybook globs, and the Vitest `{src,*/src}` spec roots all pick up the new entry. (3) First milestone: `ngx-yeti/accessibility.css` resolves in both Storybook and `yeti-app` (one-time task). (4) Milestone that first installs Aria (the one carrying `generated-ids`): install the cdk and aria 22.2.1 pair, then server-render an Aria Toolbar and Tabs to reproduce A5 and A6 at 22.2.1, and check which console channel A9 uses, because the story preview fails on any `console.error` while tabs.md allows a warning. (5) First milestone that touches `apps/yeti-analog`: one real item renders under Analog SSR from source, Yeti CSS is served at `/yeti-css/` in dev and in the built output, and `yeti-analog-e2e` runs against the Nitro output and the `static` output with JavaScript on and off (decisions on Analog consumption, modes, and CSS serving).
- **Walking skeleton**: The `setup` spec end to end plus one level-1, types-only item (for example `visually-hidden` or `badge`; the roadmapper picks): the `ngx-yeti/styles` loader writing the item's head link in rank order on the server and adopting it on the client, `yeti-types.ts`, the layer statement and global stylesheet in `yeti-app`, the item at its own `ngx-yeti/{item}` entry point, its story with the axe gate, browser and SSR specs, a prerendered and a server-rendered Fixture-app route checked by `yeti-app-e2e` with JavaScript on and off, the per-spec contract check against the built manifest, and `nx build ngx-yeti` producing the entry point. The placeholders `NgxYeti` and `Highlight` go in the same change, with their infrastructure tests moved onto the real item.
- **Pitfalls → tasks**: `fastCompile` does not type-check → every Verify that runs `test`, `build-fast`, or a Storybook `-c fast` target also runs `nx typecheck {project}` (all tasks). Placeholders are today's test targets → the task that removes them moves the `highlight` fixture, the `src-lib-ngx-yeti--heading` story, the SSR spec, and both e2e assertions to the real item in one commit (walking-skeleton task). A hand-made entry point misses the `tsconfig.lib.json` lines, so `typecheck -c src` silently skips it → always the generator (every item task). Any new target that reads Yeti's `dist/` needs `^yeti-build` through targetDefaults or it races (setup, contract check, Analog CSS serving). A local green run is Chromium only → cross-engine claims need CI or `CI=true` with browsers installed (all item tasks with engine-specific behaviour). Aria pins cdk exactly → bump both in one commit; run the A5, A6, A9 tests and the ADR 0044 id-shape test first on every bump (dependency tasks). `_IdGenerator` is underscore-private → the generated-ids server-and-client test is the guard (generated-ids task). A9's dev message → tabs tests allow exactly that one message; confirm it does not reach the story preview's `console.error` gate (tabs task). A5 → `buttons` and `tabs` assert the server `tabindex` hand-over and no `inert` in server HTML (buttons and tabs tasks). Analog has no Beasties step → setup spec's A4 test and the `noscript` copy do not apply to `yeti-analog`; prove JavaScript-off styling there through the loader's head links and Vite's stylesheet link (Analog tasks). Analog's dependency crawler treats aria and cdk as framework packages → if the tabs or buttons page fails under Analog SSR, add them to `ssr.noExternal` (Analog Aria page task). `yeti-analog` lacks `withI18nSupport()`, the layer statement, and the Yeti imports → its setup task adds them per setup spec (first Analog task). Every adaptation of a spec to the workspace (for example setup spec B under Vite) → a row in the ngx-yeti-specs Departures table in the same change (any task that departs). Docs-audit ruling 5 ("`injectYetiItemStyles` arriving with the setup spec") → land with the setup milestone; rulings 1 to 4 are small doc or fixture fixes for the first milestone. Do not re-add `.project` to `.gitignore` (pipeline checkpoints). Never edit `vendor/yeti` or `docs/specs` (all tasks). The codebase map's "npm 11 withheld install scripts" is wrong → no task is planned on it (decision "npm allowScripts approvals").
