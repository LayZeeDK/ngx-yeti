1. **How a group with no `yetiButtonsItem` member renders** (spec Solution, sections 2, 3, 4, 8, `buttons--segmented`). Impact: HIGH (Yeti's own example contains such a group, and every consumer who forgets the part directive gets one). Confidence: MEDIUM (read in Aria's source; not run).
   - **Question.** "Aria decisions" row 27 makes `yetiButtons` host `ngToolbar`, and a `hostDirectives` entry cannot be conditional. Yeti's segmented control is an affixed `.buttons` holding `label.button` members that wrap radios, inside a `fieldset` that names the group (`buttons/docs.md`; `buttons/example.html`). Its members cannot be toolbar widgets: a `label` is not focusable, and Aria's arrow handling would `preventDefault` the radios' native arrow keys (ticket 29, finding 8). With no registered widget, Aria's `ListFocus.isListDisabled()` is true (an `every` over an empty list, `NC/src/aria/private/behaviors/list-focus/list-focus.ts:62-64`), so Aria renders the group `role="toolbar"` (with the package's role binding), `tabindex="0"`, `aria-disabled="true"`, and `aria-orientation="horizontal"` (`toolbar.ts:49-52`; `list-focus.ts:77-83`), on the server too. Its `keydown` handler returns at once (`private/toolbar/toolbar.ts:202-206`), so the radios keep their arrows. What should the group render?
   - **Option A (recommended): an item-less group renders as Yeti's plain group.** While the root's content query finds no member, `YetiButtons` binds `role`, `tabindex`, `aria-disabled`, and `aria-orientation` to `null`, and the replay guard does nothing; while it has members, `role` is `toolbar` and the other three equal Aria's values, computed from the same public signals (`Toolbar.disabled()`, `Toolbar.orientation()`, each member's `ToolbarWidget.disabled()`), which building-blocks 1.9's shared-attribute rule allows. Approve: the segmented control renders exactly as Yeti's example (no role, the `fieldset` is the group), no empty disabled toolbar becomes a Tab stop, no new public API, and the content query is equal on server and client, so hydration rewrites nothing. Cost: three more host bindings, and a copy of Aria's list-disabled formula over public signals that a later Aria release could change; layer 2 and layer 3 cases catch a drift.
   - **Option B: accept Aria's output.** Dismiss: the group becomes an extra Tab stop announced as a disabled toolbar around a radio group, which fails 4.1.2 and 2.4.3 in spirit and contradicts Yeti's markup.
   - **Option C: a second item directive for the segmented form** (for example `[yetiButtons]` and a separately selected group without Aria). Dismiss: new public API that no record names, a second class for one Yeti item, and a forgotten choice still produces Option B's output.
   - **Option D: the segmented control's radios become Aria widgets.** Dismiss: Aria's arrows would move focus without checking, replacing the platform's radio group, which works with no script.
   - **Option E: usage rule only, never write a group without members.** Dismiss: Yeti's own example would then have no way to be written, because a consumer writes no Yeti class (ADR 0003).
   - **Evidence and confidence.** Aria's behaviour with no items: read at `708d4c6e2` (HIGH that the code says so; MEDIUM that nothing else intervenes, not run). That a `null` binding on the host beats Aria's binding on the first pass and holds while neither changes: building-blocks 1.9's rule and ticket 30's measured hand-over, which used the same ordering (MEDIUM). The spec's layer 1 (`buttons--segmented`), layer 2, and layer 3 cases measure it.
   - **To overrule.** For B, remove the four null bindings and the segmented story's role assertions, and record a ledger row for the empty toolbar. For C, add the second directive, its selector, and its import to the spec, and amend "Aria decisions" row 27. Either way, the layer-3 segmented case changes its expected server HTML. Decided 2026-10-03 in ticket 50, decision 112 (orchestrator, full AFK mode).

2. **Which members are reachable by keyboard before Aria is live** (spec sections 2, 7, 10; layer 4's JavaScript-off count). Impact: HIGH (WCAG 2.1.1 with JavaScript off and inside `hydrate never`, which ADR 0011 promises). Confidence: MEDIUM.
   - **Question.** "Aria decisions" row 27 says the part directive's `[attr.tabindex]` "gives the first widget the Tab stop until Aria's `active()` is true", which ticket 30 measured as one reachable member per toolbar with JavaScript off, before hydration, and inside `hydrate never`. With no Aria behaviour in those states the arrow keys do nothing, so members after the first cannot be reached by keyboard at all: with JavaScript off for the whole visit, and inside `hydrate never` even with JavaScript on. The JavaScript-off ruling promises that "its native controls keep working" (map, Standing rulings; ADR 0011). Is the first-member-only Tab stop right?
   - **Option A: the record as written** (the spec's text today). Approve if one Tab stop matters more than reaching every member before Aria is live: it is what ticket 30 measured and what the user saw before choosing. Cost: members 2 to n are pointer-only with JavaScript off and in `hydrate never` (inferred from the measured Tab order and Aria's inactive keys).
   - **Option B (recommended): every member keeps its native Tab stop until Aria is live.** `YetiButtonsItem` binds `[attr.tabindex]` to `null` while no member is `active()`, then passes Aria's value through, as now. The server HTML then equals Yeti's own no-script group (a Tab stop per button), the same choice the user made for `tabs` ("All panels show (Recommended)": Yeti's no-script state with JavaScript off). Once Aria is live, members 2 to n change to `tabindex="-1"`: a state change after hydration, as `tabs` adds `hidden` once live, not a hydration mismatch. Approve: every member stays keyboard-reachable in every rendering mode, and the binding stays one computed with no platform check. Cost: the server HTML is no longer a single Tab stop, which changes "Aria decisions" row 27's wording and ticket 30's measured expectation; the change after hydration needs its own layer-4 case.
   - **Option C: Option A plus a usage rule that toolbars never sit in `hydrate never`.** Dismiss: it leaves the JavaScript-off loss and adds a rule nothing checks.
   - **Evidence and confidence.** Option A's states: measured in ticket 30 (three engines). That members 2 to n are unreachable: inferred from that measurement and from Aria's keys needing the client. Option B's behaviour: inferred from the same binding order ticket 30 measured; not run.
   - **To overrule.** To keep A (the spec's current text), remove the "(open: see ticket)" marks and record the loss in the spec's JavaScript-off list and as a ledger row. To take B, change the hand-over's server branch to `null`, the spec's sections 2, 7, 8, and 10 and the layer-2, layer-3, and layer-4 expectations (every member reachable before live; the post-live `-1` writes asserted), and amend "Aria decisions" row 27 and ledger A11Y-12. 4. **Disabling a member** (spec usage rules 5 and 6, Out of Scope, layer 2's recorded case). `ToolbarWidget` binds `[attr.disabled]` and `[attr.inert]` to `null` while soft-disabled, and `[attr.aria-disabled]` always (`toolbar-widget.ts:53-55`), so on the first pass it removes a consumer's static or bound native `disabled` from a member (read; inferred to happen on the server too) and overwrites `YetiButtonDisabledLink`'s `aria-disabled` on a link member (the same conflict ticket 29 measured for a busy button). Alternative: expose a second input on `YetiButtonsItem` for "disabled, not busy"; dismissed for now because a host directive input can be exposed under one alias only, and the record names `busy`. Impact: MEDIUM. Confidence: MEDIUM (the removal is read, not run; layer 2 records it). Decided 2026-10-03 in ticket 50, decision 115 (orchestrator, full AFK mode).

## Answer

Resolved 2026-10-03 by Claude Opus 5.5. Spec: [specs/buttons.md](../specs/buttons.md).

Two directives in `ngx-yeti/buttons`. The item directive `YetiButtons` on `[yetiButtons]` hosts Aria `Toolbar` by composition, binds `class="buttons"`, `data-gap` (`gap: YetiGap`), `data-affix` (`affix: boolean`), `role="toolbar"` over any written role, the presence attribute `data-ngx-yeti-item-buttons`, and the replay guard, provides `yetiButtonsToken`, and acquires the `buttons` item file. The part directive `YetiButtonsItem` on `button`, `a`, and `input` members, written beside `yetiButton`, hosts `ToolbarWidget` with `inputs: ['disabled: busy']`, lists `provideYetiAriaIds()`, and binds the `tabindex` hand-over to Aria's `active()`. `yetiButton` hosts nothing from Aria. The hand-over gets a layer-2 and a layer-4 test because it is inferred from source under the record's names. The Shift+Tab race and the one-pass role rewrite are carried as known issues with recorded, not asserted, e2e cases. The spec owns ledger rows A11Y-12 (closed) and A11Y-1b (covered by A11Y-1a's rule).

Counts: 50 user stories, 12 usage rules, 8 story ids, 6 open points. Points 1 and 2 are in the trap quadrant (HIGH impact, MEDIUM confidence) and carry their options records above. No open point blocks the spec: it carries the records' text (point 2) or its best reading (point 1), and overruling either changes host bindings and test expectations, not the item's shape.
