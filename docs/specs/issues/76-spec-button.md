## Question

What is the Angular API of Yeti's `button` component, and what does its spec say? Its decisions are already made in the records: its row in `building-blocks.md` Part 2 (and the "Aria decisions" section where it applies), its rows in [Decide: how the package maps each of Yeti's `data-*` attributes](26-decide-yeti-data-attributes-mapping.md), its item file under [ADR 0060](../adr/0060-item-styles-are-counted-links-to-the-consumers-yeti-build.md), its ledger rows, and the shared specs it links to.

## How to work it

Write `specs/button.md` with the `/to-spec` template and the map's Spec shape note, from the records only. The spec decides nothing a record has not decided. Anything it needs and no record settles goes under the ticket's `### Open` for the orchestrator. Append an `## Answer` that links the spec.

### Open

Each point is marked "(open: see ticket)" in the spec. Impact and confidence follow the trap-quadrant rule (map, Standing rulings, 2026-10-03). Point 2 is in the trap quadrant and carries its options record.

1. **`label[yetiButton]` as a fourth host, and the `input` host's type** (spec Solution, sections 2 and 4, usage rule 1). Part 2 row 26 lists `button[yetiButton]`, `a[yetiButton]`, and `input[yetiButton]`. Yeti's manifest note says to put the class "on a button, an a, a submit input, or a label wrapping a radio or checkbox", its docs and its `button` and `buttons` examples use `label.button` toggles, and ledger A11Y-1a's rule targets `.button:has(> input:checked)`, which only a label host can match. Building-blocks 1.1 makes every item a directive "on the elements Yeti's docs put its class on". Recommendation: add `label[yetiButton]` to row 26; keep `input[yetiButton]` as row 26 has it, with usage rule 1 limiting it to `type="submit"` (a selector on a static `type` would fail silently for a bound `[type]`). Without the label host, Yeti's no-script toggle and segmented control cannot be written and A11Y-1a's checked case has no host to test. Impact: MEDIUM. Confidence: HIGH (read in the manifest, docs, examples, and `button.css:83`, `:111-129`). Decided 2026-10-03 in ticket 50, decision 107 (orchestrator, full AFK mode).
2. **Where a link's disabled state lives** (spec Solution, sections 2 to 4, usage rule 4). Impact: HIGH, because it is public API on every button in every spec, and a wrong choice silently breaks native `disabled` on `button` hosts. Confidence: MEDIUM (the mechanism is read; the choice between B and C is a judgement).
   - **Question.** [ADR 0022](../adr/0022-button-declares-no-listeners.md) point 2 says the directive marks a disabled `<a>` `role="link"` and `aria-disabled="true"`, and its consequence says "Disabling a link takes two bindings (the target and the disabled state)", so a disabled-state input exists. Its considered options reject "a `disabled` input on every host that binds native `disabled`". But Angular sets a bound property on a directive input instead of the element whenever a directive on the element declares that input (`setPropertyAndInputs`, `NGP/core/src/render3/instructions/shared.ts:259-265`, read). So a `disabled` input on `YetiButton`, whose selector also matches `button`, would take `<button yetiButton [disabled]="saving()">` away from the native property, with no error. Where does the link's disabled state go?
   - **Option A: one `YetiButton` with a `disabled` input that binds `[attr.disabled]` on `button` and `input` hosts** (Material's shape, `NC/src/material/button/button-base.ts:60`, `:205-207`). Dismiss: it is exactly the option ADR 0022 rejects, and ADR 0003 point 3 and its considered options keep native state the consumer's.
   - **Option B: two classes with disjoint selectors**: `YetiButton` on `button`, `input`, and `label`, and an anchor class on `a[yetiButton]` with `variant`, `emphasis`, `size`, and `disabled`. Dismiss: a consumer must import a second class for every button link, a forgotten one renders an unstyled link with no error when only static inputs are used (building-blocks 1.9), the three inputs are declared twice, and the hero, stack, and cluster specs, already written with `<a yetiButton ...>` and `imports: [YetiButton]`, would all need amending.
   - **Option C (recommended): `YetiButton` keeps all four selectors and declares no `disabled`; a second directive, `YetiButtonDisabledLink` on `a[yetiButton][disabled]`, takes `disabled` and binds `role`, `aria-disabled`, and `'[attr.disabled]': 'null'`.** Angular matches attribute selectors against property-binding names (`NGP/compiler/src/render3/view/util.ts:213-217`, read), so the directive matches both `disabled` and `[disabled]` on a link and never matches a `button`, `input`, or `label`. Approve: `[disabled]` stays the native property on every non-link host, the consumer writes the same `[disabled]` on every host, existing specs' `<a yetiButton>` examples keep working with `YetiButton` alone, and a forgotten import of the new directive with a bound `[disabled]` is a compile error (NG8002, because `disabled` is not a property of `a`; inferred, not run). Cost: a second export and import for the one case of a disabled link, and a static `<a yetiButton disabled>` without the import renders a plain `disabled` attribute with no error.
   - **Option D: one class with an anchor-only input under another name** (`linkDisabled`, or an input aliased `aria-disabled` as Material's `ariaDisabled`). Dismiss: the input would also exist on `button` hosts, where it either does nothing (a confusing API) or binds `aria-disabled`, which fights `ngToolbarWidget`'s own `aria-disabled` binding inside a `buttons` group (measured, `prototypes/aria-buttons/README.md` finding 2).
   - **Option E: no input; the consumer writes `role="link"` and `[attr.aria-disabled]` on the link.** Dismiss: contradicts ADR 0022 point 2 ("the directive marks it").
   - **Evidence and confidence.** The binding rule and the selector matching: read in Angular 22.2.0's source (HIGH), not run. That NG8002 reports a forgotten import of C's directive: inferred from the same rule (MEDIUM). The directive's name, `YetiButtonDisabledLink` with `exportAs: 'yetiButtonDisabledLink'`, is the writer's choice under building-blocks 1.3 and not among the 46 names `yeti.d.ts` exports (LOW impact on its own).
   - **To overrule.** For B, split the selectors, move the three inputs to both classes, rename the second class, and amend the imports of the hero, stack, and cluster specs, whose examples put `yetiButton` on links. For A, also amend ADR 0022 and ADR 0003. Either way, layer 2's guard test (`<button yetiButton [disabled]>` sets the native property) stays, for A as an assertion that the forwarding works. Decided 2026-10-03 in ticket 50, decision 108 (orchestrator, full AFK mode).
3. **`spinner` acquired unconditionally** (spec sections 2 and 13). ADR 0060 point 9 says "the button item acquires `spinner` while a button is busy"; Part 2 row 26 says "the spec says how" and "acquiring it unconditionally is the smallest answer", and keeps `aria-busy` the consumer's, which no directive input sees. Recommendation: acquire `spinner` with `button` in the constructor and release both on destroy, and amend ADR 0060 point 9's "while a button is busy" with a dated note. Dismissed: a `busy` input on `YetiButton` (contradicts row 26 and would collide with `yetiButtonsItem`'s `busy`, "Aria decisions" row 27); a `MutationObserver` on `aria-busy` (a render callback and an observer per button for a 1.4 kB file, against ADR 0022's listener-free shape). Cost: one more small request on every page with a button (ticket 23 measured `spinner.css` at about 1.4 kB of source). Impact: MEDIUM. Confidence: HIGH. Decided 2026-10-03 in ticket 50, decision 109 (orchestrator, full AFK mode).
4. **No spinner presence attribute on the button host** (spec sections 10, 13, layer 4). A server-rendered busy button inside a `hydrate never` block, after every live button and spinner has left, loses its ring (its dim and cursor stay), because ADR 0060 point 4's DOM check looks for `[data-ngx-yeti-item-spinner]`, which the button host does not carry. Recommendation: accept and document it; a button rendered busy and never hydrated cannot stop being busy, which is a consumer error in itself, and layer 4 records the case. Alternative: `YetiButton` also sets `data-ngx-yeti-item-spinner` on its host, which closes the gap at the cost of one more attribute on every button and a second item's attribute set by a directive that is not that item's (ADR 0045 names one attribute per item directive). Impact: LOW. Confidence: MEDIUM (the residue is inferred from ADR 0060 point 4, not measured). Decided 2026-10-03 in ticket 50, decision 110 (orchestrator, full AFK mode).
5. **No `disabledInteractive`** (spec sections 4 and 5, Out of Scope). ADR 0022 point 3 describes a focusable disabled button "if the `button` spec offers it". Recommendation: not offered in the first milestone. Yeti's documented focusable-disabled form is the consumer's `aria-busy` with `aria-disabled` (manifest `a11y.notes`), and an input that binds `aria-disabled` and `type="button"` on a `button` host would fight `ngToolbarWidget`'s `aria-disabled` inside a `buttons` group (measured, ticket 29) and take `type` from the consumer. The busy submit button's double submit is a usage rule (spec usage rule 7; ADR 0022 consequences). Adding the input later is not breaking. Impact: MEDIUM. Confidence: HIGH. Decided 2026-10-03 in ticket 50, decision 111 (orchestrator, full AFK mode).
6. **Toggles and the contrast between their states** (spec usage rule 6, section 7 criteria 1.4.1 and 1.4.11, `button--toggle`). Building-blocks 1.10 asks a spec whose item draws a state by colour alone to assert the ratio between the two states, but sets no threshold. A medium or low toggle goes from no fill to the strong fill; a high-emphasis toggle goes from the variant fill to its strong stop, which is likely below 3:1 against each other (inferred, not measured). Recommendation: usage rule 6 (toggles use `medium` or `low`, as all of Yeti's toggle examples do); `button--toggle` asserts at least 3:1 between the pressed fill and the page for medium and low toggles, and records the high-emphasis pair; if that pair is below 3:1, add an anti-pattern story `button--anti-pattern-high-emphasis-toggle` and a ledger row owned by `button` (WCAG 1.4.1), with no package CSS. Impact: MEDIUM. Confidence: MEDIUM. Decided 2026-10-03 in ticket 50, decision 94 (orchestrator, full AFK mode).

## Answer

Resolved 2026-10-03 by Claude Opus 5.5. Spec: [specs/button.md](../specs/button.md).

Two directives in `ngx-yeti/button`. The item directive `YetiButton` on `button`, `a`, `input`, and `label` hosts with `[yetiButton]` (`exportAs: 'yetiButton'`) binds the static class `button` and the presence attribute `data-ngx-yeti-item-button` ([ADR 0045](../adr/0045-each-item-marks-its-host-with-its-own-attribute.md)), binds `data-variant`, `data-emphasis`, and `data-size` from `variant: YetiVariant`, `emphasis: YetiEmphasis`, and `size: YetiSizeControl` (`inert`), declares no listener ([ADR 0022](../adr/0022-button-declares-no-listeners.md)), hosts nothing from Aria (building-blocks "Aria decisions" row 27), and acquires the `button` and `spinner` item files ([ADR 0060](../adr/0060-item-styles-are-counted-links-to-the-consumers-yeti-build.md) point 9). The free behaviour directive `YetiButtonDisabledLink` on `a[yetiButton][disabled]` marks a disabled link `role="link"` and `aria-disabled="true"` and removes a static `disabled`. `aria-pressed`, `aria-busy`, `aria-disabled`, and native `disabled` and `checked` stay the consumer's. The spec owns ledger row A11Y-1a and writes the first rule of the package's accessibility stylesheet.

Counts: 54 user stories, 12 usage rules, 12 story ids, 6 open points (one, point 2, HIGH impact with MEDIUM confidence, so in the trap quadrant and recorded with its options above). No open point blocks the spec: the spec carries each recommendation, and overruling any of them changes a selector, an acquisition, or a test rather than the item's shape. The spec writes no ledger or upstream-bug row itself; point 6 may add one.
