## Question

What is the Angular API of Yeti's `demo` component, and what does its spec say? Its decisions are already made in the records: its row in `building-blocks.md` Part 2 (and the "Aria decisions" section where it applies), its rows in [Decide: how the package maps each of Yeti's `data-*` attributes](26-decide-yeti-data-attributes-mapping.md), its item file under [ADR 0060](../adr/0060-item-styles-are-counted-links-to-the-consumers-yeti-build.md), its ledger rows, and the shared specs it links to.

## How to work it

Write `specs/demo.md` with the `/to-spec` template and the map's Spec shape note, from the records only. The spec decides nothing a record has not decided. Anything it needs and no record settles goes under the ticket's `### Open` for the orchestrator. Append an `## Answer` that links the spec.

### Open

Each point is marked "(open: see ticket, point N)" in the spec, which carries the recommendation as its reading. Impact and confidence follow the trap-quadrant rule (map, Standing rulings, 2026-10-03). Points 2 and 9 are HIGH impact with confidence below HIGH, so each is recorded with its options.

1. **The selector: `figure[yetiDemo]` or `<yeti-demo>`** (spec sections 2, 4, 8, 11). Impact MEDIUM, confidence HIGH. Part 2 row 30, ticket 11 row 30, and ticket 26 rows 109 to 113 write `<yeti-demo>`, and ADR 0080 point 1 and `CONTEXT.md` use it as the example of a dash-case component selector. Yeti's root is a `figure` with an optional `figcaption` (`Y/src/components/demo/docs.md:12`, manifest `children`). A `figcaption` is valid only as the first or last child of a `figure`, so on a `<yeti-demo>` host a projected caption is invalid HTML. That breaks the hydration ruling's valid-HTML constraint (map, Standing rulings, item 54), and Yeti styles only `.demo > figcaption`. Building-blocks 1.1 and architecture-guide P1 say a component "on a consumer element ... takes an attribute selector", and P1 lists `<yeti-dialog>` as the shape to avoid. **Recommendation:** `figure[yetiDemo]`, class `YetiDemo`, `exportAs: 'yetiDemo'`. The component renders its template inside the consumer's `figure` and projects the `figcaption` first. Amend Part 2 row 30, ticket 11 row 30, ticket 26 rows 109 to 113, and the examples in ADR 0080 point 1 and `CONTEXT.md` (any dash-case example will do there, since none is in use). To overrule: keep `<yeti-demo>`, remove `figcaption` support and user stories 11 and 13, and accept that the caption loses Yeti's caption style and the figure's native semantics. A `role="figure"` host with `aria-labelledby` would need a caption element of another tag. Decided 2026-10-03 in ticket 50, decision 136 (orchestrator, full AFK mode).
2. **The frame's `sandbox`, and whether the frame runs script** (spec sections 2, 4, 7, Out of Scope; [ticket 25](25-decide-building-blocks-map.md) point 9 left it to this spec). Impact HIGH, because it decides whether an author's `code` can script the host origin, and the component must bypass Angular's sanitizer to build the frame at all. Confidence MEDIUM. Trap quadrant.
   - **Question.** `demo.js` writes the code into `srcdoc` with a module `<script>` for `yeti.js` and no `sandbox` (`demo.js:74`), so the framed document shares the host's origin and runs whatever the code holds. In Angular, `iframe|srcdoc` is an HTML security context (`NGP/core/src/sanitization/dom_security_schema.ts:79`). The sanitizer keeps no `link`, `base`, `style`, `script`, or `data-*` (`html_sanitizer.ts:52-112`), so the component must pass `bypassSecurityTrustHtml`. `sandbox` cannot be bound: Angular throws, and it removes a frame with a bound `sandbox` (`dom_security_schema.ts:127-153`; `iframe_attrs_validation.ts:15-34`). So the choice is one static value in the template. Which one?
   - **Option C (recommended): `sandbox="allow-forms"`, and no `<script>` in the frame document.** The frame gets an opaque origin and runs no script, so the bypass can never execute script on the host, even if a consumer breaks usage rule 2. Platform behaviour still works: `details`, `popover` and `popovertarget`, invoker commands, `showModal` through `command`, and `form method="dialog"`, which `allow-forms` keeps (the form-submission algorithm stops on the sandboxed forms flag before it handles `method="dialog"`; inferred from the HTML standard, layer 1 and 4 measure it). Approve, because it is the smallest safe value. It also needs no `yeti.js` served and no CORS header. And it fits [ADR 0040](../adr/0040-package-replaces-yetis-optional-modules.md) and architecture-guide P27: in an ngx-yeti application the behaviour comes from the package's directives, so a preview that ran `yeti.js` would show module behaviour the application does not have (tabs selected by `tabs.js`, not by Aria). The cost: an example that needs a module shows Yeti's documented no-module state (all tab panels, dots that follow fragments, no backdrop close).
   - **Option B: `sandbox="allow-scripts allow-forms"`, and `demo.js`'s module `<script>`.** It keeps Yeti's "whole Yeti page ... every module" (`demo.js:8-12`) while the origin stays opaque. Dismissed for now for three reasons. A module script from an opaque origin is a CORS request with `Origin: null`, so `yeti.js` loads only where the host sends `Access-Control-Allow-Origin` (inferred from the Fetch standard; not measured). It needs a second `assets` entry for `dist/yeti.js`, which ADR 0060 point 11's CSS-only entry does not copy (read in `Y/package.json` exports and `bin/build.js:115-130`). And it shows module behaviour that is not the application's. Approve it if layer 4 shows the module loads in three engines and an author needs module behaviour in previews.
   - **Option A: no `sandbox`, like `demo.js`.** Dismissed: with the sanitizer bypassed, any `code` value runs as the host page (stored script injection if a consumer binds untrusted data), and the HTML standard's own warning makes `allow-scripts allow-same-origin` equivalent (option D, dismissed for the same reason).
   - **Option E: an input that picks between two static frames (`@if` over two `iframe` elements).** Dismissed for the first milestone: it adds API for a need nobody has stated, and the safe default stays C. Adding it later is not breaking.
   - **Evidence and confidence.** The sanitizer and the binding refusal: read in Angular 22.2 (HIGH). The opaque origin and the CORS mode of module scripts: from the HTML and Fetch standards, not measured (MEDIUM). That platform openers work without `allow-scripts`, and that `method="dialog"` needs `allow-forms`: inferred from the HTML standard (MEDIUM). Layer 1 story `demo--sandbox` and layer 4 measure all of them.
   - **To overrule.** For B, change the template's static `sandbox`, add the module `<script>` to the frame document, add the `yeti.js` `assets` entry to the setup spec, document the CORS header, and turn `demo--sandbox` into an assertion that a module ran. For A, also add a usage rule that `code` must never hold anything but the author's own markup, and record the accepted risk in the decision log. Decided 2026-10-03 in ticket 50, decision 137 (orchestrator, full AFK mode).
3. **The second load of the frame at hydration** (spec sections 10, 11, layer 4). Impact MEDIUM, confidence MEDIUM. Ticket 33 row 7 leaves the choice to this spec: document the reload, or render the frame after hydration. Hydration writes the `srcdoc` binding on the first client pass, and the platform reloads on a same-value write (C2, measured in three engines; the Angular half inferred). **Recommendation:** document it, as [ticket 50](50-decide-open-points-of-the-specs.md) decision 36 does for `frame`. Rendering the frame only after hydration would cost the JavaScript-off reader the example, which the JavaScript-off ruling keeps. Under point 2's option C the second load costs only a cached stylesheet and the frame's scroll and toggle state. Layer 4 counts the loads, and if it confirms 2, an Angular row goes into `upstream-bugs.md`, as decision 36 has it. To overrule: wrap the `iframe` in `@if (live())`, state in Rendering modes that JavaScript-off readers see an empty box (Yeti's no-module state, `docs.md:28`), and change the load count to 1. Decided 2026-10-03 in ticket 50, decision 138 (orchestrator, full AFK mode).
4. **The grip renders only after hydration** (sections 2, 7, 10, 11). Impact MEDIUM, confidence HIGH. No record says when the grip appears. A server-rendered grip would be focusable with no value (a focusable `separator` needs `aria-valuenow`, which needs layout) and inert until hydration. Its presence also switches off the browser's corner (`demo.css:197-201`), so JavaScript-off readers would lose the only resize they have. **Recommendation:** `@if (live())`, with `live` set in `afterNextRender`. This is not a platform branch: both ends render no grip at hydration. It keeps Yeti's no-module state for JavaScript off (`docs.md:30`). To overrule: render it on the server with `aria-disabled` and no values, and accept the lost corner. Decided 2026-10-03 in ticket 50, decision 139 (orchestrator, full AFK mode).
5. **Strings: names and value text** (sections 2, 4, 7, Out of Scope). Impact MEDIUM, confidence MEDIUM. `demo.js` writes "<name>, live" as the frame title, "Resize <name>" as the grip's name, and "<stop>, <n> pixels" as its value text, and Yeti's markup has a "View Code" summary. Building-blocks 1.10 and architecture-guide P21 forbid package strings. **Recommendation:**
   - the frame's `title` is `preview`, which the manifest says it carries;
   - the grip's `aria-label` is `preview`, as the APG says the splitter's name matches the primary pane's (`windowsplitter-pattern.html:35`);
   - `aria-valuetext` is the stop name alone (`lg`), a value of Yeti's `width` vocabulary that the bar shows too, while `aria-valuenow` keeps the pixels;
   - the summary is the consumer's projected `summary`, or the browser's own default label;
   - `preview` becomes required.

   No string input: adding one later (a `valueText` function, as `MatSlider.displayWith`) is not breaking, the same reasoning as ticket 50 decision 28. To overrule: add `valueText: (stop, px) => string`, and keep the stop name as its default. Decided 2026-10-03 in ticket 50, decision 140 (orchestrator, full AFK mode).
6. **Writing the private tokens `--_yeti-demo-edge` and `--_yeti-demo-middle`** (sections 2, 8, Styles). Impact MEDIUM, confidence HIGH. Yeti places the grip through two private tokens that "the module measures and writes inline" (`demo.css:181-206`). Without them the grip stays at the figure's end and middle, off the box's edge whenever the box is narrower. [ADR 0004](../adr/0004-yeti-tokens-are-a-consumer-stylesheet-surface.md) and building-blocks 1.13 forbid reading or writing private tokens, and ADR 0004 says a spec that wants a third exception "reopens this record rather than adding one quietly". **Recommendation:** a third exception in ADR 0004 for tokens Yeti's CSS documents as written by the module that the package replaces. Today these two are the only ones. Write them as style bindings on the grip from signals, and add a layer-1 assertion of the grip's place, so that a pin move that renames them fails. To overrule: leave the grip at the figure's end (a visible regression), or add package CSS that positions it, which the "Accessibility CSS: Yes." ruling does not cover. Decided 2026-10-03 in ticket 50, decision 141 (orchestrator, full AFK mode).
7. **The frame's default stylesheet** (sections 2, 4, layer 2). Impact MEDIUM, confidence MEDIUM. `demo.js` falls back to the host page's `link[href$="yeti.css"]`, which an ngx-yeti page does not have (ADR 0060: the always-loaded group is bundled, and items are per-item links). **Recommendation:** with `stylesheet` unset, the frame links `yeti.css` under `provideYetiStyles()`'s `url` (default `yeti-css/`). That is Yeti's `dist/css/yeti.css`, which ADR 0060 point 11's `assets` entry already copies, and which `@import`s the whole of Yeti. The component reads the configuration the loader reads, through a package-internal export of `ngx-yeti/styles` (the [setup](../specs/setup.md) spec keeps the loader unexported; its point 1). To overrule: make `stylesheet` required, or default to the literal `yeti-css/yeti.css` and document that a changed `url` needs `stylesheet` as well. Decided 2026-10-03 in ticket 50, decision 142 (orchestrator, full AFK mode).
8. **Two layout touches outside building-blocks 1.5's list** (sections 2, 3, 11). Impact LOW, confidence MEDIUM. First, `demo.js:88-96` reads the box's min and max by writing `0px` and `100000px` to its inline size and restoring it. 1.5 limits direct writes to imperative calls. The spec keeps the probe, in handlers and observer callbacks after hydration only, restored in the same task, because the caps are `calc()` and `min()` over the container that a computed style does not resolve to pixels. Second, the keys and the drag mirror by the box's computed `direction`, as `demo.js:108` does, rather than by `Directionality`. The reason is 1.5's own exception: geometry follows CSS direction. **Recommendation:** accept both, with a note in building-blocks 1.5. To overrule: compute the max from the figure's content width less the box's computed border and padding, and use `Directionality.valueSignal` with the usage rule that a right-to-left demo sits under CDK's `dir`. Decided 2026-10-03 in ticket 50, decision 143 (orchestrator, full AFK mode).
9. **WCAG 2.2 2.5.7 Dragging Movements for the grip** (sections 7, layer 1). Impact HIGH, because the package's AA claim for the item depends on it and it adds behaviour Yeti does not have. Confidence LOW. Trap quadrant.
   - **Question.** The grip's pointer path is a drag (`demo.js:131-149`). 2.5.7 asks that every function operated by dragging can also be done with a single pointer without dragging, unless dragging is essential or the user agent provides it. The box's native corner is the user agent's and is exempt; the grip is the author's. Ticket 17 did not raise it (its axe run has no 2.5.7 rule). The keyboard path does not count, because the criterion is about pointers. What single-pointer path does the package add?
   - **Option A (recommended): a press and release on the grip that changed no width steps the box one stop narrower, and from the min it goes to the max.** A pointer user reaches every stop with taps, and the bar's label and `aria-valuetext` follow. No new element and no string. Approve, because it is the smallest change that covers the function (seeing the example at each stop). It costs a behaviour Yeti does not have, and the wrap-around is less discoverable than buttons.
   - **Option B: a tap toggles collapse and restore, as Enter does.** Dismissed: it reaches two widths only, so it does not cover "all functionality".
   - **Option C: package-rendered narrower and wider buttons.** Dismissed for the first milestone: Yeti's CSS has no style for them, they need names (strings the consumer would have to supply, P21), and they add tab stops.
   - **Option D: record the gap and add nothing.** Dismissed: the package's AA requirement "is never a recommendation" (map, Inherited preferences, Accessibility; ticket 50 decision 32 dismissed the same option).
   - **Evidence and confidence.** The criterion's text and its user-agent exception: recalled, not read in a local copy of WCAG 2.2 (MEDIUM). That a tap that cycles stops satisfies "achieved by a single pointer": a reading, not checked against the Understanding document (LOW).
   - **Ledger.** A new row: item `demo`; gap "the grip's drag has no single-pointer alternative"; source WCAG 2.2 2.5.7; what Yeti does `demo.js:131-149`, a drag only; what the package adds is option A; building block a template listener; verified *read*; tested by L1 and L4; owner `demo`.
   - **To overrule.** For C, add the two buttons to the template with consumer-supplied names and a play-function case for each. For D, remove the tap step and record the row as accepted. If the Understanding document's examples rule out a cycling tap, C replaces A. Decided 2026-10-03 in ticket 50, decision 144 (orchestrator, full AFK mode).
10. **Ledger and upstream-bug bookkeeping** (sections 7, layer 4). Impact LOW, confidence HIGH. A11Y-7's "Tested by" reads L1; the spec tests it at L1, L2, and L4, so the cell becomes "L1, L2, L4". Its "Package" column is confirmed as written. The point-9 row is added if point 9 stands. The conditional Angular row for the `srcdoc` reload follows point 3. This spec writes no ledger row itself. ## Answer

Resolved 2026-10-03 by Claude Opus 5.5. Spec: [specs/demo.md](../specs/demo.md).

`YetiDemo` is the package's only Angular component, in `ngx-yeti/demo`, on `figure[yetiDemo]` (point 1), with `exportAs: 'yetiDemo'`. The host has the static class `demo` and the presence attribute `data-ngx-yeti-item-demo`. It binds `data-height`, `data-width`, `data-resize`, and `data-stylesheet` from `height: YetiHeight`, `width: YetiWidth` (both `inert` on a `figure`), `resize: YetiResize`, and `stylesheet: string`. It takes the required inputs `preview` (the marker `data-preview`, the frame's title, and the grip's name) and `code`, and acquires the item file last in its constructor.

The template renders, in order:

- the projected `figcaption`;
- the preview box, with an id from an internal `YetiDemoPreview` that calls `injectYetiId('demo')`;
- an `iframe` with a static `sandbox` (point 2), whose `srcdoc` is built from `code` and bound through `bypassSecurityTrustHtml`, because Angular's sanitizer would strip Yeti;
- after hydration, the grip (point 4), a window splitter with Arrow keys, Home, End, Enter's collapse and restore, and `aria-controls` (A11Y-7);
- a `details` with the projected `summary` and the code.

The `srcdoc` reload at hydration is documented and counted in layer 4 (point 3). The template has no `@boundary` (ticket 50 decision 44) and no `@defer`. `demo.js` is mapped line by line.

Counts: 52 user stories, 11 usage rules, 7 story ids, 10 open points. Two are trap-quadrant points with options recorded above: point 2, the sandbox (HIGH impact, MEDIUM confidence), and point 9, 2.5.7 (HIGH, LOW). None blocks the spec, which carries each recommendation as its reading. The spec owns A11Y-7 and proposes one new ledger row (point 9). It writes no ledger or upstream-bug row itself.
