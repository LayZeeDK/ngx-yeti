# 09. Decide: which architecture principles and building-blocks rules carry over

Type: grilling
Status: resolved
Blocked by: 06, 07
Labels: wayfinder:grilling
Map: ../map.md

## Question

For each principle of the old `architecture-guide.md` (P1 to P26) and each cross-cutting section of the old `building-blocks.md` (1.1 to 1.14), decide whether it is carried over, adapted, or abandoned for Yeti, with the reason. Examples:

- DI and parent discovery;
- host directives;
- entry points and tree shaking;
- the rendered-state rule;
- render hooks;
- animation rules;
- the Breakpoint service;
- the Anchored pane;
- Triggers;
- the Nested menu;
- the spec shape.

## How to work it

AFK grilling against the research tickets and the decisions this ticket is blocked by. Some shared utilities may be replaced by the platform under the chosen browser target, for example the Anchored pane by CSS anchor positioning or Triggers by invoker commands. Say so with the evidence. Write `architecture-guide.md` and the cross-cutting part of `building-blocks.md` here, keeping each principle's origin, and list abandoned ones in this ticket's Answer.

### New for Yeti

- **P27 and ADR 0040.** The package replaces Yeti's optional modules; a consumer loads none beside it. From ticket 20's measurements (load-once modules miss every route; re-running costs N+1 events; shell panels survive navigation) and ticket 18's (hydration rewrites what a module did before load). Impact HIGH, confidence HIGH.
- **P28 and section 1.7.** Breakpoints are the container's; the package reads no viewport. Impact MEDIUM, confidence HIGH (checked in Yeti's CSS and modules).
- **P29 and section 1.8.** Openers, panels, and placement are the platform's and Yeti's; the package positions nothing and keeps the module behaviours. Impact HIGH, confidence HIGH (ADR 0003 point 5 already records the opening half; the placement half is checked in Yeti's CSS and bounded by ADR 0002).
- **P30.** Events are outputs; no event-manager plugin and no re-dispatcher. Restates the map's contract line (ticket 07) with ticket 16's measurements; ADR 0040's consequences hold the "no DOM event re-dispatched" clause. Impact MEDIUM, confidence HIGH.
- **Section 1.15.** Single-page application behaviour (setup, closing on navigation, fragment links under `<base href>`, listener cleanup). From ticket 20. Impact HIGH, confidence HIGH for the problems; the mechanism per item is ticket 25's.
- **The shared-vocabulary clause of P9.** Impact LOW, confidence HIGH.

### Questions asked and answered

Both sides were played against the sources; the answer recorded is the one the evidence supported.

1. **Does "directive first" survive when a `styleUrl` may force a component?** Yes, as a default with ticket 13 as the only grantor. Against: once one item is a component for styles, consistency might push all to be. For: the user's ruling is conditional ("where applicable"), ticket 04 measured a `styleUrl` working but ticket 13 has not yet chosen it, and a component changes the consumer's markup only by an attribute selector. P1 holds; the kind table lists no decided component.
2. **Is there still a "one directive per class" rule when markers mark parts?** Yes, extended to parts. Against: a marker is one attribute, and a consumer could write `data-close` as easily as a directive attribute. For: ADR 0003 point 2 says the consumer writes no `data-*` attribute of Yeti's, and the parts that carry markers are the ones that carry ids, outputs, or behaviour (the nav's close button, the field's error). A position-styled `li` gets no directive, which keeps the count honest.
3. **Does P4's token pattern still matter when the platform relates elements by id?** Yes, for ordering and for parts that need the root's state (a tab's selection, a field's `aria-describedby`); the platform's ids are what the token-coordinated directives render. The opener of a dialog is the one case with no parent and takes a template reference, which the old Triggers also did.
4. **Does the rendered-state rule survive?** No. It existed because the Breakpoint service wrote `current` in an `earlyRead` callback and a later-phase callback could run before the pass that rendered the swap. Yeti has no JavaScript-driven mode swap: every shape change is a container query. A spec that introduces one reinstates the rule in its decision log (1.5).
5. **Does the Breakpoint service survive in any form, for example for `serverBreakpoint`?** No. Against: a consumer might want a viewport-keyed input for their own layout. For: no Yeti attribute is viewport-keyed, `data-show` and `data-hide` are `@container` rules, and a viewport input would re-create a mechanism Yeti deliberately abandoned. Impact MEDIUM, confidence HIGH.
6. **Does the Anchored pane survive as a fallback for browsers without anchor positioning?** No. Anchor positioning is outside Baseline 2025 but Yeti guards it with a fallback the user accepted by choosing Yeti's target (ADR 0002 consequences: "Yeti's guarded features keep Yeti's fallbacks below their support"), and a package positioner would fight `popover`'s top layer and Yeti's `position-area` where it is supported. The spec states the fallback it relies on.
7. **Do Triggers survive for the tooltip, which is not a popover?** No. Yeti's tooltip is CSS on hover and `:has(:focus-visible)` (`tooltip.css:2`, `:57`), with Escape dismissal through `hidden` as the one package addition (ticket 03, ticket 17). No opener directive is needed.
8. **Does hover intent survive?** Yes, inside the dropdown spec as the `data-trigger="hover"` behaviour, because `hover.js` is a module the package replaces (ADR 0040) and `interestfor` is not in the target. The delays are Yeti's tokens, read from computed style, which also avoids `hover.js`'s inferred unit hazard (`upstream-bugs.md` Y2).
9. **Does the Nested menu survive for the nav's dropdowns?** No. A nav holds dropdowns as nested items, each its own spec; there is no mode switching, no disclosure tree, and no submenu class emission. The old family answered Foundation's Nest utility, which Yeti does not have.
10. **Should the package load Yeti's modules where they still work (the delegated ones)?** No; ADR 0040's considered options. One rule beats a split that a consumer would have to learn, and the delegated modules still fail in the shell on navigation.
11. **Should `yeti:*` events be re-dispatched or aliased so templates can bind them?** No. Measured by ticket 16: all three options work, only the output types `detail` without augmentation and costs nothing where unused, and none replays. Once the modules are not loaded, there is no DOM event to alias.
12. **Does "one code path" conflict with ADR 0002's "anything newer needs a fallback"?** It did as written; settled by taking Yeti's CSS fallbacks as the fallbacks and adding no package guard (P16; conflicts list 3). Both records hold.
13. **Does the animation fallback timer survive when Yeti dispatches events at the choice, not the arrival?** Only where a directive must act after a transition (focus after a close). The timer reads computed `transition-duration`, never a token's text, because of Y1. Impact LOW.
14. **Is a later-milestone check spec worth keeping at all?** No (ticket 07 left it to tickets 08 and 09). The closed unions catch literal values at compile time; a part outside its parent is NG0201; a bound input on a missing directive is NG8002; what remains (a static attribute with no imported directive, a computed value outside a vocabulary) is a gap Yeti itself never needed a check for, and the user's reason for deferring checks ("an issue Angular should correct") argues against specifying one here. P23 records it; ticket 08 records old ADR 0046's fate. Impact MEDIUM, confidence HIGH.
15. **Do defaults tokens survive?** As opt-in per spec with a reason. Yeti's defaults are the manifest's, and a token for every item would be a second place to look for a value Yeti's CSS already applies. Impact LOW.
16. **Does P21's logical-properties clause mean anything when the package ships no CSS?** No; recorded as carried with nothing to apply to, so the audit does not look for it. `:dir()` is inside the target in any case.
17. **Does the `inert`-not-`aria-hidden` rule hold when Yeti's CSS keys on `hidden`?** Adapted: `hidden` where Yeti keys on it, Aria's `inert` where Aria adds it, both from one signal on the tab panel; `aria-hidden` still never hides.
18. **Should the prefix be decided here, since ticket 07 named both 09 and 10?** No. The map's Notes say "the prefix itself is set with the glossary", and ticket 10 is blocked by this ticket, so the guide uses a stand-in (`pfx`) and ticket 10 replaces it. Deciding it here would pre-empt the glossary's selector-prefix call.
