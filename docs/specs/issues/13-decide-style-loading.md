# 13. Decide: how component styles load and unload

Type: grilling
Status: resolved
Blocked by: 04, 06, 08, 23
Labels: wayfinder:grilling
Map: ../map.md

## Question

How does each component's CSS reach the page? The options are Yeti's single stylesheet, loaded globally, or per-component files loaded and unloaded with the directives. If per component, by which mechanism? And what is the loading unit, and what does the consumer write?

## User ruling, 2026-10-02

The user's own message to the orchestrator, verbatim, on vendoring Yeti's files: "Vendoring: Yes, but if possible don't bundle Yeti's CSS in our package. Try to find a way to let the consumer". The message was cut off; the user then completed it, verbatim: "Vendoring: Try to find a way to let the consumer bring a build." So the decision looks for a mechanism in which the consumer brings their own build of Yeti, at the pin, and the package does not ship or inline Yeti's CSS, while the package still loads and unloads each part lazily. A library `styleUrl` that inlines Yeti's CSS into the package is acceptable only where nothing else meets the requirements, and the Answer says why.

## How to work it

AFK grilling against [Research: Yeti's styling model, and loading component styles lazily](04-research-yeti-styles-and-lazy-loading.md), and the old map's measured evidence (its tickets 182 to 198), whether this requirement carries over ([Decide: which standing preferences and user rulings carry over](07-decide-inherited-preferences-and-rulings.md)), and the browser target ([Decide: the browser target](06-decide-browser-target.md)). Record an ADR. Settle the loading unit's name with [Decide: the glossary](10-decide-glossary.md).

Note, 2026-10-01 (audit 0002, M6): the options to choose from are section 7 of [Research: Yeti's cascade layers and stylesheet order, for lazy loading](23-research-yeti-layers-and-import-order.md).

Note, 2026-10-02 (orchestrator, while recording tickets 10 and 26): the package's input types import Yeti's exported vocabulary types from `yeti.d.ts`, so a consumer's TypeScript has to resolve that file at the pin, also when the consumer brings their own build; under `skipLibCheck` an unresolved import silently turns every input type into `any` (inferred there). This ticket says where the types come from in each delivery option.

## Answer

Resolved 2026-10-02 (Fable 5.1), AFK grilling against the sources named above, with one probe. Record: [ADR 0060](../adr/0060-item-styles-are-counted-links-to-the-consumers-yeti-build.md). Probe: [prototypes/style-loading/README.md](../prototypes/style-loading/README.md), built in `D:/tmp/ngx-yeti-13/app` (a copy of ticket 23's Angular CLI 22.2 SSR workspace; ticket 23's folder was read only) and measured against a production SSR build in Chromium, Firefox, and WebKit through Playwright 1.63.0, with every item file's response delayed 300 ms and again with no delay. "Measured" below is this probe or the cited ticket; "read" is source; "inferred" is neither.

- **Mechanism: the item link.** A root service (`YetiStyles` in the probe; `provideYetiStyles({ url, preload })` configures it) owns one reference-counted `<link rel="stylesheet">` per item file, `href` `<url><kind>/<name>/<name>.css?v=<pin>` relative to `<base href>`, `url` defaulting to `yeti-css/`. Attributes `data-ngx-yeti-styles="<item>"`, `data-ngx-yeti-app="<APP_ID>"`, `data-beasties-skip`, and the `CSP_NONCE`. Each directive sets `data-ngx-yeti-item="<item>"` on its host (the probe wrote `data-ngx-yeti-part`; the name follows the glossary term below), acquires its item in its constructor on the server and the client, and releases it on destroy. Links are inserted in Yeti's `yeti.css` order from a rank table generated at package build, and removed in the frame after the live count is zero and no host with the attribute is connected (a `MutationObserver` on the document triggers the check). Angular's renderer never owns the links. The package ships and inlines no Yeti CSS (measured: the library FESM and `main-*.js` hold no Yeti rule).
- **Loading unit and its name, for [Decide: the glossary](10-decide-glossary.md):** **item file**, the one CSS file of a Yeti item, `yeti-css/css/<kind>/<name>/<name>.css`, 49 in all. _Avoid_: part file (Yeti's own word, `install.md:97`, but "part" names a sub-directive of a multi-part item in ADRs 0012 and 0013), family (the old map's unit), component stylesheet. Also for the glossary: the host attribute `data-ngx-yeti-item`, the link attributes `data-ngx-yeti-styles` and `data-ngx-yeti-app`, and the always-loaded group as already defined.
- **What the consumer writes** (build configuration only; a generator may write it): a build of Yeti at the pin under the specifier `yeti-css` (the Nx workspace package and `yeti-build` target of ticket 22 and ADR 0006, or a clone at the pin built with `npm run build` and installed as a `file:` or tarball dependency, ticket 21); one `assets` entry `{ "glob": "**/*.css", "input": "node_modules/yeti-css/dist/css", "output": "yeti-css" }` (66 files, measured); a global stylesheet that starts with `@layer yeti, ngx-yeti;`, then Yeti's always-loaded group as 16 `@import 'yeti-css/css/...'` lines in Yeti's order, then the package's own stylesheet; optionally `provideYetiStyles({ url, preload })`. No TypeScript per item, no carrier component.
- **Types.** Measured: with `import type { YetiGap } from 'yeti-css'` in the library and `yeti-css/dist/yeti.d.ts` present, a wrong input value fails the build (`TS2322`); with the file absent and Angular's default `skipLibCheck: true`, the same build passes with no error or warning. So the orchestrator's inference holds. Decided (ADR 0060 point 10): the package build copies `yeti.d.ts` at the pin into a generated source module that the package re-exports, and every input type imports from it; the consumer's TypeScript never resolves `yeti-css`, whatever they bring. Per delivery option: consumer brings a build (chosen): types from the package's generated copy, CSS from the consumer's build; package vendors Yeti's files (ADR 0006 point 3 before the ruling): the same generated copy, because a published `.d.ts` that imports `yeti-css` still needs the consumer to resolve it; `yeti-css` on npm with a peer dependency (future): `import type` from `yeti-css` and no copy, which reopens the point.
- **Cascade-layer rule.** Yeti's statement first, from the consumer's global sheet (`layers.css` is the first import); `ngx-yeti` declared right after `yeti` by the consumer's leading `@layer yeti, ngx-yeti;`; with Tailwind v4 the one shared statement of ticket 24, `@layer theme, base, yeti, ngx-yeti, components, utilities;` (or without `base`), plus `@source not inline('container');`. Item links add rules to layers already placed, so no load order moves a layer (ticket 23, measured; this probe's reload and tie rows). The package's own accessibility CSS is one small global stylesheet in `@layer ngx-yeti`, not per item.
- **Rendering-modes contract.** Server HTML: links in `<head>` in Yeti's order, hosts marked; styled with JavaScript off (measured). Full hydration: links adopted by attribute, 0 style mutations after `DOMContentLoaded`, 0 unstyled frames in Chromium and WebKit, 0 computed differences from full Yeti (measured). Incremental hydration: a dehydrated host (`hydrate never`, or `hydrate on ...` before its trigger) holds its link while it is on the page; hydration claims it (measured). Client-only `@defer`: fetch on construct, 18 to 20 unstyled frames at a 300 ms delay and 1 to 2 with none; the consumer's `preload` list gives 0 in all three engines (measured). Prerendering: the same HTML path (inferred; ticket 18 found prerender equal to SSR). Event replay, i18n, zoneless: the loader touches no component state and no change detection (read). Entry animations from an item file (Yeti's `enter` utility): the file must be present before insertion, by server rendering or by the preload list, because Angular removes an `animate.enter` class after one frame (ticket 189, read); not re-measured.
- **Leave animations and dehydration.** A class-form `animate.leave` host keeps its link until Angular removes the element: 0 unstyled frames while leaving, the link gone in the frame after, the bare `.card` probe reading 0 px afterwards, with a permanent function-form `(animate.leave)` listener on the page the whole time (measured; angular/angular#66244 does not reach library-owned links). `hydrate never`: the badge kept its styles after the last live badge left (measured; ticket 18 had measured the opposite for `styleUrl`).
- **Exceptions.** The always-loaded group and the package's own stylesheet are global. A directive acquires every item file its item's rules depend on, named in its spec: the button item acquires `spinner` while busy (ticket 23, measured); the smooth scrolling `toc.css` gives nav fragment links is documented, and in-page scrolling belongs to the fragment-links utility spec.
- **Rejected options, with reasons** (ADR 0060 lists them in full): library `styleUrl` inlining Yeti's CSS (ships Yeti's CSS; leaks under a consumer's function-form listener; loses `hydrate never` styles; loses Yeti's tie order: tickets 04, 18, 23, measured), so ruling 28's exception triggers nowhere and every item stays directives; a library-owned `<style>` from a generated string (ships Yeti's CSS; the fallback if the preload list is ever judged insufficient); Angular's own external styles (`RendererType2.getExternalStyles`: behind the same guard, uncounted dehydrated instances, private feature, server adoption keyed by the file name alone, which conflates `base/media.css` and `recipes/media/media.css`; read); consumer-written carrier components (TypeScript per item, and Angular-counted); `inject: false` entries per item (245 lines for the same runtime); everything global (fails the requirement); a paint gate (breaks focus and the accessibility tree, old 197); a grace period or `sheet.disabled` (stale styles for one cached frame in WebKit); making `stack`, `center`, `shell` global (unneeded with ordered insertion); the statement atop each item and a development order check (the loader owns no file; checks are a later milestone).
- **Questions asked and settled (the grilling record).** Q1 Can the consumer bring the build at all without consumer code? Yes: one `assets` entry and the import lines; measured. Q2 How does the package know the URL under `baseHref` and i18n? A relative URL resolves against `<base href>`; measured under `/sub/`; `deployUrl` is unsupported by ruling 29. Q3 Cache busting without hashed names? The pin in a query; the URL changes exactly when the CSS can (measured headers; the change inferred). Q4 Does Beasties copy or block? Angular 22.2 inlines only from build-time plans for its own global stylesheets and warns for every other link; `data-beasties-skip` silences it; the links stay render-blocking with no stale copy (measured). Q5 Does the leave guard reach a library link? No (measured, L3). Q6 Do dehydrated hosts hold? Yes, by the host attribute (measured, `hydrate never` and `hydrate on interaction`). Q7 Is Yeti's tie order kept? Yes, by ordered insertion from a generated rank table (measured, stack after center). Q8 The client-only `@defer` gap? Structural; closed per item by the preload list (measured 0). Q9 Where do the types come from? The package's generated copy of `yeti.d.ts` at the pin (measured why). Q10 Where does the package's own CSS go? One global stylesheet in `@layer ngx-yeti`, declared after `yeti` by the consumer's statement; per-item `<style>`s rejected as a second element kind for a few hundred bytes (judgment, reversible). Q11 Does ruling 28 apply anywhere? No: the measured `styleUrl` losses leave no item where a component's `styleUrl` makes lazy styles meet the requirements. Q12 Two applications on one page, CSP, `ng serve`? Links keyed by `APP_ID`; `nonce` from `CSP_NONCE`; assets are not Vite-tracked stylesheets; all inferred from the old map's 198, not measured. Q13 How much does lazy loading save at all? At most about 13 kB gzipped per page (19.5 kB for all of Yeti minified against 6.55 kB for the always-loaded group, measured); see Triage.
- **Side findings for the orchestrator.** (a) Angular's inlined critical copy of the always-loaded group drops six of Yeti's nine `:root` token blocks (the component tokens, `--yeti-border-width`, `--yeti-white`, the reduced-motion durations), so a server-rendered item paints with its rules but without its tokens until the async global stylesheet arrives; Firefox showed 1 to 2 such frames on localhost (measured in Chromium and Firefox; cause not pinned). It is the same for every mechanism and belongs in [upstream-bugs.md](../upstream-bugs.md) and the always-loaded group's documentation. (b) WebKit refetches a re-inserted `<link>` (1 unstyled frame on reload from the cache; Chromium and Firefox 0; measured). (c) ADR 0006 point 7 gains two build-time reads, `yeti-css/css/yeti.css` and `yeti.d.ts`; the orchestrator owns that record.

### Triage

- **The mechanism and what the consumer writes.** Impact HIGH, confidence HIGH: measured in three engines against a production SSR build, on the user's two rulings. Decided.
- **Lazy loading's ceiling.** Impact HIGH (abandoning the requirement would remove ADR 0060's machinery and change every spec's Rendering modes subsection), confidence NOT HIGH: the requirement was ruled for Foundation 6.9's stylesheet and carried over by ticket 07; for Yeti the whole of its CSS is 19.5 kB gzipped and the always-loaded group alone 6.55 kB (measured), so per-item loading saves at most about 13 kB of CSS transfer per page, at one request per item in use and the render-blocking cost of ticket 190. The user has reaffirmed lazy loading since (ruling 28 and the vendoring ruling, as read by the orchestrator), which is why this is recorded and not acted on. Decided by the user, 2026-10-02: "Keep per-item loading (Recommended)" (map, Standing rulings). The question was: keep per-item loading (the recommendation: it is built, measured, and costs the consumer three configuration lines), or load all of Yeti globally and reduce ADR 0060 to one `styles` line.
- **Types from a generated copy of `yeti.d.ts`.** Impact MEDIUM (reversible: the import path changes, the names and values do not), confidence MEDIUM: the silent `any` is measured; whether a build-time copy counts as reuse rather than redeclaring under the approved recommendation in the map's Prefix bullet is this ticket's reading. Not open under the triage rule; the orchestrator may put it to the user with the glossary.
- **The client-only `@defer` preload opt-in.** Impact MEDIUM (a 1 to 20 frame flash only for client-only deferred content whose item is not yet on the page), confidence HIGH (measured). Decided.
- **"item file" over "part file".** Impact LOW, confidence MEDIUM. Handed to the glossary ticket.
- **The Nx workspace symlink under the `assets` glob, `ng serve`, CSP, two applications.** Impact LOW, confidence MEDIUM (inferred, not measured). For the `setup` spec (the fifth shared spec, [map](../map.md) Destination) to measure.
