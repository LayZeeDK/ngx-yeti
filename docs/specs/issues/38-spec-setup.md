# 38. Spec: Setup (shared spec)

Type: task
Status: resolved
Blocked by: 13, 25, 35

## Question

What does a consumer write once per application to use ngx-yeti, and what does the `setup` spec say? This covers bringing a Yeti build at the pin, the `assets` entry, the global stylesheet with the cascade-layer statement and the always-loaded group, the package's accessibility stylesheet in its `ngx-yeti` layer, `provideYetiStyles()`, `provideYetiFragmentLinks()`, the hydration providers (`provideClientHydration()` with event replay, incremental hydration, and `withI18nSupport()`), the JavaScript-off guarantee under SSR and prerendering, Tailwind v4 coexistence, and the documented interactions with a consumer's `@boundary` once [Prototype: consumer `@boundary` and `@error` blocks around ngx-yeti, under SSR](37-prototype-consumer-boundaries-around-ngx-yeti.md) reports.

## How to work it

Write `specs/setup.md` with the `/to-spec` template and the map's Spec shape note, from the records only: the map's Standing rulings and Inherited preferences, the ADRs, `building-blocks.md`, `architecture-guide.md`, `ledger.md`, `upstream-bugs.md`, and `CONTEXT.md`. The spec decides nothing a record has not decided. Anything it needs and no record settles goes under the ticket's `### Open` for the orchestrator. Append an `## Answer` that links the spec.

## Answer

Resolved 2026-10-03 by Claude Opus 5.5. Spec: [specs/setup.md](../specs/setup.md).

The spec documents what a consumer writes once: Yeti built at the pin (the vendored workspace package with a cached `yeti-build` target, or a clone built and installed as `file:` or a tarball), the `assets` entry, the global stylesheet (`@layer yeti, ngx-yeti;`, the 16 always-loaded imports in Yeti's order, the package's accessibility stylesheet; the Tailwind v4 forms C1 and C2), `provideClientHydration(withI18nSupport())`, `provideYetiStyles({ url, preload })`, `provideYetiFragmentLinks()`, and an exact install of the version that names the pin ([ADR 0060](../adr/0060-item-styles-are-counted-links-to-the-consumers-yeti-build.md) points 7, 8, and 11; [ADR 0006](../adr/0006-yeti-pinned-develop-commit-vendored-and-gated.md); [ADR 0017](../adr/0017-release-policy-with-a-pinned-yeti.md)). It also owns the loader every item directive uses (counting, ordered insertion, removal once no presence attribute is connected, adoption at hydration, preload, nonce, `APP_ID`; ADR 0060 points 2 to 6 and [ADR 0045](../adr/0045-each-item-marks-its-host-with-its-own-attribute.md)), and documents consumer `@boundary` blocks once for every item (ticket 50 decisions 41 to 44; upstream bugs A4 and A8 under Known upstream bugs).

Counts: 57 user stories, 11 usage rules, 4 story ids, 7 open points. None is HIGH impact, so none is in the trap quadrant. No ledger or upstream-bug row is written by this ticket; the spec owns no ledger row and cites A11Y-1a to A11Y-1f, A11Y-6, and A11Y-16.

### Open

1. **The loader's entry point and the item directives' helper** (spec sections 3 and 4). ADR 0060 names "a root service" and `provideYetiStyles()`, but no record names the entry point or the call an item directive makes. The spec's reading: a secondary entry point `ngx-yeti/styles` exporting `provideYetiStyles`, its configuration type, and `injectYetiItemStyles(item: YetiComponentName): void`, which registers the release on `DestroyRef` and then acquires, called as the last statement of an item root's constructor (ticket 50 decision 42); the root service stays unexported; `preload` is typed `readonly YetiComponentName[]` from the generated `yeti-types.ts`. Options: (i) the reading above, mirroring `ngx-yeti/generated-ids` and `ngx-yeti/fragment-links`; (ii) put all of it in the primary entry point `ngx-yeti`, which every item already imports types from, at the cost of turning the primary entry point from types-only into a value import for every item. Recommendation: (i). To overrule: move the exports and change every item spec's import line. Impact: MEDIUM (every item directive calls it; renaming later is a breaking release under ADR 0017). Confidence: MEDIUM. Decided 2026-10-03 in ticket 50, decision 45 (orchestrator, full AFK mode).
2. **The accessibility stylesheet's import specifier** (sections 4 C and 4). No record names the file. The spec's reading: `@import 'ngx-yeti/accessibility.css';`, published through the package's `exports` map. Options: (i) `ngx-yeti/accessibility.css`, named for what it holds; (ii) a generic `ngx-yeti/styles.css`, which reads as if it held Yeti's CSS. Recommendation: (i). To overrule: change the last import line of the documented global stylesheet and the Storybook preview. Impact: MEDIUM (every consumer writes it). Confidence: MEDIUM. Decided 2026-10-03 in ticket 50, decision 68 (orchestrator, full AFK mode).
3. **A generator in the first milestone** (sections 4 E and Out of Scope). ADR 0060 point 11 leaves "whether the first milestone ships one" to this spec. The spec's reading: none; the documentation is the setup. Options: (i) none in the first milestone, citing the map's Milestones note ("I want to keep the initial milestone simpler and smaller in scope") and building-blocks 1.13 ("whether an `ng add` writes it is a later decision"); (ii) an Nx generator, reused as `ng add` as migrations are (map, Release policy), that writes the `assets` entry, the global stylesheet, and the providers, but cannot write step A (building Yeti), which is most of the work. Recommendation: (i); (ii) in a later milestone. To overrule: add a generator section and a layer-3 test that runs it against an empty application. Impact: MEDIUM. Confidence: MEDIUM. Decided 2026-10-03 in ticket 50, decision 69 (orchestrator, full AFK mode).
4. **Which Tailwind form the documentation leads with, and how layer 4 builds it** (sections 4 C and Layer 4). Ticket 24 measured both forms and ADR 0060 point 7 allows both. The spec's reading: lead with C2 (no preflight), which measured identical to Yeti alone, and document C1 beside it with its two measured losses (list markers, modal dialog centring) and no fix; test both under a second build configuration of the one fixture app, plus a check that the `ngx-yeti` cascade layer keeps its place, which ticket 24 did not include. Options: (i) the reading above; (ii) lead with C1 because it is `ng add tailwindcss`'s default, and then a fix for the two losses has to be measured first. Recommendation: (i). To overrule: swap the order in section 4 C and measure a C1 fix. Impact: MEDIUM. Confidence: MEDIUM. Decided 2026-10-03 in ticket 50, decision 70 (orchestrator, full AFK mode).
5. **Stray and leaked item links around a consumer `@boundary`** (sections 10 and 11). Ticket 37 measured a link left in the server HTML after a server-side catch, and a count leaked after a client constructor error; decision 42 closes the package directive's own constructor case only. Left: a host-binding or effect error caught on the server (the server never removes links), and another directive's error in the same view after the acquisition (the failed view is never destroyed). The spec's reading: document both, no change. Options: (i) document; (ii) remove links with a zero count before the server serialises, which needs a server-side hook the loader does not have today and helps only the JavaScript-off page; (iii) remove the count condition from removal, which would break hosts that are counted before they are inserted. Recommendation: (i). Impact: LOW (an extra request, and a stylesheet whose rules match only package-marked hosts). Confidence: MEDIUM (the host-binding case on the server is inferred). Decided 2026-10-03 in ticket 50, decision 71 (orchestrator, full AFK mode).
6. **Advice on upstream bug A4** (Known upstream bugs; Layer 4). The spec's reading: document the bug and the `inlineCritical: false` build option without recommending either setting, and have layer 4 count the token-less frames in each engine with inlining on and off. Options: (i) the reading above; (ii) recommend `inlineCritical: false` now, which makes the global stylesheet render-blocking at a first-paint cost nobody has measured for Yeti; (iii) say nothing beyond the bug. Recommendation: (i). Impact: MEDIUM (1 to 2 frames in Firefox, measured on localhost). Confidence: LOW (the cause is not pinned, and the option's cost is not measured). Decided 2026-10-03 in ticket 50, decision 72 (orchestrator, full AFK mode).
7. **What `provideYetiStyles({ url })` accepts** (section 4). ADR 0060 point 2 says the URL is relative to `<base href>`, and ruling 29 supports only `baseHref`. The spec's reading: a path relative to `<base href>` only; an absolute URL (a CDN) is not supported or tested. Recommendation: as read. To overrule: allow an absolute `url`, and add a layer-4 case for it and for the CSP it needs. Impact: LOW. Confidence: MEDIUM. Decided 2026-10-03 in ticket 50, decision 73 (orchestrator, full AFK mode).
