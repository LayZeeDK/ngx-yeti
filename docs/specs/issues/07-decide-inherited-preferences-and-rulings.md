# 07. Decide: which standing preferences and user rulings carry over

Type: grilling
Status: resolved
Blocked by: 01, 02, 03
Labels: wayfinder:grilling
Map: ../map.md

## Question

For each standing preference and user ruling in `.scratch/next-foundation-specs/map.md` (Notes: Standing preferences, Design criteria, Spec shape, the out-of-scope triage, the architecture guide note, and the rulings recorded in its tickets), decide whether it is carried over, adapted, or abandoned for Yeti, with the reason. Examples:

- directive over component;
- composition over subclassing;
- the implementation order;
- input naming from `data-*` options;
- signals and OnPush;
- WCAG 2.2 AA with the APG;
- `animate.enter` and `animate.leave`;
- rendering modes;
- testing layers;
- the release policy;
- the milestones;
- the class rule;
- one spec per docs page.

Added 2026-10-01. The user's own message to the orchestrator, verbatim: "21. What about adding CSS classes or setting CSS Custom Properties?" This was a reply to [Research: Yeti's JavaScript modules and what Angular adds](03-research-yeti-javascript-and-angular.md), which found that a wrapper adds only types for most items. The decision covers it as two parts of the class rule's successor:

- whether the package's directives set Yeti's classes, data attributes, and markers from typed inputs, so that the consumer writes none (the old map's ADR 0039 did this for Foundation's classes);
- whether, and how, typed inputs or providers set Yeti's public `--yeti-*` tokens as custom properties, for example per instance through host style bindings or per application through a provider.

The decision also applies the user's ruling that a component with `styleUrl` may replace a directive where that makes lazy styles meet the requirements (map, Standing rulings).

## How to work it

AFK grilling against the research tickets. Abandon what rests on Foundation 6.9's Sass, its jQuery plugins, its class contract, or its browser target, and keep what rests on Angular, accessibility, or the user's own preferences. Example: "Foundation CSS classes and state classes are the styling contract" becomes a question about Yeti's class and attribute contract.

Write the result as a table, with the record, its origin, the verdict, and the reason. Rewrite each kept or adapted item into this map's Notes, with its origin cited. The user's rulings in the old map are the user's own words; an adapted ruling says what changed and why, and never presents the adaptation as the user's words.

### The classes-and-custom-properties decision

The user asked, verbatim (the user's own message to the orchestrator, 2026-10-01; the orchestrator holds the conversation): "21. What about adding CSS classes or setting CSS Custom Properties?" The two parts of the ticket's framing are decided as follows. The wording below is the orchestrator's and this agent's, never the user's.

**Part 1: the directives set Yeti's class, attributes, and markers; the consumer writes none.** Decided yes, as the successor of the old map's class rule, and recorded as [ADR 0003](../adr/0003-directives-set-yetis-class-attributes-and-markers.md).

- Each item has exactly one class, which the directive binds as a static host class (`class: 'card'` from `src/components/card/manifest.json`, `"classes": []`).
- Every `data-*` attribute and marker of the item is set from a typed input, named from the attribute in camelCase and typed by its vocabulary ([ADR 0005](../adr/0005-closed-unions-from-yetis-vocabularies.md)). A consumer writes `<article nfsCard raised ratio="4/3">`, not `class="card" data-raised data-ratio="4/3"`. The per-attribute mapping, including which attributes stay the consumer's, is [ticket 26](26-decide-yeti-data-attributes-mapping.md)'s.
- There are no State classes to bind, because Yeti takes every state from the element or from ARIA (`src/guides/components.md`, "State is native"). So `:hover`, `:focus-visible`, `:disabled`, `:checked`, and `:user-invalid` need nothing from the package, and `aria-pressed`, `aria-busy`, `aria-current`, and `aria-invalid` are bound by the directive that owns that state and left to the consumer where the state is the consumer's (a `role="status"` on an alert, the `required` attribute on a control).
- An attribute that a person or a Yeti module can change before hydration is Angular-owned state, not a static attribute, because hydration writes every static template attribute again ([ticket 18](18-prototype-yeti-rendering-modes.md), measured: a static `open` reopens a closed `details`, a static `aria-selected="true"` leaves two tabs selected).
- The platform's opening attributes (`popovertarget`, `commandfor`, `command`, `popover`) are rendered by the directive with generated ids, so they work in the server HTML before any script.

**Part 2: typed inputs and providers do not set Yeti's `--yeti-*` tokens as a general contract.** Decided no for a token-per-input API, with two narrow exceptions, and recorded as [ADR 0004](../adr/0004-yeti-tokens-are-a-consumer-stylesheet-surface.md).

- Against a general token API: the 297 public token names are frozen but **their default values are explicitly not** (`src/guides/stability.md:19`, `:27`), so an input per token would publish a surface that moves under the package while old map ADR 0045 (`release-policy-devkit-version-scheme`)'s successor promises a deprecation path for anything public.
- Against per-instance inputs for the inputs that matter most: hues, chroma, and the scale "only take effect on `:root`, because Yeti computes every derived token there" (`src/guides/theming.md:38`). A host style binding on a component or directive host therefore cannot carry a theme, and a provider that wrote `:root` would be a global style write racing with hydration and shared between two applications on one page — the same hazard the old map measured for shared styles (old map ticket 198 (`prototype-candidate-costs-dev-hmr-csp`): with two applications on one page, the first to drop a shared unit removed it from the other).
- For the consumer, nothing is lost: a customisation is a block of custom properties in any stylesheet, a theme file, or a runtime `setProperty`, and an unlayered consumer `:root` block beats Yeti's layered tokens wherever it sits, including for a part file inserted later ([ticket 04](04-research-yeti-styles-and-lazy-loading.md) 4.2, measured in three engines). So the package documents the tokens each item reads and stays out of the way.
- Exception 1, state tokens: where a Yeti module writes a token as state, the directive writes it instead, as a host style binding from a `computed`. The measured case is `range.js`'s `--yeti-range-value`, which becomes a server-rendered binding so the fill is right in the first paint and `range.js`'s `MutationObserver` is not needed ([ticket 03](03-research-yeti-javascript-and-angular.md) 4.4). Angular supports this: `[style.--yeti-range-value]` and a `style` host binding holding a custom property are both covered by `styling_spec.ts:256-317`, and `DomRenderer.setStyle` routes any `--` name through `setProperty` (`dom_renderer.ts:437-447`), which is what the server renderer uses too.
- Exception 2, a per-instance derived token a spec names: a derived token such as `--yeti-color-primary` does work on any element (`theming.md:38`, measured on a card in [ticket 04](04-research-yeti-styles-and-lazy-loading.md) 4.2), so a spec may expose one as an input where the item's own API needs it. It states the token, why an input beats the consumer's own class, and that it is not a theme.
- Consequence for the map's "Not yet specified" line on theming beyond tokens: the package does not ship or wrap Yeti's `soft` and `sharp` theme files, and offers no theme provider. They are 19 lines of token values the consumer links after Yeti (`src/themes/soft.css`), and wrapping them would add a surface with no behaviour. A spec may cite them as examples. Impact MEDIUM, confidence HIGH.

### Questions asked and answered

Both sides of each question were played against the sources; the answer recorded is the one the evidence supported.

1. **Does "directive over component" survive a user ruling that allows components for lazy styles?** Yes, as a default with a named second exception. Against: the ruling could be read as licence for components wherever convenient. For: the ruling is conditional in the user's own words — "where applicable", and only where a component's `styleUrl` is what makes lazy styles meet the requirements. [Ticket 13](13-decide-style-loading.md) decides whether that condition is ever met; until it does, directives.
2. **Is Yeti's single class per item really the whole class contract, or are there variant classes hiding in the CSS?** Whole. Every component manifest I read declares `"classes": []` and puts its looks in `data-*` attributes, and the docs examples write one class per item (counted across `src/components/*/example.html`: `class="button"` 18 times, every other value a single item class, with two compositions, `center box` and `seam box`, which are two items on one element). Checked for the 22 components by reading the examples; for layouts and utilities this is inferred from the same manifest shape.
3. **Then what replaces the old map's Variant input machinery?** A closed union per vocabulary. Against: a consumer might want a value Yeti does not ship, which the old registries allowed. For: Yeti's values cannot be extended by a setting, because no Yeti setting generates a class or a value, and the vocabularies are frozen against removal and renaming, so a consumer who wants another look writes their own class on their own element — which the old map's rule always allowed for application classes. The user's stated ideal, a misspelt name failing to compile, is met.
4. **Are there State classes after all, for example a `.is-open` equivalent?** No. The states table in `src/guides/components.md` lists seven states, each from the element or ARIA. This removes the old map's largest class-rule mechanism (host bindings for State classes) and its copied-class reports.
5. **If state is native, does the package own any of it?** Yes, where hydration or a module would fight the markup. Measured in [ticket 18](18-prototype-yeti-rendering-modes.md): a static `open`, `aria-selected`, or `data-once` is written again at hydration, overwriting what a person or a module did before load. So the rule is: state the consumer sets once is theirs; state that changes before or after hydration is Angular's.
6. **Should the package replace Yeti's opening mechanisms with Angular click handlers, which would be the idiomatic Angular shape?** No. Measured: with JavaScript off, invoker commands and `popover` already open the dialog and the dropdown, and replay only reaches a handler later. Keeping the attributes is the better no-script and pre-hydration result, and Angular's DOM schema has no property for them anyway ([ticket 03](03-research-yeti-javascript-and-angular.md) 4.1), so the directive sets attributes and observes events.
7. **Does an input per `--yeti-*` token give the consumer anything a stylesheet does not?** Only for the two narrow cases above. The hues and the scale cannot work off `:root`, and derived tokens are already settable by the consumer's own class with no package code. An input per token would be a 297-name public surface over defaults Yeti says may still move.
8. **Could a provider set tokens for a whole application instead?** Not without a global style write, which means a shared `:root` block, hydration timing, and two applications on one page. The consumer's own global stylesheet does the same thing with none of that, and Yeti's theming guide is written for exactly that.
9. **Does Angular 22.2 even support a custom-property style binding, including on the server?** Yes. `[style.--my-var]` and a `style` host binding carrying a custom property are both in Angular's own acceptance tests (`styling_spec.ts:256`, `:278`, `:297`, case-sensitive names included), and `setStyle` sends any `--` name to `setProperty` (`dom_renderer.ts:438-443`). Checked by reading; not run.
10. **Does the WCAG 2.2 AA requirement still have teeth without Foundation's Sass to fix?** Mostly it needs less: axe found 0 violations on all 49 examples in three engines. What is left is behaviour the directives can own (Escape on the tooltip, closing on focus-out, the carousel's missing pattern, `aria-orientation` on vertical tabs) and `forced-colors`, which needs CSS the package would have to add. That last one is the open item.
11. **May the package add CSS of its own to Yeti's components at all?** Not settled by the sources. Yeti states that a component's skin is token-only and that class names are Yeti's (`theming.md:115`), and the old map's rule was to reuse upstream CSS rather than re-implement it; the user's WCAG requirement is unconditional. See `### Triage`.
12. **Do the old map's milestone rulings mean anything here, when their subject is Foundation's families and checks?** The reasoning does, the lists do not. The user's words about WCAG binding the consumer's pages and about keeping the first milestone small are general, and they are what the Notes text carries.
13. **Is the lazy-styles requirement still worth keeping, when Yeti's always-loaded group is only 6.5 kB transfer and 49 part files are plain CSS?** Keep it: the user called it library-wide, and the measurement says it is now cheap to meet, not that it is unnecessary. The question of whether any item is an exception is [ticket 13](13-decide-style-loading.md)'s, which now has a real candidate list (the two measured cross-part rules: a busy button's ring in `spinner.css`, and `toc.css`'s smooth scrolling for nav fragment links).
14. **Does "one spec per docs page" survive three sources that disagree on the count?** As "one spec per manifest item", which is also its docs page for 49 of the 50 pages. The manifest is what the frozen contract, the part files, the tokens, and the llms slices are keyed by. [Ticket 11](11-decide-spec-list.md) sets the count.
15. **Does the `Nfs` prefix carry?** The convention does, the letters do not; the package is not `ngx-foundation-sites`. Left to [ticket 09](09-decide-inherited-principles-and-building-blocks.md) and [ticket 10](10-decide-glossary.md) rather than decided here, because it is a naming decision the glossary owns.
16. **Does anything in the old map's process notes bind this map twice?** Several notes (AFK override, audits, commits, bundle layout, upstream filings) are already carried by this map's own Notes on the user's rulings. They are in the table as carried over with no change, so the inheritance record is complete and the Notes text below does not repeat them.

**The open item.** The user's accessibility requirement is unconditional and carries over: every directive and component meets WCAG 2.2 AA, and where a default fails, the spec states the fix rather than a recommendation. Eight of Yeti's deviations can be met with ARIA, behaviour, or a token. At least one cannot: Yeti ships no `forced-colors` rules, and under forced colours you cannot see a pressed or checked toggle, the selected tab, the checkbox, radio, switch, and range state, the native progress bar, or the current page in pagination ([ticket 17](17-research-yeti-accessibility-and-standards.md), measured). The fix the sources point to is CSS: the CDK `high-contrast` mixin and Material's per-control rules.

Why confidence is not HIGH: the sources conflict, and no measurement settles the conflict.

- Yeti states that a component's skin stays token-only and that "a class name belongs to Yeti, and a theme that restyled one would break when its internals change and could flatten its states" (`src/guides/theming.md:115`). Package CSS that selects `.button` or `.tabs` is exactly what that sentence warns against, and Yeti's validator refuses a class selector inside `@layer yeti.theme` (`theming.md:94`).
- The old map's own preference was to reuse the upstream's CSS and never re-implement what it has, with custom CSS only for what it cannot express, as the smallest documented rule — which is an argument for the fix, since forced colours is something Yeti does not express at all.
- Yeti's layers leave room: a rule in a layer the package declares above `yeti.components`, or an unlayered rule, wins without touching Yeti's files ([Research: Yeti's cascade layers](23-research-yeti-layers-and-import-order.md), measured: unlayered CSS beats late parts wherever it sits, and a consumer layer after Yeti's statement sits above it). So it is technically clean; what is unclear is whether it is wanted.
- It is also a question about the package's relationship with an upstream that is pre-beta and whose defaults may still move, and about whether the package or Yeti should carry the accessibility fix, which bears on filing upstream (human-only by kind).

The competing options, with no option applied as settled:

- (a) The package ships a small documented rule per gap, in its own layer above Yeti's, built from the CDK `high-contrast` mixin and Material's per-control rules, and lists each one in `ledger.md` as a feature the package adds. Meets the requirement, at the cost of package CSS that selects Yeti's classes and may need revisiting on a pin move.
- (b) The package adds no CSS: each spec states the gap as a documented limitation, with the token or markup a consumer can use, and the gap goes to `ledger.md` as unmet by either project. Keeps Yeti's contract intact and fails the user's requirement for the affected items.
- (c) The package ships the rules and the gap is reported upstream, so the fix can be removed later. Needs the user's confirmation for the filing (map, Standing rulings, item 44 and the Out of scope line), so it cannot be chosen here.

Recommendation, for the user to accept or refuse: (a), with each rule in one place the specs share, each named in `ledger.md` with the criterion it meets and the engines it was measured in, and each written against Yeti's state hooks rather than its internals, so a pin move breaks a test rather than a page. [Decide: the building-blocks map](25-decide-building-blocks-map.md) and [Decide: which ADRs carry over](08-decide-inherited-adrs.md) are the tickets that would record it.

> ### Inherited preferences and rulings (decided 2026-10-01, [Decide: which standing preferences and user rulings carry over](07-decide-inherited-preferences-and-rulings.md))
