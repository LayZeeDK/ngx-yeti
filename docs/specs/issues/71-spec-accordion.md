### Open

1. **Which heading form goes inside `summary`, and where its CSS lives** (spec sections 2, 4 usage rule 3, 7, and Testing; HIGH impact, MEDIUM confidence; trap quadrant).
   - **Question.** The user decided "Heading in summary (Recommended)" for row 21, and building-blocks "Aria decisions" row 21 leaves the spec to choose "between `<h3>` with one documented CSS rule and `span[role=heading]`", and to check "Firefox's lost heading on an opened item". Every accordion's heading structure, and its look, follow from the choice.
   - **Option A (recommended): a real heading (`h2` to `h6`, the consumer's level) as the summary's only content, plus one rule in the package's accessibility stylesheet** (`@layer ngx-yeti`, `ngx-yeti/accessibility.css`, ticket 50 decision 68). The rule selects a heading that is a direct child of `.accordion > details > summary` and sets its font, letter spacing, and text wrapping to inherit from the summary, so the row looks like Yeti's plain summary. Approve: a native heading follows the first rule of ARIA use; ticket 30 measured a level-3 heading inside the still-expandable summary in Chromium (CDP) and in Firefox (UIA), and its UIA output (`prototypes/aria-composition-accordion/results/uia.txt`, `/d`) shows the heading kept on the row that was clicked open, which answers the Firefox check for this form. The rule closes the one cost ticket 30 measured (29.17 px bold text, rows 7.4 px taller), it is one small documented rule in the layer the user's "Accessibility CSS: Yes." ruling allows, and it is tied to ledger row A11Y-11. Its layout is inferred: ticket 30 suggested `font: inherit` but did not try it, so layer 1 asserts the computed font and the row height against a heading-less summary.
   - **Option B: the same heading, with the rule documented as consumer CSS** (a usage rule and an example), and no package CSS. Dismissed as the default: every consumer who follows usage rule 3 would have to copy the rule or accept a different look, and the user's Package CSS ruling exists for accessibility gaps the package closes. It is a fallback if the orchestrator reads that ruling as covering only forced-colours and similar WCAG failures of Yeti's own CSS (the map's text says each rule is "built from CDK's high-contrast mixin and Material's per-control rules", which fits forced colours, not this rule).
   - **Option C: `span role="heading" aria-level="N"`.** No CSS needed: ticket 30 measured 0 property differences from Yeti's summary. Dismissed: in Firefox (UIA) the row that was clicked open lost its heading role ("tekst") in two runs, cause not isolated, which is the loss the Aria decision asks the spec to check; and it uses ARIA where a native element exists.
   - **Option D: a real heading with Yeti's heading look and no CSS.** Dismissed: the rows grow by 7.4 px with 29 px bold text against Yeti's summary (ticket 30, measured), so the accordion no longer looks like Yeti's documented component.
   - **Evidence and confidence.** Measured: the Chromium and Firefox trees, the styles diff, the valid parse, axe 0, every rendering mode the same as plain `details` (ticket 30). Not measured: WebKit's tree (not inspectable on Windows), any screen reader's heading navigation, and the rule itself. MEDIUM, because the rule is untried and the Package CSS ruling's reach is a reading.
   - **To overrule.** For B: remove the package-CSS row from spec section 2, move the rule's description into usage rule 3 and the usage examples, and change the Styles subsection's item 5. For C: replace usage rule 3's heading with `span[role=heading][aria-level]`, remove the CSS row, and turn the engine-tree check into a known failure with a ledger note. For D: remove the CSS row and the layer-1 font assertion. Decided 2026-10-03 in ticket 50, decision 95 (orchestrator, full AFK mode).

2. **The open state's API** (spec sections 2, 4, 5; MEDIUM impact, MEDIUM confidence).
   - Part 2 row 21 says "`open` model written from a `toggle` host listener". Two things no record settles: the name, and what a parent's write does when `open` may never be bound.
   - **Recommended (the spec's reading):** `isOpen`, a read-only signal, plus an `isOpenChange` output; no model input and no methods. A consumer opens a row from code by setting the element's own `open` property in a handler (usage rule 6), and `isOpen` follows the `toggle`. Reasons: the name follows building-blocks 1.3 (`isX` where the verb collides) and ADR 0021 point 1 (the dialog's `isOpen`, "so it does not collide with the dialog's own `open` attribute and property"); an input named `open` would also capture the consumer's static `open` attribute, the documented way to ship a row open, and a `model<boolean>` cannot take `booleanAttribute`, so `<details yetiAccordionItem open>` would fail to type-check (inferred from `strictTemplates`, not run). With no input there is no parent write that could undo a toggle made before hydration. Adding a model input later is not breaking.
   - **Alternative:** an `isOpen` model whose parent writes are applied by setting `open` in an `afterRenderEffect` that skips its first run, so the creation read wins (ticket 33's audit, row 3, inferred). It gives `[(isOpen)]` two-way binding, at the cost of a parent value that can disagree with the DOM at creation and an imperative write the hydration audit only inferred to be safe.
   - **To overrule:** turn `isOpen` into `model<boolean>()` in spec section 4, add the write path and its layer-2 and layer-4 cases (a parent value at creation that differs from the DOM, and a pre-hydration toggle under a bound `[(isOpen)]`), and update the Material table. Decided 2026-10-03 in ticket 50, decision 96 (orchestrator, full AFK mode).

3. **Whether a replayed `toggle` emits `isOpenChange` after the creation read already found the new state** (spec sections 4 and 10; MEDIUM impact, MEDIUM confidence).
   - The [events](../specs/events.md) spec says state found at creation emits nothing (rule 9) and also that a replayed `toggle` "reaches the package handler once the boundary hydrates, and the handler then emits: late, but once". For the accordion both cannot hold: the creation read already sees a row the visitor opened before hydration.
   - **Recommended:** emit only when the live `open` differs from `isOpen()`, so the replayed `toggle` emits nothing; `isOpen()` is already right. This follows rule 9 and the open-state ruling's "read once", and needs no replay detection.
   - **Alternative:** emit on every `toggle` event after creation, even with no change, so a consumer hears late about a toggle made before hydration. Dismissed: it emits for a state found at creation and fires for a `toggle` caused by hydration's own write-back of a static `open`.
   - **To overrule:** change section 4's `isOpenChange` row and the layer-4 case "no `isOpenChange` was logged", and amend the events spec's replay sentence for `details`. Decided 2026-10-03 in ticket 50, decision 97 (orchestrator, full AFK mode).

"Building block": `details` and `summary`, WHATWG's `summary` content model. "Verified": measured (ticket 30, Chromium CDP and Firefox UIA). "Tested by": L1, L3, L4, and the engine-tree check. Only the orchestrator edits the ledger. Decided 2026-10-03 in ticket 50, decision 98 (orchestrator, full AFK mode).

Ticket 17's forced-colours screenshots did not list the accordion, and the open state is the chevron drawn in `currentColor` borders, which forced colours keep (inferred). ## Answer

Resolved 2026-10-03 by Claude Opus 5.5. Spec: [specs/accordion.md](../specs/accordion.md).

Two directives in `ngx-yeti/accordion`: the item directive `YetiAccordion` on `[yetiAccordion]` (`exportAs: 'yetiAccordion'`) binds the static class `accordion` and the presence attribute `data-ngx-yeti-item-accordion` ([ADR 0045](../adr/0045-each-item-marks-its-host-with-its-own-attribute.md)), ends its constructor with `injectYetiItemStyles('accordion')`, and provides `yetiAccordionToken`; the part directive `YetiAccordionItem` on `details[yetiAccordionItem]` (`exportAs: 'yetiAccordionItem'`) reads `open` once at creation, follows `toggle` (read live), and exposes `isOpen` with `isOpenChange`. Nothing binds `open`. Native platform, level 1, no Aria and no CDK, as the user decided ("Heading in summary (Recommended)"). No module to replace (`js: null`); the spec maps each platform behaviour instead. `name` stays the consumer's; a row shipped open with a static `open` loses a close made before hydration, which is documented and asserted as residue (ticket 33). Find-in-page and fragment links open rows natively and `isOpen` follows; consumer bare links go through [fragment-links](../specs/fragment-links.md). Owns ledger row A11Y-11, closed by the heading usage rule plus one proposed rule in `@layer ngx-yeti`. Firefox's lost heading on an opened row: measured only for `span[role=heading]`; the `h3` form kept it in ticket 30's UIA output, and the spec adds a recorded engine-tree check.

Counts: 51 user stories, 10 usage rules, 5 story ids, 5 open points. Point 1 is HIGH impact with MEDIUM confidence, so it is in the trap quadrant and is recorded with its options above. None blocks the spec: it carries each recommendation as its reading.
