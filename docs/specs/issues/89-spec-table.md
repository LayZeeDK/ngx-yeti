### Open

Three points no record settles. None is HIGH impact, so none is a trap-quadrant decision; point 1 still carries its options, because it adds public API.

1. **The pinned header row: who renders `data-sticky` on the `thead`?** (MEDIUM impact, MEDIUM confidence). Yeti's docs ("`data-sticky` on the `thead` pins the header row at `--yeti-sticky-offset`"), its CSS (`Y/src/components/table/table.css:53-57`, plus the always-loaded `[data-sticky]` rule, `Y/src/layouts/attributes.css:318-344`), and its own test (`Y/test/browser/components/table.spec.js:79-91`) all pin a `thead` with `data-sticky`. The manifest names it only in the `> thead` child's description and declares no marker for it, so ticket 26 has no row, Part 2 row 39 names no part for it, and the contract check, which reads the manifest, cannot cover it. A consumer may not write `data-sticky` (ADR 0003 point 2; ADR 0070's 2026-10-03 note).
   - **Option A (recommended): a Part directive `YetiTableHead`** on `thead[yetiTableHead]`, `exportAs: 'yetiTableHead'`, with `sticky: boolean` (`booleanAttribute`) rendering `data-sticky`, injecting `yetiTableToken` optionally and reading nothing, with no presence attribute and no item file (ticket 50 decision 6). Approve because it is ADR 0070 kind C applied to a marker Yeti documents on a child, with the same input name and type `sticky` already has on `yetiStackChild`, `yetiSidebarChild`, `yetiShellRegion`, and `yetiNav` (ticket 26 rows 60, 67, 86, 126), and it keeps a documented Yeti feature reachable. With it: the table shares ledger row A11Y-22 (a stuck head over rows with focusable content can hide focus, WCAG 2.2 2.4.11), owned by `sidebar`, through the spec's usage rule 10 (set `--yeti-scroll-padding` on `:root` to at least the offset plus the head's height) and a layer-4 Shift+Tab walk, after decisions 47 to 49; and `upstream-bugs.md` gains a new docs-and-manifest row ("the table manifest declares no `data-sticky` marker for `> thead` while its docs, CSS, and test use one"; verified *read*; no reproduction needed; not filed), after Y9 and Y11.
   - **Option B: the consumer writes `data-sticky` on the `thead` statically.** No directive binds it, so hydration writes back the same value and nothing conflicts. Dismiss: it breaks ADR 0003 point 2 and the typed-input rule, a misspelling is silent, and it is the one Yeti attribute a consumer would write by hand.
   - **Option C: leave the pinned head out of the first milestone** and record the manifest gap in `upstream-bugs.md` only. Dismiss: it removes a documented, tested Yeti feature with no technical reason; a part directive is a few lines and types only.
   - **Option D: an any-element `yetiSticky` marker directive.** Dismiss: ticket 26 maps every `data-sticky` declaration as kind C or R scoped to its parent, never as kind G, and an any-element form would compile on elements where Yeti never documents it.
   - **Evidence and confidence.** The docs, CSS, and test: read (HIGH). That no record maps it: read across ticket 26, Part 2 row 39, and ticket 11 row 39 (HIGH). That the stuck head can hide focus: inferred from the same scroll-padding model as A11Y-22, not measured (MEDIUM). That a head inside a `scroller` does not pin to the page: inferred from CSS sticky positioning and `scroller.css:7` (`overflow-x: auto` makes the scroller a scroll container on both axes), not measured (MEDIUM).
   - **To overrule.** For C, remove `YetiTableHead`, user story 24, usage rule 10, the `table--sticky-head` story, the sticky rows of sections 2, 4, and 5, the layer-2 and layer-4 sticky cases, and the A11Y-22 reference; keep the upstream-bugs row. For B, replace `YetiTableHead` with a usage rule naming the static attribute as a documented exception to ADR 0003 and amend ADR 0003's consequences. Decided 2026-10-03 in ticket 50, decision 195 (orchestrator, full AFK mode).
2. **The kind of `nowrap` on a cell** (LOW impact, MEDIUM confidence). Ticket 26 row 150 recommends `output` (HTML `nowrap` on `th` and `td` means what `data-nowrap` means) and leaves each spec to confirm the kind on its hosts. The spec's reading follows it: `[attr.nowrap]` is bound from the input beside `data-nowrap`. But HTML's `nowrap` is obsolete, so a server-rendered cell would carry an attribute the Nu Html Checker reports, which Yeti's own markup never has (ticket 17 found Yeti's examples Nu-clean), and the visible result is the same either way because `data-nowrap` already keeps the line. **Recommendation:** `removed` (`'[attr.nowrap]': 'null'`) on all three hosts: the server HTML stays Yeti's documented markup and conforming, and the static-form cost is the same write-back-and-remove pass that `align` on the same host already has, covered by the same decision-9 e2e case. If kept as `output`, nothing else in the spec changes. Decided 2026-10-03 in ticket 50, decision 196 (orchestrator, full AFK mode).
3. **Forced colours** (LOW impact, MEDIUM confidence). Yeti has no `forced-colors` rule (ticket 17 section 2.6). Under forced colours the stripes and the hover tint disappear, and row rules, cell borders, and the header rule take system colours (inferred, not measured). Neither tint draws a state or carries information (1.4.1 is met in the spec without them). **Recommendation:** no ledger row and no package CSS, after decisions 26, 30, and 78; layer 4 records the borders and the header rule under `forcedColors: 'active'` with a screenshot in three engines. If the rules vanish, a ledger row owned by `table` and one `@layer ngx-yeti` rule follow, as decision 88 says for breadcrumbs. Decided 2026-10-03 in ticket 50, decision 197 (orchestrator, full AFK mode).

## Answer

Resolved 2026-10-03 by Claude Opus 5.5. Spec: [specs/table.md](../specs/table.md).

Three directives in `ngx-yeti/table`: the item directive `table[yetiTable]` (`YetiTable`), binding the static class `table`, the presence attribute `data-ngx-yeti-item-table`, and `data-size`, `data-striped`, `data-hover`, `data-border`, `data-nowrap`, and `data-fixed` from `size: YetiSizeControl` and five `boolean` inputs (ticket 26 rows 143 to 148); the part directive `yetiTableCell` on `th`, `td`, and `tr` (`nowrap`, and `align` typed `YetiTableAlign = Extract<YetiAlign, 'start' | 'center' | 'end'>`, rows 150 and 151); and the any-element `yetiNumeric` (`YetiNumeric`, row 149), which loads no item file. `border` and `align` are `removed`, `size` and table-level `nowrap` are `inert`. Native platform, level 1, types only; no Module, no Aria `Grid`, no CDK table, no ledger row (Part 2 row 39). The hydration ruling's explicit `tbody` is usage rule 1, extended to parser-shaped structure and `tr`-selector row components (usage rule 2), with a layer-3 assertion and a layer-4 negative control. The usage rules also carry the `yetiIcon` exception from the table's side (ticket 50 decision 39), the `yetiBorder` exception (box usage rule 3), the scroller for wide tables (decision 59), and the consumer's name and `scope`.

Counts: 56 user stories, 3 open points (point 1 MEDIUM impact, points 2 and 3 LOW; none blocks the spec).
