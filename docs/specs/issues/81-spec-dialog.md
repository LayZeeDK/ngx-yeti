### Open

Each point is written into the spec as its best reading and marked "(open: see ticket)". Impact and confidence are rated as the map's trap-quadrant ruling asks. Point 1 is the only trap-quadrant point (HIGH impact, MEDIUM confidence) and carries its options record.

1. **The parent's initial `isOpen` against the element's state** (spec section 4, Open state, point 2; HIGH impact, MEDIUM confidence; trap quadrant). The open-state ruling says `isOpen` "is read from the element once, when the directive is created" (ADR 0021 note of 2026-10-03; map, Standing rulings). With `[(isOpen)]="x"`, Angular sets the parent's value after the constructor, so the two can disagree at the first render: the user opened the dialog before hydration while `x` is `false`, or `x` starts `true` while the dialog is closed. No record says which wins.
   - **Option A (recommended): the element wins.** At the first render the model is set to the element's state, and `isOpenChange` emits only when that differs from the bound value, so the parent's two-way state follows the dialog. `opened` does not emit (events rule 9). Later parent writes are commands (`showModal()` or `close()` in an `afterRenderEffect`). An initial `true` opens nothing; a dialog that must open on load calls `open()` from `afterNextRender`. Approved because it is the ruling's literal reading, it keeps a pre-hydration open (the harm ticket 34 measured), and it keeps the parent's state equal to the dialog's.
   - **Option B: the parent's initial value wins on the client.** After the first render `true` opens and `false` closes. Dismissed: on a dialog the user opened before hydration with a parent bound `false`, the package itself closes it at hydration, undoing the user's action, which is what the ruling exists to prevent (a lesser form of ticket 34's failure, not the hidden-but-blocking state).
   - **Option C: the element wins, and nothing emits at creation**, the strictest reading of events rule 9. Dismissed: the parent's signal stays `false` while the dialog is open, and a later parent write of `false` is no change, so it never reaches the model and cannot close the dialog (inferred from how a signal input ignores an equal value).
   - **Option D: a read-only `isOpen` signal plus the outputs, no model.** Dismissed: building-blocks 1.4 and the events spec's rule 8 decide a `model()` for the dialog's open state.
   - **Evidence:** the ruling's words (quoted in the map); ticket 34 measured that a bound `open` hides a modal dialog opened before hydration (three engines); that `model().set()` emits `isOpenChange` and a parent write does not is Angular's documented `model()` behaviour (read, not measured here). Not measured: a pre-hydration open under a bound `isOpen`. The spec's layer 2 case (initial bound `true` on a closed host) and layer 4 case (ticket 34's regression with `[(isOpen)]` bound `false`) measure it.
   - **To overrule:** for B, replace section 4's Open state point 2 with "the parent's initial value is applied after the first render", turn layer 2's initial-`true` case around, and add a usage rule that a bound `isOpen` must start `false`. For C, remove the emission and add a usage rule telling consumers to read `isOpen` from the directive after the first render. Decided 2026-10-03 in ticket 50, decision 146 (orchestrator, full AFK mode).
2. **Observing the open through the dialog's `toggle` event** (spec sections 2 and 4; MEDIUM impact, HIGH confidence). Part 2 row 31 says the open is observed "through the `dialog` `toggle` event if ticket 01 places it inside the target, else `dialog.js:36-50`'s task deferral"; ticket 01 did not check it. `@mdn/browser-compat-data` 8.1.4, the copy ticket 01 installed (`D:/tmp/ngx-yeti-01/node_modules/@mdn/browser-compat-data`), lists `api.HTMLElement.toggle_event.dialog_elements` in Chrome 132, Firefox 133, and Safari and Safari iOS 26 (read), inside Baseline 2025's Chrome 141, Firefox 145, and Safari 26.2. Recommendation: `toggle`, so `opened` follows every open (command, `open()`, a model write, the consumer's `showModal()`), not only a command's as `yeti:open` did; the 0 ms task stays only to clear an opener whose command did not open the dialog. Each handler reads the live `open`, never `newState`, so a replayed `toggle` that no longer matches changes nothing. Layer 2 and layer 4 cover it. Decided 2026-10-03 in ticket 50, decision 147 (orchestrator, full AFK mode).
3. **Whether a parent's `isOpen` write emits `opened` or `closed`** (spec section 4, Open state, point 4; MEDIUM impact, MEDIUM confidence). Events rule 9 (ticket 40 point 1, decided in ticket 50 decision 5) says a write through the model binding "does not" emit, "as `model()` emits no `xChange` for a parent write", and a method call emits "as Yeti's `yeti:close` fires on every dialog close". Recommendation: read the rule as being about `isOpenChange`. A parent write emits no `isOpenChange`, but `opened` and `closed` follow every open and close of the element, as `yeti:close` is dispatched "however it was closed" (manifest). Otherwise the `close` handler would have to know what caused a close, and a consumer who closes by writing the model would never see `closed`. To overrule: suppress the completion outputs for a change started by a model write, and turn the `dialog--model-and-methods` assertions around. Decided 2026-10-03 in ticket 50, decision 148 (orchestrator, full AFK mode).
4. **Focus return for a dialog the user opened before hydration** (spec section 4, Focus return; section 3; MEDIUM impact, MEDIUM confidence). `command` is not replayed (not in `NGP/core/primitives/event-dispatch/src/event_type.ts:295-366`), so a dialog found open at creation has no recorded opener; in WebKit, where a clicked button never has focus, the platform's restoration leaves focus on `body`, the case `dialog.js` exists for (`dialog.js:6-8`). Recommendation: when exactly one `YetiDialogOpener` is registered with the dialog, through the opener-to-dialog registration that building-blocks 1.5 already allows, focus returns to it; with none or several, the platform's restoration stands. Add a ledger row (number assigned by the orchestrator): item `dialog`; feature "focus returns to the opener after a close of a dialog opened before hydration"; source WCAG 2.2 2.4.3; what Yeti does: nothing, `dialog.js` too records only from `command`; building block: the registry signal from building-blocks 1.5; verified *inferred*; tested by L4 (ticket 34's case). Alternative: accept the residue and state it, which removes the registration. Decided 2026-10-03 in ticket 50, decision 149 (orchestrator, full AFK mode).
5. **`closePredicate`: name, type, and reach** (spec section 4, Veto; MEDIUM impact, MEDIUM confidence). Part 2 row 31 and building-blocks 1.4 decide "a predicate input (Material's `closePredicate`)" over `cancel`, and ADR 0021 point 3 adds the Escape `keydown` on `window`; none fixes the type or what it gates. Recommendation: `closePredicate: (() => boolean) | undefined`, unset meaning every close is allowed; asked for Escape, any other close request through `cancel`, and the Backdrop press; never for `close()`, a model write, a `form method="dialog"` submission, or a navigation, so a keyboard way out always remains (WCAG 2.1.2). No arguments: Material's `(result, config, componentInstance)` has no counterpart here. Add a ledger row (number assigned by the orchestrator) for this Material parity feature (the user's standing ruling 36 covers parity features): item `dialog`; source Material `closePredicate` and `disableClose` (`NC/src/material/dialog/dialog-config.ts:69`, `:72`); what Yeti does: nothing; verified *read*; tested by L1 and L2. Decided 2026-10-03 in ticket 50, decision 150 (orchestrator, full AFK mode).
6. **The opener's `aria-haspopup` and `aria-controls`** (spec section 2; LOW impact, HIGH confidence). ADR 0021 point 4 leaves them to this spec "as a `ledger.md` row if added". Recommendation: render neither and add no row. Yeti's example lacks both, the APG's own modal dialog example renders neither on its openers (`APG/content/patterns/dialog-modal/examples/dialog.html:52`, `:91`, `:144`, read), and the modal dialog's role, name, and modality are announced when focus enters it. Decided 2026-10-03 in ticket 50, decision 151 (orchestrator, full AFK mode).
7. **The dialog's edge under forced colours** (spec user story 49, section 7, layer 4; MEDIUM impact, MEDIUM confidence). Yeti's `.dialog` has `border: 0` and draws its edge with `--yeti-shadow-md` (`dialog.css:9`, `:13`), and forced-colours mode removes box shadows, so the dialog's surface may merge with the page behind (inferred; ticket 17's forced-colours screenshots did not include an open dialog). Material draws a transparent 2 px border on its dialog surface that forced colours paint (`NC/src/material/dialog/dialog.scss:111-122`, read). Recommendation, after A11Y-1a to A11Y-1f and ticket 50 decision 17's "record and measure": a new row A11Y-1 with the next letter, owned by `dialog`, verified *inferred*, tested by L4; layer 4 records the open dialog under `forcedColors: 'active'` in Chromium and Firefox, and if the edge is lost the package adds one rule in `@layer ngx-yeti` under `@media (forced-colors: active)`, after Material's shape, which adds no layout change in normal mode. Decided 2026-10-03 in ticket 50, decision 152 (orchestrator, full AFK mode).
8. **Completion details** (spec section 4, Completion; LOW impact, HIGH confidence). Building-blocks 1.6 rule 1 says "filtered by `event.target`"; the `::backdrop`'s transitions also report the dialog as their target. Recommendation: also require an empty `pseudoElement`, take the longest computed `transition-duration`, and complete a running wait at once when the opposite change starts, so `closed` always precedes the next `opened`. Decided 2026-10-03 in ticket 50, decision 153 (orchestrator, full AFK mode).
9. **Correction to ADR 0043's note of 2026-10-03** (spec section 10, Event replay; MEDIUM impact, HIGH confidence). The note says `pointerdown` is not in Angular's replayed list, citing `event_type.ts:295-300`. At `5db6fc4453` `'pointerdown'` is in `BUBBLE_EVENT_TYPES` (`event_type.ts:335`), and replay collects every early event type that has a listener (`NGP/core/src/hydration/event_replay.ts:248-255`) (read, not measured). So a `pointerdown` made before hydration is replayed. For the dialog, a Backdrop press before hydration closes it once its boundary hydrates, late but once, as the spec states. Recommendation: a dated note on ADR 0043, and a note to the `dropdown` and `nav` writers that their `pointerdown` guard does see a replayed press, which changes the residue the note describes. Layer 4 measures the dialog case. Decided 2026-10-03 in ticket 50, decision 92 (orchestrator, full AFK mode).
10. **`requestClose()` is inside the target** (spec Further Notes; LOW impact, HIGH confidence). Building-blocks 1.8 lists `dialog.requestClose()` as not used "before they reach the target". The same compatibility data lists it in Chrome 134, Firefox 139, and Safari 18.4 (read), inside Baseline 2025. Recommendation: correct 1.8 with a dated note; do not adopt it in the first milestone, because the Backdrop press keeps `dialog.js`'s `close()` like for like and the veto already covers it; a later record may route the press through `requestClose()` so that `cancel` is the single veto point. Decided 2026-10-03 in ticket 50, decision 154 (orchestrator, full AFK mode).

## Answer

Resolved 2026-10-03 by Claude Opus 5.5. Spec: [specs/dialog.md](../specs/dialog.md).

Two directives in `ngx-yeti/dialog`. The item directive `YetiDialog` on `dialog[yetiDialog]` (`exportAs: 'yetiDialog'`) binds the static class `dialog`, the presence attribute `data-ngx-yeti-item-dialog`, `data-max` from a `YetiWidth` input (static form `inert`), and the host's `id` through `injectYetiId('dialog')`. It loads the `dialog` item file. It has an `isOpen` model that never binds `open`: the model is read from the element once and then follows `toggle` and `close`. It has the `void` Completion outputs `opened` and `closed`, `open()` and `close()` methods, and a `closePredicate` veto over `cancel` and Escape. Its host listeners replace `dialog.js`: `command` records the opener, `close` returns focus to it, and `pointerdown` with `click` close the dialog on a Backdrop press. It closes on navigation through `injectCloseOnNavigation`. The Free behaviour directive `YetiDialogOpener` on `button[yetiDialogOpener]`, written beside `yetiButton`, renders `commandfor` and `command="show-modal"` from a template reference and no `aria-expanded`. No `FocusTrap`: ledger row A11Y-8 is confirmed and measured in layer 4. Two new ledger rows (points 4 and 5) and a forced-colours row (point 7) are proposed.

Counts: 56 user stories, 12 usage rules, 7 story ids, 10 open points. Point 1 has HIGH impact and MEDIUM confidence, so it is in the trap quadrant and is recorded with its options above. No open point blocks the spec: it carries each recommendation as its reading.
