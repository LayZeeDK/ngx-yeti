### Open

Each point is marked "(open: see ticket)" in the spec. Impact and confidence follow the trap-quadrant rule (map, Standing rulings, 2026-10-03).

1. **A sticky region over stacked content** (spec usage rule 7, section 7, layer 4). Impact: HIGH, confidence: MEDIUM, so it is in the trap quadrant. It is the same point as [ticket 65](65-spec-sidebar.md)'s open point 1, whose options name `shell`; this record adds only what differs for the shell.
   - **Question.** Once the body row has stacked (below about twice `width` plus the gap), a sticky `nav` comes first and sits above `main` while `main` scrolls under it (`[data-sticky]` has `z-index: 2`, `Y/src/layouts/attributes.css:333-342`). A control that focus scrolls into view stops at `--yeti-scroll-padding`, which defaults to the sticky offset (`Y/src/tokens/space.css:56-69`), so Shift+Tab can leave a focused link entirely behind the stuck `nav` (WCAG 2.2 2.4.11). A sticky `aside` comes last and has no later content in the body row to cover (inferred from sticky positioning within its containing block). A sticky region taller than the viewport keeps its own lower content out of reach (1.4.10). A page-top bar that sticks above the whole shell, as in Yeti's starter, raises the same question for every control on the page.
   - **Option A (recommended): follow ticket 65's option A.** Usage rule 7 as written (stick only a region that fits the smallest viewport; where a stuck `nav` sits above stacked content, set `--yeti-scroll-padding` on `:root` to at least its height, or stick only the `aside`), the ledger row ticket 65 proposes, shared by `sidebar`, `stack`, and `shell`, and the layer-4 Shift+Tab walk asserted with the rule followed and recorded with Yeti's defaults. Approve because it is one decision for three items whose sticky CSS is the same always-loaded rule, and it follows [ticket 50](50-decide-open-points-of-the-specs.md) decisions 17 and 32.
   - **Option B: a package rule in `@layer ngx-yeti`.** Dismiss for the reason ticket 65 gives: CSS cannot tell when the body row has stacked, because the switch is flex-basis arithmetic with no container query, so a rule that unsticks regions would also remove the feature side by side.
   - **Option C: a shell-only answer that differs from the sidebar's.** Dismiss: the geometry and the rule are the same, and two answers for one rule would confuse consumers who build a shell from a stack and a sidebar (Yeti's docs, "Built from primitives").
   - **Evidence and confidence.** The stacking geometry, the z-index, and the order of `nav` before `main`: read in `shell.css` and `attributes.css` (HIGH). That focus scrolling leaves a link under the stuck region: inferred from the scroll-padding model, not measured (MEDIUM).
   - **To overrule.** Whatever ticket 50 decides for ticket 65 applies here unchanged: replace usage rule 7, the section 7 rows for 1.4.10 and 2.4.11, and the layer-4 walk with that decision's text. Decided 2026-10-03 in ticket 50, decision 48 (orchestrator, full AFK mode).

2. **Where `yetiShell` goes** (spec usage rule 1, Solution). Impact: MEDIUM, confidence: HIGH. [Ticket 11](11-decide-spec-list.md) row 20 placed the shell "on the outermost element the application renders (inferred, to be confirmed by the spec)". The spec reads this as the outermost element of the root component's template, a `div`. Options: (a) that `div`; (b) the root component's host through `hostDirectives`, which works but leaves `gap` and `width` unbindable, since nothing binds the root host's inputs; (c) the package writing the class to `body`, which breaks ADR 0003 point 1 (a static host class) and the hydration constraints' "no direct DOM manipulation". **Recommendation: (a)**: Yeti's reset zeroes `body`'s margin (`Y/src/base/reset.css:12-14`), so an inner host with `min-block-size: var(--yeti-cover-height)` matches `body.shell`. To overrule toward (b), document `hostDirectives` on the root component and remove the inputs from the example. Decided 2026-10-03 in ticket 50, decision 83 (orchestrator, full AFK mode).

3. **The `router-outlet` inside `main`** (spec usage rule 3, layer 4). Impact: MEDIUM, confidence: MEDIUM. No record says where the outlet goes. As a direct child of the body row or the shell, the outlet element is one more flex item and takes a `gap` of its own, and the routed host beside it is a plain item, not `main`; inside `main` neither happens and every route keeps one main landmark. Inferred from Yeti's child selectors and flex `gap`, not measured. **Recommendation:** keep the usage rule, and keep the layer-4 variant fixture that measures the outlet as a direct body-row child. To overrule, a measurement showing no extra gap would reduce the rule to the landmark reason alone. Decided 2026-10-03 in ticket 50, decision 84 (orchestrator, full AFK mode).

4. **The skip link in `index.html`** (spec usage rule 5). Impact: MEDIUM, confidence: HIGH. Yeti's skip-link rule matches only `body > a[href^="#"]:first-child` (`Y/src/base/typography.css:70`), and the [fragment-links](../specs/fragment-links.md) and [setup](../specs/setup.md) specs say to write the link and add `provideYetiFragmentLinks()` but not where. Inside an Angular template the link is never `body`'s first child, so it would be an ordinary visible link at the top of the shell. **Recommendation:** the usage rule as written (first child of `body` in `index.html`, pointing at an `id` on `main`), and a note in the setup spec's skip-link example. To overrule toward a skip link inside the template, the consumer needs CSS of its own to hide it until focused: Yeti's visually-hidden utility does not fit, since its manifest notes that anything focusable inside it takes Tab focus with nothing on screen (`Y/src/utilities/visually-hidden/manifest.json:16`). Decided 2026-10-03 in ticket 50, decision 85 (orchestrator, full AFK mode).

5. **The `center` and `shell` order is stated wrongly in two other specs** (spec section 13). Impact: LOW, confidence: HIGH. [Ticket 23](23-research-yeti-layers-and-import-order.md)'s research measured that in Yeti's order a `.center` directly inside a `.shell` has 0 margins (`shell.css` comes after `center.css`, `Y/src/yeti.css:30`, `:39`), and 102 px reversed. The [center](../specs/center.md) spec's user story 11 and section 13, and the [setup](../specs/setup.md) spec's "The loader's behaviour" item 5, say Yeti's order keeps a center centred inside a shell; that holds for `stack`, not for `shell`. The shell spec states Yeti's real result and a usage rule (usage rule 9: a center goes inside `main`). **Recommendation:** correct those two specs' wording to "Yeti's order gives full Yeti's result: a center in a stack is centred; a center directly in a shell is not". No package CSS: the package reproduces Yeti. This writer edits only its own files, so the correction is the orchestrator's. Decided 2026-10-03 in ticket 50, decision 86 (orchestrator, full AFK mode).

## Answer

Resolved 2026-10-03 by Claude Opus 5.5. Spec: [specs/shell.md](../specs/shell.md).

Two types-only directives in `ngx-yeti/shell`. The item directive `YetiShell` on `[yetiShell]` (`exportAs: 'yetiShell'`) binds the static class `shell` and the presence attribute `data-ngx-yeti-item-shell` ([ADR 0045](../adr/0045-each-item-marks-its-host-with-its-own-attribute.md)), binds `data-gap` and `data-width` from `gap: YetiGap` and `width: YetiWidth` (`inert`), acquires the item file, and provides `yetiShellToken`. The part directive `YetiShellRegion` on `[yetiShellRegion]` binds `data-sticky` from a boolean `sticky` input on the body row's `nav` or `aside` (ticket 26 rows 84 to 86). Neither class name is among the 46 that `yeti.d.ts` exports. The host is the outermost element of the root component's template; the skip link stays first in `body` in `index.html`; the `router-outlet` goes inside `main`. Shell panels close on navigation through the `nav`, `dropdown`, and `dialog` directives ([navigation-close](../specs/navigation-close.md), ledger A11Y-15); the skip link relies on [fragment-links](../specs/fragment-links.md) (A11Y-16). The spec links [sidebar](../specs/sidebar.md) and [stack](../specs/stack.md) for the composed form and tests the two forms against each other.

Counts: 54 user stories, 12 usage rules, 9 story ids, 5 open points (one HIGH impact with MEDIUM confidence, in the trap quadrant and recorded with its options above; it follows ticket 65's open point 1). No open point blocks the spec. The spec writes no ledger or upstream-bug row; point 5 asks the orchestrator to correct wording in the center and setup specs.
