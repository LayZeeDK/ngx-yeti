### Open

Each point is marked "(open: see ticket)" in the spec. Impact and confidence follow the trap-quadrant rule (map, Standing rulings, 2026-10-03). Point 2 is in the trap quadrant and carries its options record.

1. **`pointerdown` is replayed; ADR 0043's note and building-blocks 1.11 decision 5 say otherwise** (spec section 10, layer 4). ADR 0043's 2026-10-03 note says `pointerdown` is not in Angular's replayed list, citing `event_type.ts:295-300`, and concludes that a press on non-focusable panel content before hydration closes the panel at replay. The same file lists `pointerdown`, `pointerover`, and `pointerout` in `BUBBLE_EVENT_TYPES` at `:335-340`, and the hydration code collects every listener whose type passes `isEarlyEventType` (`NGP/core/src/hydration/event_replay.ts:248`), so a `pointerdown` host listener gets a `jsaction` and replays. Only `pointerenter`, `pointerleave`, `mouseenter`, and `mouseleave` are skipped (`MOUSE_SPECIAL_EVENT_TYPES`, `:287-292`). The dialog spec (ticket 81, point 9) found the same. Building-blocks 1.11 decision 5 calls `pointerover` and `pointerout` "non-replayed", which is wrong for the same reason; Part 2 row 32 and ADR 0011 clause 6 already use `pointerenter` and `pointerleave`, which are not replayed, and the spec uses those. Recommendation: add a dated correction to ADR 0043's note (the guard probably sees the replayed press, queued before the `focusout`, so the panel stays open; inferred, not measured), and correct 1.11 decision 5 to `pointerenter` and `pointerleave`. The guard needs no change, because it does not depend on `pointerdown` going unreplayed. The spec's layer-4 fixture case (a press on the panel's padding before hydration, then hydration) measures which reading holds in three engines. Impact: MEDIUM (a stated residue changes; no API changes). Confidence: HIGH that the source lists the events (read); MEDIUM that the replay order keeps the panel open (inferred). Decided 2026-10-03 in ticket 50, decision 92 (orchestrator, full AFK mode).
2. **The `isOpen` model on a popover** (spec section 4 items 5 and 7, section 5, layer 1 `dropdown--outputs`, layer 2). Impact: HIGH (public API of a model that consumers bind two-way, and the open-state ruling's guarantee that a toggle made before hydration survives). Confidence: MEDIUM.
   - **Question.** Part 2 row 32 gives the root an "`isOpen` model from the panel's `toggle`", and the open-state ruling says a directive "reads the element's open state once, when it is created, then follows the native `toggle` and `close` events". Four things are not settled. (a) When the state is read: a popover has no `open` attribute, only the `:popover-open` pseudo-class, and the server's DOM never has an open popover. (b) What a parent's write to `isOpen` does. (c) Which outputs a parent's write emits: events rule 9 says a write through the model's input binding emits nothing, but the panel really opens and closes. (d) Whether the root also has `open()`, `close()`, and `toggle()` methods, which building-blocks 1.3's vocabulary allows and row 32 does not list. Also (e): what happens when a close interrupts the wait for `opened`.
   - **Option A (recommended).** (a) Read `:popover-open` once in the first client render callback (`afterNextRender`, `earlyRead`), not at construction. Event replay runs after that first render, so the read sees what the user did before hydration, and replayed `toggle` events then match it and emit nothing. If the element's state differs from the model's value, the model is set from the element, which emits `isOpenChange`, so a two-way binding learns the real state. (b) After that, a parent's write is applied in an `afterRenderEffect` write phase with `showPopover()` or `hidePopover()`, guarded by `:popover-open`, because both throw on a no-op (`hover.js:56`, `:89`). (c) `isOpenChange` does not emit for a parent's write, because `model()` does not emit for one. `opened` and `closed` do emit, because they report a change that was committed and has finished its transition, whatever caused it. Only the state found by the first read emits nothing. (d) No methods: the model is the one programmatic path, and a method can be added later without a breaking change. (e) A new change cancels a pending completion wait, and the cancelled change emits nothing. Approve: the server never runs a DOM query on a pseudo-class (whether the server DOM supports `:popover-open` was not checked), a toggle made before hydration survives as the ruling intends, and the outputs keep their "completion" meaning.
   - **Option B: read at construction, as `injectYetiId` reads the id.** Dismiss: `matches(':popover-open')` would run on the server DOM too, which needs either a platform check (forbidden, building-blocks 1.11 decision 3) or the unchecked assumption that the server DOM accepts the pseudo-class. It also gains nothing, because on the client the element is already claimed at both points.
   - **Option C: no model; a read-only `isOpen` signal plus `open()` and `close()` methods**, as Material's `menuOpen` getter and `openMenu()` work. Dismiss: it contradicts row 32's "`isOpen` model" and building-blocks 1.4's `model()` for open state, and it differs from the dialog's `isOpen` model.
   - **Option D: apply a parent's initial value at the first render** (controlled from the start). Dismiss: a parent's `false` would close a panel the user opened before hydration, which is exactly what the open-state ruling prevents for `details` and `dialog`.
   - **Evidence and confidence.** The open-state ruling and ticket 34 (measured: a bound `open` undoes a toggle made before hydration). That replay runs after the first render callback is inferred from Angular's hydration order and not measured. `showPopover()` and `hidePopover()` throwing on a no-op: read in `hover.js`'s comments. The spec's layer-2 and layer-4 cases measure (a) and the replay order.
   - **To overrule.** For C: replace the model with a `computed` and three methods in sections 4 and 5 and in the stories, and amend Part 2 row 32. For D: remove the first-render adoption, and turn the pre-hydration e2e case into one that records the panel closing. Either way, the [dialog](81-spec-dialog.md) spec should answer (c) and (e) the same way, because the events spec's rules 7 and 9 are shared. Decided 2026-10-03 in ticket 50, decision 91 (orchestrator, full AFK mode).
3. **Focus after a navigation close** (spec section 4 item 6, layer 2, layer 4). ADR 0041 point 4 has the dropdown spec measure whether `hidePopover()` restores focus and "add a `focus()` on the opener if it does not". The HTML standard's hiding steps restore focus to the element focused when the popover opened, and only when focus is inside the popover (inferred; not read for this spec). After a click open in WebKit that element is `body`, because a clicked button never gets focus. Recommendation: the close path calls `focus()` on the Opener only when focus was inside the panel before the call and is not on the Opener after it. Layer 4 records each engine's result. This covers the keyboard user, whose Enter on a link left focus in the panel, and does not pull focus to the Opener when the user was elsewhere. For a dropdown inside an open nav sheet, the Opener is hidden with the sheet, so focus is the nav's to place; layer 4 records it with the [nav](84-spec-nav.md) spec. Impact: MEDIUM. Confidence: MEDIUM. Decided 2026-10-03 in ticket 50, decision 155 (orchestrator, full AFK mode).
4. **No injection of `yetiNavToken`** (spec section 3). Building-blocks 1.9 ("a dropdown inside or outside a nav") and architecture-guide P6 and P22 name the dropdown's optional injection of the nav's token as an example. This spec finds no behaviour that needs it. Each item closes its own panel on focus-out and on navigation. The platform nests the dropdown's popover inside the nav's list, so hiding the list hides the panel and Escape closes the inner one first. Yeti's `nav.css` styles the nested case by selector. Recommendation: no injection in the first milestone, which keeps `ngx-yeti/dropdown` free of `ngx-yeti/nav`; keep the guide's sentence as an illustration of the optional form. Revisit if the nav spec (ticket 84, written in parallel) asks the dropdown for something. Impact: LOW. Confidence: MEDIUM. Decided 2026-10-03 in ticket 50, decision 156 (orchestrator, full AFK mode).
5. **Reflow at 320 CSS pixels** (spec usage rule 7, section 7 criterion 1.4.10, `dropdown--narrow`). Yeti places the open panel at `position-area: block-end span-inline-end` from the Opener's start edge, with `min-inline-size: 12rem`, and declares no `position-try` fallback (`dropdown.css:46-56`). A panel whose Opener sits near the inline end, with `side` left at `start`, can therefore run past the viewport. A `position: fixed` panel cannot be scrolled into view (inferred from the CSS, not measured). Recommendation, after ticket 50 decisions 17 and 47: usage rule 7 (`side="end"` for an Opener in the inline-end half of a row); a new ledger row owned by `dropdown` (WCAG 2.2 1.4.10; Yeti offers `data-side="end"` and no fallback; the package adds the usage rule; verified *inferred*; tested by L1 and L4); no package CSS until `dropdown--narrow` has measured the default case in three engines. Dismissed: a package `position-try-fallbacks` rule now. It is unmeasured, it changes Yeti's documented placement for every consumer, and it was not checked against the browser target. Impact: MEDIUM. Confidence: MEDIUM. Decided 2026-10-03 in ticket 50, decision 157 (orchestrator, full AFK mode).
6. **Forced colours and the panel's edge** (spec section 7, layer 4). The open panel has `border: 0` and is drawn by a background and a shadow, so under `forced-colors: active` its edge against the page may disappear, while its text and focus ring remain. Recommendation, after ticket 50 decisions 26, 30, and 78: no ledger row and no package CSS now. Layer 4 records the computed border and a screenshot in three engines, and asserts that the focus ring remains. If the panel cannot be told from the page behind it, add a ledger row owned by `dropdown` and one `@layer ngx-yeti` rule giving `.dropdown > [popover]:popover-open` a system-colour border, after A11Y-1f. Impact: LOW. Confidence: MEDIUM. Decided 2026-10-03 in ticket 50, decision 158 (orchestrator, full AFK mode).

## Answer

Resolved 2026-10-03 by Claude Opus 5.5. Spec: [specs/dropdown.md](../specs/dropdown.md).

There are three directives in `ngx-yeti/dropdown`. The root is `YetiDropdown` on `[yetiDropdown]`, a `div` or a nav's `li`. It binds the class `dropdown`, `data-side` (`YetiSide`), `data-trigger` (`YetiTrigger`), and the presence attribute `data-ngx-yeti-item-dropdown`. It provides `yetiDropdownToken`, holds the `isOpen` model, and emits the completion outputs `opened` and `closed`. It carries the `focusout` listener with the `pointerdown` guard (ledger A11Y-3a; ADR 0043), the hover listeners that replace `hover.js` for `trigger="hover"`, and `injectCloseOnNavigation`. The Opener is `YetiDropdownToggle` on `button[yetiDropdownToggle]`, which renders `popovertarget`. The panel is `YetiDropdownPanel`, which renders `popover` and its generated or consumer id, follows `toggle`, and waits for the opening transition. There are no menu roles and no Aria or CDK menu (ADR 0019; the user's "Custom disclosure nav (Recommended)"). Every `hover.js` behaviour is mapped line by line. The spec owns A11Y-3a and confirms it as written.

Counts: 62 user stories, 12 usage rules, 9 story ids, and 6 open points. Point 2 has HIGH impact and MEDIUM confidence, so it is in the trap quadrant and its options are recorded above. No open point blocks the spec. The spec carries each recommendation, and overruling one changes a listener's timing, a usage rule, or a test, not the item's shape. Point 1 corrects ADR 0043's note and building-blocks 1.11 decision 5 (the coordinator relayed the same finding from ticket 81). Point 5 may add a ledger row. The spec itself writes no ledger or upstream-bug row.
