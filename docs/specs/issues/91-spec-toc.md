## Question

What is the Angular API of Yeti's `toc` component, and what does its spec say? Its decisions are already made in the records: its row in `building-blocks.md` Part 2 (and the "Aria decisions" section where it applies), its rows in [Decide: how the package maps each of Yeti's `data-*` attributes](26-decide-yeti-data-attributes-mapping.md), its item file under [ADR 0060](../adr/0060-item-styles-are-counted-links-to-the-consumers-yeti-build.md), its ledger rows, and the shared specs it links to.

## How to work it

Write `specs/toc.md` with the `/to-spec` template and the map's Spec shape note, from the records only. The spec decides nothing a record has not decided. Anything it needs and no record settles goes under the ticket's `### Open` for the orchestrator. Append an `## Answer` that links the spec.

### Open

Each point is written in the spec as its best reading and marked "(open: see ticket)". Impact and confidence are rated as the map's trap-quadrant ruling asks; points 1 and 2 are HIGH impact with MEDIUM confidence and carry decision records.

1. **The model's name and value type** (spec sections 2 and 4; HIGH impact, MEDIUM confidence; trap quadrant).
   - **Question.** Part 2 row 41 and building-blocks 1.4 give the toc a model for the current link beside the `current` output. [Ticket 40](40-spec-events.md) point 3, decided in [ticket 50](50-decide-open-points-of-the-specs.md) (decision 5), renames the model away from `current` "for example `currentLink`", but no record fixes the name or what the model holds.
   - **Option A (recommended): `currentLink: string | undefined`, the current link's target id** (its fragment, decoded, which equals the heading's `id`). Approved because a string is what a consumer can write statically or bind from route data on the server, so the server HTML can ship the mark, which Yeti's docs allow ("a page that knows its own current section can simply ship the attribute in its HTML") and which a static `aria-current` can no longer do under ADR 0003 point 4; it survives SSR and `TransferState`-free hydration because both ends compute it from the same input; it compares with each link's fragment with no element reference; and the name follows the ticket 40 example and the glossary's **Current link**. The elements stay available on the `current` output's `YetiCurrentDetail`.
   - **Option B: `currentLink: HTMLAnchorElement | null`.** Dismissed: an element cannot be set from a template literal, from route data, or on the server before the link exists, so the server HTML could never carry the mark, and a parent would need a reference to the link to write it.
   - **Option C: no model; a read-only `currentLink` signal plus the output.** Dismissed: building-blocks 1.4 and Part 2 row 41 name a model for this state, and without one the server-rendered mark is lost.
   - **Option D: the same string under another name** (`currentId`, `currentHeading`, `currentFragment`). Not chosen: each is accurate, but `currentLink` is the record's own example and matches the glossary term; any of them is a rename in the spec's sections 2, 4, 8, and the stories.
   - **Evidence and confidence.** Read: building-blocks 1.4, Part 2 row 41, ticket 40 point 3, ticket 50 decision 5, `toc.js:12-19`, the manifest's `a11y.notes`, ADR 0003 point 4. Nothing measured. MEDIUM, because the value type is new public API that no record states.
   - **To overrule.** For B: change the model's type, remove the static and server forms from usage rule 6, section 8, and the layer-3 smoke, and state that the server HTML carries no mark. For D: rename the model and its `currentLinkChange` in sections 2, 4, 8, the stories `toc--model` and `toc--dynamic`, and the layer-2 cases. Decided 2026-10-03 in ticket 50, decision 207 (orchestrator, full AFK mode).

2. **Links rendered from data** (spec sections 2 and 4, usage rule 5; HIGH impact, MEDIUM confidence; trap quadrant). The same question as [ticket 79](79-spec-carousel.md) point 6 for the carousel's dots, and the carousel's record says "the toc spec (ticket 91) faces the same question for its links and should match whichever wins".
   - **Question.** Ticket 50 decision 4 has a package-owned link read the consumer's static `href` once through `HostAttributeToken('href')`. Inside `@for`, a static `href` cannot carry each heading's id, and `href="#{{ h.id }}"` is a binding that `HostAttributeToken` does not see and that competes with the directive's `[attr.href]`. Tocs are often generated from a page's headings. Where does such a link's fragment come from?
   - **Option A (recommended): a selector-named input `yetiTocLink: string | undefined`, the target id without `#`, passed to `injectSameDocumentHref` as a signal; when set, the consumer writes no `href`; `HostAttributeToken('href')` is injected optionally.** Approved because the fragment-links spec accepts "a string or a signal of one" and leaves the source to the owning spec (its section 4 and usage rule 2), the static form of decision 4 still works unchanged, the selector-named form follows the user's choice "Selector name (Recommended)" (map, Standing rulings), and it matches the carousel's recommendation, so the two package-owned link parts take one shape.
   - **Option B: static `href` only.** Dismissed: a generated contents list is the common case, and `@for` is the documented way to render it.
   - **Option C: derive the fragment from the link's position against the headings.** Dismissed: ADR 0025 makes the link's own fragment the contract, and the toc has no list of headings to count against.
   - **Evidence and confidence.** Read: decision 4, fragment-links section 4, ticket 79 point 6, `HostAttributeToken`'s static-only reading (inferred from Angular's API, not run). MEDIUM, because the input is new API on a part.
   - **To overrule.** Follow whatever ticket 79 point 6 decides. For B: remove the input from sections 2 and 4, usage rule 5, the `toc--dynamic` story's `@for`, the second usage example, and the layer-2 case, and add a usage rule that links are written statically. Decided 2026-10-03 in ticket 50, decision 208 (orchestrator, full AFK mode).

3. **Whether the observer's first report emits** (spec section 4; MEDIUM impact, MEDIUM confidence). [Events](../specs/events.md) rule 9 says state found at creation emits nothing; it cites `tabs.js`, which skips its load pass. `toc.js` does not skip: at load it dispatches `yeti:current` whenever its first callback moves the mark, and returns when the link is already current (`toc.js:33-36`). Recommendation: the model's initial value (the server's mark) emits nothing, and the first report emits `current` and `currentLinkChange` only when it moves the mark, as `toc.js` does, because that report is the directive's own change after creation, and the consumer's mirrored UI would otherwise keep the server's section while the toc marks another. Alternative: never emit for the first report and set `currentLink` silently, which events rule 9 could be read to ask; a consumer bound with `[(currentLink)]` would then show a different section from the toc until the next move. Decided 2026-10-03 in ticket 50, decision 209 (orchestrator, full AFK mode).

4. **Which render callback resolves headings again** (spec sections 2 and 4; MEDIUM impact, HIGH confidence). ADR 0025 point 3 says "after each application render", Part 2 row 41 and building-blocks 1.15 say the observer is created in `afterNextRender`, and architecture-guide P12 prefers "`afterRenderEffect` for the toc's `IntersectionObserver`". `afterRenderEffect` runs again only when a signal it reads changes, and a `@defer` or `@if` that renders a heading elsewhere changes no signal the toc reads. Recommendation: create the observer in `afterNextRender` (row 41) and resolve missing or disconnected headings in an `afterEveryRender` callback (`NGP/core/src/render3/after_render/hooks.ts:136`), which is what ADR 0025 point 3 describes and costs what it states; correct P12's example to name both. Alternative: `afterRenderEffect` over the registered-link signal, which picks up new links but misses a heading rendered later for an existing link. Decided 2026-10-03 in ticket 50, decision 210 (orchestrator, full AFK mode).

5. **A fragment that fails to decode** (spec sections 2 and 4; LOW impact, MEDIUM confidence). `decodeURIComponent` throws on a malformed escape (`#%E0%A4%A`), and `toc.js:17` does not catch it, so one bad link stops Yeti's whole toc. Recommendation: treat such a link as unresolved (a working link the observer ignores), so one consumer typo cannot throw from a render callback. Alternative: let it throw like-for-like, which surfaces the typo in development but stops the mark for every link. Decided 2026-10-03 in ticket 50, decision 211 (orchestrator, full AFK mode).

6. **Two links to one heading** (spec usage rule 4; LOW impact, MEDIUM confidence). `toc.js:13-19` keeps one link per heading in a `Map`, so the later link in document order wins and the earlier is never marked. Recommendation: keep that, like-for-like, and state the usage rule "at most one toc link per heading". Alternative: mark every link that names the current heading, which changes Yeti's behaviour and could mark two links. Decided 2026-10-03 in ticket 50, decision 212 (orchestrator, full AFK mode).

7. **Forced colours and the current link** (spec section 7; LOW impact, MEDIUM confidence). The current link's hue difference is replaced under forced colours; its weight survives, and whether the start-edge bar stays distinct is not known (inferred). Recommendation, after [ticket 50](50-decide-open-points-of-the-specs.md) decision 88 (the breadcrumbs' current step): no ledger row and no package CSS now; layer 4 asserts that the weight difference survives `forcedColors: 'active'` in three engines and records the bar; if the assertion fails, a ledger row owned by `toc` and one `@layer ngx-yeti` rule follow, after A11Y-1f. Decided 2026-10-03 in ticket 50, decision 213 (orchestrator, full AFK mode).

8. **The wording of ticket 50 decision 4** (LOW impact, HIGH confidence). Decision 4 and ADR 0023's 2026-10-03 note say the directive "never binds `href`", while the fragment-links spec (section 4), the carousel spec, and this spec read the static `href` once and bind `[attr.href]` from `injectSameDocumentHref`. [Ticket 79](79-spec-carousel.md) point 15 raises the same wording. Recommendation: reword to "never binds the consumer's `href` as state; it binds the same-document form", once for both specs. Decided 2026-10-03 in ticket 50, decision 214 (orchestrator, full AFK mode).

None blocks the spec.

## Answer

Resolved 2026-10-03 by Claude Opus 5.5. Spec: [specs/toc.md](../specs/toc.md).

The spec has two directives in `ngx-yeti/toc`: `YetiToc` on `nav[yetiToc]` (`variant`, `size`, `numbered`; the `currentLink` model; the `current` output with `YetiCurrentDetail`; `yetiTocToken`; one `IntersectionObserver` with default options, created in `afterNextRender`, re-resolving headings after each render, ADR 0025) and `YetiTocLink` on `a[yetiTocLink]` (a same-document `href` through `injectSameDocumentHref`; `aria-current` bound from the root's model, P11). It maps every behaviour of `toc.js` (kept or changed; none removed), cites `toc.css`'s `.cluster` rule as the toc's own and its smooth-scrolling rule as Yeti's CSS under the reduced-motion token, owns no ledger row (Part 2 row 41, like-for-like), runs A11Y-16's toc case, and adds no upstream-bugs row. 53 user stories and 8 open points (above); points 1 and 2 are trap-quadrant points with decision records.
