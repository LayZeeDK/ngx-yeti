## Question

What is the Angular API of Yeti's `tabs` component, and what does its spec say? Its decisions are already made in the records: its row in `building-blocks.md` Part 2 (and the "Aria decisions" section where it applies), its rows in [Decide: how the package maps each of Yeti's `data-*` attributes](26-decide-yeti-data-attributes-mapping.md), its item file under [ADR 0060](../adr/0060-item-styles-are-counted-links-to-the-consumers-yeti-build.md), its ledger rows, and the shared specs it links to.

### Open

Each point is marked "(open: see ticket)" in the spec, which carries the recommended reading. Impact and confidence follow the trap-quadrant rule (map, Standing rulings, 2026-10-03). Points 1 and 2 are in the trap quadrant and carry their options records.

1. **An `id` input on the Aria-hosted parts** (spec sections 2, 4, usage rules 4 and 6, Out of Scope). Impact: HIGH (public API, and whether a deep link can name a panel). Confidence: MEDIUM (two records disagree).
   - **Question.** building-blocks "Aria decisions (2026-10-03)" row 40 says "an `id` input so that ids match across hydration", from ticket 30's prototype, which exposed Aria's `id` on `yetiTab` and `yetiTabPanel` and used Yeti's ids. Later the same day, [ADR 0044](../adr/0044-generated-ids-count-per-application-and-are-adopted-at-hydration.md) made Aria's generated ids equal on both ends through `provideYetiAriaIds()`, and [ticket 50](50-decide-open-points-of-the-specs.md) decision 5 adopted [ticket 39](39-spec-generated-ids.md) point 6: "a usage rule, stated in the tabs and buttons specs, that these parts take no consumer `id`. A deep link targets an element inside the panel." Which one does the tabs spec follow?
   - **Option A (recommended, the spec's text): no `id` input.** Ids come from `provideYetiAriaIds()` only; usage rule 4 forbids a consumer `id` on a tab or a panel; a deep link names an element inside the panel. Approve: it is the later, explicit decision for this spec; the reason row 40 gives ("so that ids match across hydration") is met by ADR 0044 without consumer ids (measured, ticket 35); it matches the [buttons](../specs/buttons.md) spec's usage rule 5 and the [generated-ids](../specs/generated-ids.md) spec. Cost: Yeti's documented markup links to a panel's own id (`docs.md:14-18`); that form is gone, and a consumer's CSS or test cannot name a panel by a chosen id.
   - **Option B: expose Aria's `id` input on `yetiTab` and `yetiTabPanel`.** A consumer's static or bound `id` sets Aria's input on both ends, so it is equal at hydration (ticket 30, measured), and an unset `id` still falls back to `provideYetiAriaIds()`, whose missing step 1 no longer matters because Aria's input carries the consumer's value. ADR 0044 rejected passing the package's id into Aria's input, not exposing the consumer's. Approve if deep links to a panel and chosen ids matter more than one rule across the Aria-hosted parts. Dismissed for now because it reverses ticket 50 decision 5 and the generated-ids spec's text for these two parts.
   - **Option C: expose `id` on `yetiTabPanel` only.** A deep link to a panel is Yeti's documented case; a tab's id serves nothing a consumer writes. Dismissed for now as a third shape no record names.
   - **Evidence and confidence.** Row 40's wording: read. Ticket 30's consumer-id measurement: measured, three engines. ADR 0044's equal ids without consumer ids: measured (ticket 35). That option B leaves ADR 0044's mechanism intact: inferred from `tab.ts:62` (the input's default is the generator's id, so a set input replaces it), not run.
   - **To overrule.** For B: add `'id'` to the `inputs` of `yetiTab`'s and `yetiTabPanel`'s host directives in spec sections 3 and 4, remove the `id` clause of usage rule 4, change usage rule 6 to allow a panel's own id, add a layer-3 case (a consumer `id` renders on both ends and every reference uses it), and amend the generated-ids spec's `provideYetiAriaIds()` paragraph and ticket 50 decision 5 for tabs. For A as written: amend "Aria decisions" row 40 to read "ids that match across hydration, through `provideYetiAriaIds()`". Decided 2026-10-03 in ticket 50, decision 198 (orchestrator, full AFK mode).

2. **How the first-tab default reaches the server HTML** (spec section 4 "The default selection", sections 8 and 10, layers 2 and 3). Impact: HIGH (every set without a bound selection: its server HTML and whether `selectedChange` emits once). Confidence: MEDIUM.
   - **Question.** A11Y-17 and building-blocks 1.15 say "a tabs root selects its first or bound tab when created, in any rendering mode", and 1.9 allows a content query for "the tabs' first-tab default". Aria itself selects nothing when `selectedTab` is unset: its `setDefaultState` sets the active tab, not the selected one (`NC/src/aria/private/tabs/tabs.ts:227-246`, read), and only in an `afterRenderEffect` that never runs on the server. Ticket 30 measured only a bound selection. How does the package write the default, and what does it emit?
   - **Option A (recommended, the spec's text): `YetiTabList` writes the first non-disabled tab's value into Aria's `selectedTab` model in `ngAfterContentInit`, from `contentChildren(YetiTab)`, when `selected` names no tab.** A view's content hooks run before its host bindings in the same pass, so `aria-selected`, the hand-over `tabindex`, and the panels' `tabindex` already reflect it on the server and in the client's first pass. The write emits `selectedChange` once (so `[(selected)]` with an unset signal takes the first value) and no `select`. Approve: one write, public API only (a model is writable), the same value on both ends, and it is the shape 1.9 names. Cost: one `selectedChange` at creation, which differs from `select`'s "nothing at creation"; a parent bound with a plain field could see a development-mode `NG0100` when the child writes back during the same check (inferred; signals re-run the check instead).
   - **Option B: override `aria-selected` until Aria is live and write the model in `afterNextRender`.** The server and the first client pass show the first tab through the package's own binding, as the `tabindex` hand-over does. Dismissed: a third overriding binding, a model write after the first render that emits `selectedChange` on the client only, and until that write Aria's `visible()` is false on every panel, so the panels' `hidden` condition must special-case it.
   - **Option C: a usage rule that `selected` is always bound.** Dismissed: Yeti's markup selects the first tab by default (`tabs.js:40`), and A11Y-17 promises "first or bound".
   - **Evidence and confidence.** Aria selecting nothing when unset: read in source, not run. The refresh order (content hooks, then host bindings): inferred, not read in this ticket. The emission: read (`model_signal.ts:80-84` emits on a changed `set`).
   - **To overrule.** For B: add `[attr.aria-selected]` to `YetiTab`'s host with the hand-over's condition, move the write to `afterNextRender`, and change the layer-2 and layer-3 cases (no `selectedChange` on the server; the first client render emits it). For C: replace the default with usage rule "bind `selected`", remove the content query, and change A11Y-17's text to "the bound tab". In every case the layer-3 unbound case decides whether the server HTML shows a selected tab; if it fails under A, B is the fallback. Decided 2026-10-03 in ticket 50, decision 199 (orchestrator, full AFK mode).

3. **`data-orientation` only when vertical** (spec section 2). The root mirrors the list's `orientation`, but Aria's input defaults to `horizontal`, so the root cannot tell "unset" from "horizontal". Recommendation: bind `data-orientation="vertical"` while the list is vertical and `null` otherwise, so an unset or horizontal list renders no attribute and Yeti's horizontal default applies, as ADR 0070 rule 1 intends; Aria's keys and `aria-orientation` use the same effective value. The cost is that an explicit `orientation="horizontal"` renders no `data-orientation`, which looks the same. Impact: LOW. Confidence: MEDIUM. Decided 2026-10-03 in ticket 50, decision 200 (orchestrator, full AFK mode).

4. **`select` only on a change** (spec section 2's Module replaced, section 4, layer 2). `tabs.js` dispatches `yeti:select` on every click, the selected tab included, and on Home on the first tab (`tabs.js:28-36`, `:109`). Aria sets its model only on a change and `model()` emits only on a changed value. Recommendation: `select` fires only when the selection changes, as [events](../specs/events.md) rule 9 reads ("A change the directive makes in a handler emits"); record it as a changed behaviour. Impact: LOW. Confidence: MEDIUM. Decided 2026-10-03 in ticket 50, decision 201 (orchestrator, full AFK mode).

5. **A static `disabled` on `button[yetiTab]`** (spec sections 2, 4, 11, usage rule 9, `tabs--disabled`, layer 3). Aria's `Tab` takes `disabled` as an input and binds `aria-disabled`, but not the HTML attribute (`tab.ts:47`, `:70`), so `<button yetiTab disabled>` also renders the native `disabled`, making the tab unfocusable and unclickable, against `softDisabled`'s default. Recommendation: kind `removed` under building-blocks 1.4: `'[attr.disabled]': 'null'` on `YetiTab` with a source comment, so the static form works as Aria's soft-disabled state, following ticket 50 decision 9's pattern (written back at hydration and removed in the same pass), with layer 3 asserting the absence and layer 4 asserting no painted frame with it. Alternative: a usage rule "bind `[disabled]`, never the static form"; dismissed because it fails silently. Impact: MEDIUM. Confidence: MEDIUM (read in source, not run). Decided 2026-10-03 in ticket 50, decision 202 (orchestrator, full AFK mode).

6. **Where the replay guard sits** (spec section 3). Building-blocks 1.9 puts it on "Aria-hosting containers"; Part 2 row 40 names it without an element. Recommendation: on `yetiTabList`, the element whose `keydown` listener Aria declares (`tab-list.ts:55`), stopping the list's keys (the arrows for its orientation and direction, Home, End, Space, Enter) without modifiers. A nested set sits in a panel, outside the outer list, so the outer list never sees an inner key. Impact: LOW. Confidence: HIGH. Decided 2026-10-03 in ticket 50, decision 203 (orchestrator, full AFK mode).

7. **Automatic activation by default** (spec sections 4, 5, 7). Building-blocks 1.10 says "the tabs are Tabs with manual activation"; Part 2 row 40 and ledger A11Y-18 say the package adds manual activation as an option (`selectionMode="explicit"`), and `tabs.js` selects on every arrow key. Recommendation: Aria's default, `follow` (automatic), which is Yeti's behaviour and the APG's recommendation (`APG/tabs/tabs-pattern.html:104`), with `explicit` exposed; amend 1.10 to "Tabs, automatic activation by default, manual through `selectionMode`". Impact: MEDIUM. Confidence: HIGH. Decided 2026-10-03 in ticket 50, decision 204 (orchestrator, full AFK mode).

8. **The roving Tab stop after a reveal or a parent's write** (spec sections 7 and 10, Known issues, layer 4). Once the reader has interacted with the list (a click, a key, or focus), Aria's `setDefaultStateEffect` stops (`NC/src/aria/private/tabs/tabs.ts:248-251`), and nothing public moves its private active item without focusing the tab (ticket 30 found the same for the carousel's picker). A reveal or a parent's write then selects a tab while Tab into the list still lands on the previously active one (read, not run). Recommendation: accept as a stated residue, record where Tab lands in layer 4, and revisit if Aria adds a public way to set the active tab; no ledger row unless the layer-4 record shows Tab landing outside the list. Impact: LOW. Confidence: MEDIUM. Decided 2026-10-03 in ticket 50, decision 205 (orchestrator, full AFK mode).

## Answer

Resolved 2026-10-03 by Claude Opus 5.5. Spec: [specs/tabs.md](../specs/tabs.md).

Four directives in `ngx-yeti/tabs` host Aria's Tabs by composition: `YetiTabs` (class, `variant`, `gap`, `emphasis`, the mirrored `data-orientation`, `select`, the fragment reveal, `yetiTabsToken`, the presence attribute, the item file), `YetiTabList` (`orientation`, `wrap`, `selectionMode`, `softDisabled`, the `selected` model, the first-tab default, the replay guard), `YetiTab` (`value`, `disabled`, the `tabindex` hand-over, `provideYetiAriaIds()`), and `YetiTabPanel` (`value`, `hidden` and `inert` once Aria is live, `provideYetiAriaIds()`). Every panel shows with JavaScript off, with one Tab stop on the selected tab. The spec owns ledger rows A11Y-1c, A11Y-5, A11Y-17, and A11Y-18, and replaces every behaviour of `tabs.js` in a mapped table.

Counts: 55 user stories, 12 usage rules, 9 story ids, 9 open points. Points 1 and 2 are in the trap quadrant (HIGH impact, MEDIUM confidence) and carry their options records above. No open point blocks the spec.

Checked: Yeti's `tabs` manifest, CSS, docs, example, `tabs.js`, and its browser tests at the Pin; Aria's `Tabs`, `TabList`, `Tab`, `TabPanel`, their patterns, `SortedCollection`, and the event managers at `708d4c6e2`; Angular's `model()` emission; Material's tab group; the APG tabs pattern. Inferred, not run: the first-tab default in the server HTML (point 2), the `disabled` attribute's effect (point 5), the roving stop after a reveal (point 8), and the `tabindex` flip at hydration for tabs (measured only on the toolbar).
