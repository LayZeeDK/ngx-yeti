## Question

What is the Angular API of Yeti's `spinner` component, and what does its spec say? Its decisions are already made in the records: its row in `building-blocks.md` Part 2 (and the "Aria decisions" section where it applies), its rows in [Decide: how the package maps each of Yeti's `data-*` attributes](26-decide-yeti-data-attributes-mapping.md), its item file under [ADR 0060](../adr/0060-item-styles-are-counted-links-to-the-consumers-yeti-build.md), its ledger rows, and the shared specs it links to.

## How to work it

### Open

Five points no record settles. None is HIGH impact, so none needs the trap-quadrant record (map, Standing rulings, 2026-10-03); points 1 and 2 still list their options.

1. **The form of the wait's announcement** (MEDIUM impact, MEDIUM confidence). Spec usage rules 2 and 4, section 7 (Announcement and the 4.1.3 row). Part 2 row 38 makes `role="status"` and the name the consumer's, and Yeti's docs write them on the ring itself "so the wait is announced once". Ticket 17 measured only the tree (`status "Loading"` in Chromium), not a screen reader. A `status` region inserted with a name and no text content is not reliably announced by every screen reader (inferred; not measured in any record).
   - **Option A (recommended): Yeti's form leads, and a decorative form is allowed beside it.** Usage rule 2 is Yeti's form (role and name on the ring, inserted with the wait). Usage rule 4 allows `aria-hidden="true"` on the ring when its visible text already sits in a status region of the consumer's, so nothing is announced twice. The end of the wait is the consumer's status message in a region present before it changes (usage rule 6). The screen-reader announcement is a manual release test (ADR 0015 point 7). Approve: it follows Yeti's docs and Part 2 row 38, needs no package code, and gives the consumer a robust form without deciding against Yeti.
   - **Option B: only the decorative form.** The ring is always `aria-hidden`, and every wait is announced by a consumer status region that exists before the wait. Dismiss: it contradicts Yeti's documented form and the manifest's `a11y.notes`, which the package's examples follow.
   - **Option C: only Yeti's form.** Dismiss as the only form: a ring inside text that is already a status would be announced twice.
   - **To overrule:** for B, remove usage rule 2's form from the examples and make usage rule 4 the rule; for C, remove usage rule 4 and the `spinner--decorative` story. Decided 2026-10-03 in ticket 50, decision 190 (orchestrator, full AFK mode).
2. **The ring as the only visual sign of the wait (WCAG 1.4.11 and 1.4.1)** (MEDIUM impact, MEDIUM confidence). Spec usage rule 3, section 7's 1.4.11 row, `spinner--default` and `spinner--variants`. ADR 0015 point 3 says play functions compute non-text contrast; no record says whether the ring is a graphical object required to understand the content, or which variants must pass.
   - **Option A (recommended):** usage rule 3 requires visible text beside the ring (Yeti's own example has it), so the ring is never the only sign; `spinner--default` asserts at least 3:1 between the bright edge and the surface for the default variant in both schemes; `spinner--variants` records the other variants' ratios without asserting. Approve: Yeti's example already pairs ring and text, and asserting every variant on an unmeasured palette could fail on Yeti's defaults with nothing the package can change.
   - **Option B:** assert 3:1 for every variant on its shown surface. Dismiss for now: no record measured the variants' ring contrast, and `white` and `black` depend on the paint behind them.
   - **To overrule:** for B, turn the `spinner--variants` recording into an assertion; if a variant fails, add a ledger row owned by `spinner` (WCAG 1.4.11) and a usage rule naming the surfaces it may sit on. Decided 2026-10-03 in ticket 50, decision 191 (orchestrator, full AFK mode).
3. **The removal usage rule under A11Y-13** (MEDIUM impact, HIGH confidence). Spec usage rule 5 and the 2.2.2 row. Ledger A11Y-13 and ticket 25 grilling question 13 already decide that the ring falls under 2.2.2's essential exception, with no package code and Yeti's reduced motion. No record says that the consumer removes the ring when the work ends, which is what keeps the exception true. **Recommendation:** usage rule 5 as written, decided together with the [progress](86-spec-progress.md) spec's open point 2 (its usage rule 9, the indeterminate stripes), so both items give one answer: no package code, no pause control, Yeti's reduced-motion handling, and the consumer removes the indicator when the work ends. The A11Y-13 row stays as it reads. To overrule: add a pause control or a maximum iteration count through `--yeti-motion-iterations` on the host as a usage rule, with a ledger note on A11Y-13; neither needs a directive change. Decided 2026-10-03 in ticket 50, decision 192 (orchestrator, full AFK mode).
4. **Forced colours** (LOW impact, MEDIUM confidence). Spec section 7 and the layer-4 forced-colours case. Ticket 17 did not measure the spinner under forced colours. Forced colours replace border colours, so the ring and its bright edge are inferred to become one colour, and a turning ring of one colour looks still; the status and name are unaffected. **Recommendation:** no ledger row and no package CSS now; layer 4 records the border colours and a screenshot in Chromium and Firefox. If the bright edge is lost, a ledger row owned by `spinner` and one `@layer ngx-yeti` rule follow, after Material's `CanvasText` arc (`NC/src/material/progress-spinner/progress-spinner.scss:46-54`), on both selectors of Yeti's shared rule (`.spinner` and `.button[aria-busy="true"]::after`), as ticket 50 decision 88 set for the breadcrumbs. To overrule: add the row and the rule now, asserted in layer 4 with the accessibility stylesheet left out, as the [progress](86-spec-progress.md) spec does for A11Y-1e. Decided 2026-10-03 in ticket 50, decision 193 (orchestrator, full AFK mode).
5. **The host element** (LOW impact, HIGH confidence). Spec usage rule 1. Part 2 row 38 gives the selector `[yetiSpinner]`, any element. **Recommendation:** keep the selector, and a usage rule: an empty, non-interactive inline element, `span` as Yeti's example writes it, never a button, link, or form control, and never with content (the host is a 1 em box whose border is the ring), after ticket 50 decision 77 for the badge's hosts. HTML `size` is `inert` on it. To overrule: narrow the selector to `span[yetiSpinner]` and amend Part 2 row 38. Decided 2026-10-03 in ticket 50, decision 194 (orchestrator, full AFK mode).

## Answer

Resolved 2026-10-03 by Claude Opus 5.5. Spec: [specs/spinner.md](../specs/spinner.md).

One item directive, `YetiSpinner` on `[yetiSpinner]` (`exportAs: 'yetiSpinner'`, entry point `ngx-yeti/spinner`), binding the static class `spinner`, the presence attribute `data-ngx-yeti-item-spinner`, and `data-variant` and `data-size` from `variant: YetiVariant` and `size: YetiSizeControl` (`inert`) (ticket 26 rows 141 and 142). Native platform, level 1, types only; no Module, no Aria, no CDK (Part 2 row 38). It calls `injectYetiItemStyles('spinner')` last in its constructor. The item file is shared with `YetiButton`, which acquires it unconditionally for the busy ring (ADR 0060 point 9; the [button](76-spec-button.md) spec), and layer 2 proves the shared count from the spinner's side. `role="status"`, the name, the visible text, and the completion message are the consumer's (Part 2 row 38; building-blocks 1.10). The spec records ledger A11Y-13's reading: WCAG 2.2.2's essential exception, Yeti's reduced motion (one 0.01 ms turn, asserted in layer 4 after Yeti's test), no package code, and the consumer removes the ring when the work ends.

Counts: 47 user stories, 5 open points (none HIGH impact; none blocks the spec).
