## Question

What is the Angular API of Yeti's `tooltip` component, and what does its spec say? Its decisions are already made in the records: its row in `building-blocks.md` Part 2 (and the "Aria decisions" section where it applies), its rows in [Decide: how the package maps each of Yeti's `data-*` attributes](26-decide-yeti-data-attributes-mapping.md), its item file under [ADR 0060](../adr/0060-item-styles-are-counted-links-to-the-consumers-yeti-build.md), its ledger rows, and the shared specs it links to.

## How to work it

Write `specs/tooltip.md` with the `/to-spec` template and the map's Spec shape note, from the records only. The spec decides nothing a record has not decided. Anything it needs and no record settles goes under the ticket's `### Open` for the orchestrator. Append an `## Answer` that links the spec.

### Open

Each point is marked "(open: see ticket)" in the spec, which carries the recommendation as its best reading. Impact and confidence follow the trap-quadrant rule (map, Standing rulings, 2026-10-03). Points 1 and 6 are in the trap quadrant and carry their options records.

1. **Escape for a Bubble shown by hover while focus is elsewhere** (spec section 4 item 2, section 7 (1.4.13, 2.4.11), user story 17, layer 2, layer 4). Impact: HIGH (it decides whether ledger row A11Y-2 meets WCAG 1.4.13 "dismissible" at all for pointer users, which is the row's whole purpose). Confidence: MEDIUM.
   - **Question.** ADR 0043 point 2 puts the tooltip's Escape on "a `keydown` host listener on the tooltip's root". A key event is dispatched to the focused element, or to `body` when nothing is focused, and bubbles from there. A Bubble shown by a resting pointer, with focus on another control or on `body` (the usual state after a mouse click on the page), therefore never sends Escape through the root, and the root listener cannot dismiss it. WCAG 1.4.13 asks that content shown on hover be dismissible "without moving pointer hover or keyboard focus", and A11Y-2's own "Tested by" names "L4 (hover then Escape, 3 engines)". How does the package hear that Escape?
   - **Option A: the root listener only**, the record's letter. Dismissed: the hover case, which is most of a tooltip's use, stays as Yeti left it; the L4 case A11Y-2 names would fail whenever focus is outside the root.
   - **Option B: the root listener plus a `document` `keydown` listener added in code on `pointerenter` and removed on `pointerleave` and on destroy**, Material's shape (Material listens on `body` through CDK's `OverlayKeyboardDispatcher` only while a tooltip is attached, `NC/src/cdk/overlay/dispatchers/overlay-keyboard-dispatcher.ts:31`; `NC/src/material/tooltip/tooltip.ts:561-568`). Not chosen: it adds a `pointerenter` listener and a code-registered listener with its own removal (building-blocks 1.15), and leaves a gap: a pointer already resting on the Trigger when the boundary hydrates (or when `hydrate on hover` fires) gets no listener until it leaves and re-enters, because `pointerenter` is not replayed. Its gain is that no listener runs while no tooltip is hovered.
   - **Option C: one `(document:keydown)` host listener per tooltip, and no root listener.** It covers both cases, because a key event in the root bubbles to the document. Not chosen: it removes the record's root listener, so an Escape pressed on a focused Trigger before hydration is no longer replayed, and it changes ADR 0043 point 2 more than needed.
   - **Option D (recommended): keep the root `keydown` listener for the focus case, and add a `(document:keydown)` host listener for an Escape whose target is outside the root**, both guarded by "shown" (the root matches Yeti's `:hover` or `:has(:focus-visible)`, which is ADR 0016 point 3's "while its trigger stays hovered or focused" and Material's `_isTooltipVisible()` predicate, `tooltip.ts:942-948`). The document path calls no `preventDefault()`, so the focused widget keeps its own Escape. Approved because it keeps the record's listener and its replay unchanged, adds one line of `host` metadata that Angular removes with the directive, has no hover gap at hydration, and follows the [dialog](../specs/dialog.md) spec's precedent of a global host listener per instance (`(window:keydown)` for its veto). Its cost: every key press on the page runs one key comparison per tooltip and, because Angular's listener wrapper marks the view for check, schedules a change-detection pass while any tooltip is on the page (inferred from Angular's listener wrapping; the dialog's `window:keydown` has the same cost).
   - **Evidence and confidence.** That key events never pass through the root when focus is outside it: the DOM's key event targeting (read, HIGH). That ticket 17 measured Escape not dismissing "either while hovered or while focused" (`research/yeti-accessibility-and-standards.md`, 4.21): measured, but before any package listener existed. That Material solves the hover case with a body-level listener: read (HIGH). The cost of option D's listener: inferred (MEDIUM). Which of B and D is better is a judgement on that cost against simplicity (MEDIUM).
   - **To overrule.** For B: in spec section 4 replace item 2's `(document:keydown)` with a `pointerenter` listener that registers the document listener and a `pointerleave` and `DestroyRef` removal; add the hydration gap to section 10 (Event replay, `hydrate on hover`) and a layer-4 case that records it. For C: remove item 1, move its `preventDefault()` rule into item 2 for targets inside the root, remove `keydown` from the `jsaction` assertions in sections 8 and 10 and layer 3, and turn the layer-4 "Escape before hydration" case into one that records nothing is dismissed. For A: remove item 2 and the hover-with-focus-elsewhere cases, and change A11Y-2's "Tested by" to the focus case only. Whatever is chosen, ADR 0043 point 2 and ledger row A11Y-2 get a dated note naming the listener. Decided 2026-10-03 in ticket 50, decision 215 (orchestrator, full AFK mode).
2. **`preventDefault()` on a dismissing Escape in the focus case** (spec section 4 item 1, section 5, user story 23, `tooltip--in-dialog`, layer 4). Impact: MEDIUM. Confidence: MEDIUM. ADR 0043's consequences say the handlers "change state first and call no `preventDefault()`"; building-blocks 1.5 says every package key handler "changes state first and calls `preventDefault()` last". With no `preventDefault()`, one Escape on a focused Trigger inside a modal `dialog` or an open dropdown panel both hides the Bubble and closes the dialog or panel, and focus moves, which is what 1.4.13 asks a dismissal to avoid. Material cancels the key and stops it (`tooltip.ts:565-566`), and the [dialog](../specs/dialog.md) spec already relies on a cancelled Escape `keydown` not becoming a close request (its veto). Recommendation: call `preventDefault()` as the root handler's last statement, only when it dismissed a shown Bubble, never from the document path; a second Escape then closes the dialog or panel. During replay the call throws after the state is set, which building-blocks 1.5 and 1.11 accept. Layer 4 records, per engine, that the first Escape leaves the dialog and a dropdown panel open. ADR 0043 gets a dated note that its "no `preventDefault()`" consequence covers the focus-out listener, not the tooltip's dismissing Escape. To overrule: remove the call from item 1 and turn `tooltip--in-dialog` into a case that records one Escape closing both. Decided 2026-10-03 in ticket 50, decision 216 (orchestrator, full AFK mode).
3. **When `dismissed` resets** (spec section 4 items 3 and 4, user story 20, layer 2). Impact: MEDIUM. Confidence: MEDIUM. ADR 0043 point 2 says "`pointerleave` and `focusout` on the root reset it"; ADR 0016 point 3 says the Bubble "stays hidden until the pointer or focus leaves and returns". Read literally, a Bubble dismissed while the Trigger is both hovered and keyboard-focused comes back as soon as the pointer moves off, because `:has(:focus-visible)` still shows it, so the user who just dismissed it sees it again without leaving the Trigger. Recommendation: keep the two listeners, but each resets only when the other route no longer shows the Bubble (`pointerleave` when the root does not match `:has(:focus-visible)`; `focusout` when `relatedTarget` is outside the root and the root does not match `:hover`). So the Bubble returns only once both pointer and keyboard focus have left and one of them comes back. To overrule: make both listeners reset unconditionally, and change the layer-2 "both at once" case to expect the Bubble back after the pointer leaves. Decided 2026-10-03 in ticket 50, decision 217 (orchestrator, full AFK mode).
4. **`role="tooltip"` rendered by the Bubble's directive** (spec section 2, section 4, usage rule 6). Impact: LOW. Confidence: HIGH. Part 2 row 42 puts `[yetiTooltipBubble]` "on the `role="tooltip"` element" without saying who writes the role. The role is the part's identity in Yeti's CSS (`.tooltip > [role="tooltip"]`, `tooltip.css:11`) and in the manifest's `children`, and ADR 0003 has the consumer write none of Yeti's contract. Recommendation: a static host attribute `role: 'tooltip'` on `YetiTooltipBubble`, as the dropdown panel's directive renders `popover` and the carousel's track directive renders its `role`; a consumer's own static `role="tooltip"` is equal and harmless. To overrule: make the role the consumer's in a usage rule and assert it in the stories instead. Decided 2026-10-03 in ticket 50, decision 218 (orchestrator, full AFK mode).
5. **A Trigger that is also a field's control** (spec section 3, usage rule 7, user story 45). Impact: MEDIUM. Confidence: MEDIUM. Part 2 row 42 says "A trigger that is also a field control has two `aria-describedby` writers (row 33); the spec states which wins", and the [field](../specs/field.md) spec defers to this spec. Both `yetiFieldControl` and `yetiTooltipTrigger` would declare an input aliased `aria-describedby` and bind `[attr.aria-describedby]`, and two package directives must not both own one attribute (building-blocks 1.4; ticket 25 point 11). Options: (a, recommended) a usage rule: never put `yetiTooltipTrigger` on a `yetiFieldControl`; use the field's hint, which Yeti's docs call "almost always the better answer", or a tooltip on a separate button beside the label; (b) `yetiTooltipTrigger` injects `YetiFieldControl` on its own element and, when present, binds nothing and hands its Bubble's id to the field control, which needs a new registration API in the field spec and makes `ngx-yeti/tooltip` depend on `ngx-yeti/field`; (c) a shared description-owner token both directives use, new to both specs. (a) is recommended because it adds no API, keeps the entry points independent, and matches Yeti's own advice. To overrule for (b): add the registration to the field spec's `YetiFieldControl`, add the self-injection to this spec's section 3, replace usage rule 7 with the composed case, and add a layer-2 and an e2e case for the merged value. Decided 2026-10-03 in ticket 50, decision 219 (orchestrator, full AFK mode).
6. **Reflow and clipping under Yeti's fallback placement** (spec section 7 (1.4.10), usage rule 12, user story 29, layer 4). Impact: HIGH (a WCAG 2.2 AA failure in every browser at the target's floor, on any page with a tooltip near the inline end). Confidence: MEDIUM.
   - **Question.** Without anchor positioning, Yeti centres the Bubble above its Trigger at `max-content` width up to `16rem` and does not slide it (`tooltip.css:11-27`); Yeti's own test says that in the fallback "the bubble overflows the edge rather than sliding" (`tooltip.spec.js:101`) and "is absolutely positioned and can be clipped" (`:138`). The Bubble is laid out while hidden (`visibility: hidden`), so a Trigger near the inline end can widen the page's scrollable area at rest, a 1.4.10 failure (inferred from the CSS). The anchor-positioning keys Yeti guards on reach Chrome 151, Firefox 151, and Safari 27 ([research/browser-baseline-vs-yeti.md](../research/browser-baseline-vs-yeti.md):281), so every floor browser of ADR 0002 uses the fallback. What does the package do?
   - **Option A (recommended): record and measure, as [ticket 50](50-decide-open-points-of-the-specs.md) decisions 17 and 47 did.** Usage rule 12 (keep a Trigger near the inline end to a short hint); a new ledger row owned by `tooltip` ("in Yeti's fallback a Bubble near the inline end overflows the page, and a scrolling ancestor clips it"; WCAG 2.2 1.4.10; Yeti states the clipping in `docs.md`; the package adds the usage rule; verified *read* for the overflow in Yeti's test, *inferred* for the page's scroll width; tested by L4); a layer-4 `scrollWidth` case at 320 px that asserts where anchor positioning exists and records where it does not, and that runs at the floor once floor testing is decided (building-blocks Part 4). No package CSS until measured. Approved because it follows the two precedents, P16 (Yeti's fallbacks are the fallbacks; no package `@supports` check), and decision 17's rule that every gap found is a row.
   - **Option B: a package rule in `@layer ngx-yeti`** under the user's "Accessibility CSS: Yes." (map, Standing rulings), for example `display: none` on the Bubble while it is not shown, inside `@supports not (anchor-name: --a)`, which removes its layout at rest. Dismissed for now: P16 avoids a package `@supports` check, the rule would change Yeti's fade in the fallback, and it fixes only the at-rest overflow, not a shown Bubble cut off at the edge. It is the first candidate if the layer-4 measurement fails.
   - **Option C: no row and no rule, as Yeti's stated limit.** Dismissed: ticket 50 decisions 17 and 32 dismissed the same option, because the package's AA requirement is never a recommendation and the ledger records Yeti's gaps too.
   - **Option D: a JavaScript positioner for the fallback.** Dismissed: building-blocks 1.8 and P29 rule out any package positioner and measured placement.
   - **Evidence and confidence.** The fallback geometry and Yeti's own statement of the overflow: read (HIGH). That a hidden, laid-out Bubble widens the scrollable area: inferred from CSS overflow rules (MEDIUM). That the floor lacks the guarded keys: read from web-features data in ticket 01 (HIGH). How often a real page puts a Trigger close enough to the edge: unknown (LOW), which is why A measures before adding CSS.
   - **To overrule.** For B: add the rule to the package's accessibility stylesheet with a source comment, set the new row's "What the package adds" to it, and turn the layer-4 record into an assertion in the fallback. For C: remove usage rule 12, the row, and the layer-4 case. If layer 4 shows no page overflow in the fallback, A shrinks to the clipping note and the row records *measured, no overflow*. Decided 2026-10-03 in ticket 50, decision 220 (orchestrator, full AFK mode).
7. **Forced colours and the Bubble's edge** (spec section 7, layer 4). Impact: LOW. Confidence: MEDIUM. The Bubble is a background with no border, and its caret a background with a `clip-path` (`tooltip.css:21`, `:41-50`), so under `forced-colors: active` its edge and caret may disappear while its text stays readable. ## Answer

Resolved 2026-10-03 by Claude Opus 5.5. Spec: [specs/tooltip.md](../specs/tooltip.md).

There are three directives in `ngx-yeti/tooltip`. The root is `YetiTooltip` on `[yetiTooltip]`, usually a `span`. It binds the class `tooltip`, `data-placement` from `placement` (`YetiPlacement`, ticket 26 row 159), and the presence attribute `data-ngx-yeti-item-tooltip`. It provides `yetiTooltipToken`, holds a read-only `dismissed` signal, and loads the item file last in its constructor. The Trigger is `YetiTooltipTrigger`, which binds `aria-describedby` to the consumer's ids followed by the Bubble's id (ticket 50 decision 46). The Bubble is `YetiTooltipBubble`, which renders `role="tooltip"`, its generated or consumer id, and `hidden` while dismissed, through Yeti's `[hidden]` rule. Escape without a modifier dismisses a shown Bubble, and the pointer and focus leaving reset it (ADR 0016 point 3; ADR 0043 point 2; ledger A11Y-2). The tooltip has no model, no outputs, no methods, no popover, and no `AriaDescriber`, `FocusMonitor`, or Aria. Yeti's tooltip has no Module, so the spec maps each behaviour of Yeti's CSS-only tooltip instead of a module.

Counts: 51 user stories, 12 usage rules, 8 story ids, and 7 open points. Points 1 and 6 have HIGH impact and MEDIUM confidence, so they are in the trap quadrant and their options are recorded above. No open point blocks the spec: it carries each recommendation, and overruling one changes a listener, a usage rule, or a test, not the item's shape. Point 1 finds that ADR 0043 point 2's root listener alone cannot hear Escape for a Bubble shown by hover while focus is elsewhere. Points 1 to 3 would each give ADR 0043 and ledger row A11Y-2 a dated note, and point 6 would add a ledger row. The spec itself writes no ledger or upstream-bug row.
