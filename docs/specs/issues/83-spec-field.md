### Open

Points 1 to 3 have HIGH impact and confidence below HIGH, so each is recorded with its options for ticket 50 (map, Standing rulings, trap-quadrant decisions in full AFK mode). The spec carries each recommendation as its reading, marked "(open: see ticket)".

1. **How the error slot shows the rule's message without overwriting the consumer's text** (spec Solution, sections 2 and 4; HIGH impact, MEDIUM confidence; trap quadrant).
   - **Question.** Part 2 row 33 and A11Y-14 say the error "renders the control's first error message through `[textContent]` where the consumer's slot is empty, as `validate.js:40-43`". A `[textContent]` host binding replaces the host's children on every write, `null` included, so it cannot leave the consumer's text alone. A directive cannot tell from its host whether the template gave the slot content: at creation on the client the children do not exist yet, at hydration the server's children do, and on the server the fallback text it rendered would look like the consumer's. So the row's mechanism cannot be built as written without a hydration mismatch or a DOM read that differs between server and client.
   - **Option A (recommended, the spec's reading): `YetiFieldError` is an attribute-selector Angular component whose template is one `ng-content` with `message()` as its fallback content.** Angular renders fallback content only when nothing is projected (the Angular clone's `adev/src/content/guide/components/content-projection.md:184-186`, read). Approve: it is exactly Yeti's rule ("An error element you fill in yourself is never overwritten; an empty one is the slot the module writes into", `docs.md:39`); both of Yeti's markup forms work unchanged; it renders on the server and hydrates as component template output; it needs no DOM read or write. Cost: a second Angular component in the package, where building-blocks Part 2, Part 4, and the glossary say `demo` is the only one. CONTEXT.md allows a component "where a part needs structure the consumer should not hand-write", which the generated message is. A whitespace-only slot counts as empty only while whitespace is not preserved (the spec's section 11).
   - **Option B: a directive that always binds `[textContent]` to a selector-named input or the rule's message** (`<p yetiFieldError="Enter your name."></p>`, empty value for the rule's message). Keeps a directive and the row's `[textContent]`. Dismissed: content a consumer writes inside the slot, as Yeti's docs do, is wiped with no error, and no rich content (a link) is possible.
   - **Option C: a directive with a read-only `message` signal that the consumer interpolates** (`<p yetiFieldError #e="yetiFieldError">{{ e.message() }}</p>`). No component and no `[textContent]`. Dismissed: an empty slot stays empty, so Yeti's empty-slot form shows a blank error, and every field repeats the interpolation.
   - **Option D: read the host's children at the first client render and write the message imperatively.** Dismissed: nothing renders on the server, the decision differs between client rendering and hydration, and building-blocks 1.5 limits imperative writes to calls such as `focus()`.
   - **Evidence and confidence.** `[textContent]` semantics and directive creation order: read and inferred, not measured. Fallback content: read in Angular's guide at 22.2; not prototyped for an attribute-selector component on a `p` under hydration. MEDIUM.
   - **To overrule.** For B: make `YetiFieldError` a directive with a selector-named string input, add a usage rule that the slot holds no content, and change the examples and the `field--message-slot` story. For C: remove the fallback, add the interpolation to every example, and make the empty-slot case a blank-slot anti-pattern. Either way Part 2 row 33 and A11Y-14 need no component, and the counts stay. Decided 2026-10-03 in ticket 50, decision 159 (orchestrator, full AFK mode).

2. **Focus on the first invalid control after a refused submit** (spec sections 4 and 7; HIGH impact, MEDIUM confidence; trap quadrant).
   - **Question.** `validate.js:61` focuses the first invalid control, which is how Yeti's message reaches a screen reader (ticket 19 section 1.3). ADR 0040 says the package owns every behaviour a module has. ADR 0020 point 3 says the message reaches assistive technology "through focus on the first invalid control after a refused submit, which Signal Forms provides (`focusBoundControl()`)", and architecture-guide P20 says the field directives "move focus to the first invalid control in an `onInvalid` recipe". Signal Forms moves no focus itself (ticket 19, read), and reactive forms have no focus helper. A11Y-14 tests "L1 (a refused submit focuses the first invalid control)". Is the focus the package's or a consumer recipe?
   - **Option A (recommended, the spec's reading): `YetiForm` focuses the first invalid registered control in its `submit` handler.** Approve: like-for-like with `validate.js` under ADR 0040, the same under Signal Forms, reactive, and template-driven forms, and it makes A11Y-14's test a package behaviour. Cost: a consumer whose `onInvalid` moves focus elsewhere (to an error summary) races the directive, depending on which `submit` listener runs last.
   - **Option B: a documented recipe** (`errorSummary()[0]?.fieldTree().focusBoundControl()` in `onInvalid`; `(invalid)="$event.controls[0]?.focus()"` under reactive forms), as P20 and the old Abide spec had it. Dismissed: every form must remember it, and a forgotten recipe leaves a refused submit silent for a screen-reader user (WCAG 3.3.1).
   - **Option C: A with an opt-out input on `YetiForm`** (for example `focusFirstInvalid`, default `true`). Not recommended now: it adds public API for a case no record raises; it can be added later without a break.
   - **Evidence and confidence.** `validate.js:59-61`, `form_root.ts:45-56`, and `structure.ts:463-511` read; ticket 19 measured that `focusBoundControl()` from `onInvalid` moves focus. The records disagree in wording, so MEDIUM.
   - **To overrule.** For B: remove the focus call from section 4, add the recipe to every usage example and to the `field--form-invalid` story, and change A11Y-14's "Tested by" to the recipe. For C: add the input to section 4's `YetiForm` table and a layer-2 case. Decided 2026-10-03 in ticket 50, decision 160 (orchestrator, full AFK mode).

3. **Values typed or checked before hydration** (spec sections 4 and 10; HIGH impact, MEDIUM confidence; trap quadrant).
   - **Question.** At hydration, Angular forms' first update writes the model into each control (`NGP/forms/signals/src/directive/control_native.ts:119-125`, read), which clears what a person typed before hydration; the replayed `input` then reads the cleared value. The old bundle's Abide prototype measured the loss in three engines on Foundation markup, under Signal Forms and reactive forms. ADR 0020 carried only the held submit (point 5), not the value rescue, although ticket 19's transfer list names both. The affix spec's e2e already expects a value typed before hydration to survive. Does `YetiFieldControl` adopt such values?
   - **Option A (recommended, the spec's reading): adopt them, as the old Abide spec did.** Save the host's `value` or `checked` at construction; in `afterNextRender`, before replay, write it back when it differs and is not empty, and dispatch `input` (and `change` on a checkbox or radio) so the forms library parses it through its own value path. Skip `file` and `select[multiple]`. Approve: WCAG 3.3.7 and plain data loss; it covers every forms API with one mechanism; client rendering is unaffected. Cost: a server-prefilled field the person cleared before hydration gets its prefill back (the old spec's stated limit). It is a new ledger row (below).
   - **Option B: document the loss and recommend `hydrate on viewport`, `idle`, or `immediate`.** Dismissed: the loss happens under full hydration too, which no trigger avoids.
   - **Option C: rely on the held submit only.** Dismissed: the held submit protects the submission, not the values.
   - **Evidence and confidence.** The overwrite is read in Angular 22.2 and was measured in the old bundle (evidence only), not re-measured on Yeti. MEDIUM.
   - **To overrule.** Remove the pre-hydration paragraph from section 4, the 3.3.7 sentence's last clause, the layer-2 case, and the layer-4 case, and state the loss under section 10's "Full hydration" as a residue; the affix spec's typed-before-hydration e2e case then changes too. Decided 2026-10-03 in ticket 50, decision 161 (orchestrator, full AFK mode).

4. **How `YetiForm` learns that a submit was refused, and how it lists the controls** (spec sections 3 and 4; MEDIUM impact, MEDIUM confidence). Part 2 row 33 says the `invalid` output comes "from Signal Forms' `onInvalid` or reactive forms' submit". `onInvalid` is the consumer's submission option, which a directive cannot hook. Recommendation (the spec's reading): `YetiForm`'s own `(submit)` host listener, with no `preventDefault()`, reads `FormRoot.fieldTree()().invalid()` (self-injected, optional) or the self-injected `ControlContainer`'s `invalid`, and does nothing with neither. That equals Signal Forms' default `ignoreValidators: 'pending'`; a form submitted with `'none'` or `'all'` may disagree, which the docs note. The controls are the hosts of the `YetiFieldControl`s registered through a new `yetiFormToken` whose field is invalid, sorted by `compareDocumentPosition` only when a submit is refused, rather than kept sorted by a `MutationObserver` (building-blocks 1.9's ordered-parts shape), because order is needed only in that handler. To overrule: build `controls` from Signal Forms' `errorSummary()` and `formFieldBindings()` (Signal Forms only), or add the `MutationObserver`. Decided 2026-10-03 in ticket 50, decision 162 (orchestrator, full AFK mode).

5. **The error's id in `aria-describedby` only while the error shows** (spec sections 2 and 4; MEDIUM impact, MEDIUM confidence). ADR 0020 point 2 and Part 2 row 33 compose the description "from the hint's and the error's ids" without saying when. A hidden element referenced by `aria-describedby` is still part of the description, so listing the error's id at all times (as Yeti's own example does) announces a message that is not on screen. Recommendation (the spec's reading): include it only while the error state is true, after Material's `_syncDescribedByIds` (`NC/src/material/form-field/form-field.ts:759-790`), which Part 2 row 33 cites as the pattern. To overrule: list it always and accept the hidden description; change the layer-1 and layer-2 cases. Decided 2026-10-03 in ticket 50, decision 163 (orchestrator, full AFK mode).

6. **A server-reported `aria-invalid="true"`** (spec sections 2 and 4; MEDIUM impact, MEDIUM confidence). ADR 0020's considered options leave to this spec how the directive adopts it at hydration. Recommendation (the spec's reading): `YetiFieldControl` declares an input aliased `aria-invalid`, the same shape as the orchestrator's `aria-describedby` decision; a static `"true"` makes the error state true until the control's first `input` or `change`, as `validate.js:69-84` clears a fixed control. The static attribute is written back at hydration and the bound value equals it, so the DOM does not change. To overrule: add a usage rule to report server errors through Signal Forms' submission errors only, and remove the input. Decided 2026-10-03 in ticket 50, decision 164 (orchestrator, full AFK mode).

7. **Which hint and error describe a control in a nested group field** (spec section 3; LOW impact, MEDIUM confidence). Recommendation (the spec's reading): the control's own field's, else the nearest enclosing field's that has them, which is `validate.js:91-96`'s "nearest field that has a slot", through each `YetiField` injecting its parent field. The alternative is `aria-describedby` on the `fieldset` itself, which no record mentions and whose support across screen readers is not checked. To overrule: bind the group's ids on the `fieldset` host and not on its controls. Decided 2026-10-03 in ticket 50, decision 165 (orchestrator, full AFK mode).

8. **Small readings of Part 2 row 33** (spec section 4; LOW impact, HIGH confidence). The spec's readings, each the smallest that meets the row: the id prefixes `field-hint` and `field-error` for `injectYetiId`; the range's value from `FormField.state().value()`, else `NgControl`, else the host's static `value` and its `input` events, and `min` and `max` from the schema, else the static attributes, else 0 and 100 (`range.js:21-22`); `YetiFieldOutput` binds `for` from the range control's `id` and a static `aria-hidden="true"` (Yeti asks every author for it, `docs.md:20`); `errorState` is a public read-only signal on `YetiFieldControl`, as Material names it. Recommendation: accept as written. Decided 2026-10-03 in ticket 50, decision 166 (orchestrator, full AFK mode).

## Answer

Resolved 2026-10-03 by Claude Opus 5.5. Spec: [specs/field.md](../specs/field.md).

Six pieces in `ngx-yeti/field`: the item directive `YetiField` on `[yetiField]` (class `field`; `variant`, `size`, `inline`; presence attribute `data-ngx-yeti-item-field`; the `field` item file; `yetiFieldToken`; `--yeti-range-value` as a server-rendered host style binding); the part directive `YetiFieldHint` and the part `YetiFieldError` (static markers, ids through `injectYetiId`; the error is an attribute-selector component whose `ng-content` fallback is the rule's message, point 1); `YetiFieldControl` on `input`, `select`, and `textarea` (`FORM_FIELD`, then `NgControl`; `aria-invalid` from one Material-shaped policy; `aria-describedby` merged from the consumer's ids, the hint, and the error while it shows); `YetiFieldOutput` on the range's `output`; and the free behaviour directive `YetiForm` (`ready`, the `invalid` output with `YetiInvalidDetail`). Custom Angular, level 4 (Part 2 row 33). Both modules, `range.js` and `validate.js`, are replaced line by line. Ledger rows owned: A11Y-1d and A11Y-6 (rules in `@layer ngx-yeti`), A11Y-14, A11Y-19.

Counts: 64 user stories, 15 usage rules, 13 story ids, 8 open points. Points 1 to 3 have HIGH impact and MEDIUM confidence, so they are in the trap quadrant and are recorded with their options above. None blocks the spec: it carries each recommendation as its reading, marked "(open: see ticket)", and says what an implementer changes to overrule it.
