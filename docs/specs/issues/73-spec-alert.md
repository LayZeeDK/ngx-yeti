## Question

What is the Angular API of Yeti's `alert` component, and what does its spec say? Its decisions are already made in the records: its row in `building-blocks.md` Part 2 (and the "Aria decisions" section where it applies), its rows in [Decide: how the package maps each of Yeti's `data-*` attributes](26-decide-yeti-data-attributes-mapping.md), its item file under [ADR 0060](../adr/0060-item-styles-are-counted-links-to-the-consumers-yeti-build.md), its ledger rows, and the shared specs it links to.

## How to work it

Write `specs/alert.md` with the `/to-spec` template and the map's Spec shape note, from the records only. The spec decides nothing a record has not decided. Anything it needs and no record settles goes under the ticket's `### Open` for the orchestrator. Append an `## Answer` that links the spec.

### Open

1. **When `closed` fires** (spec section 2 contract mapping and Module replaced, section 4, section 9 "Completion"; HIGH impact, MEDIUM confidence; trap quadrant).
   - **Question.** The writers' brief says the events spec maps the alert's `yeti:close` to `closed`, "which fires after the transition (ticket 50)". Yeti dispatches `yeti:close` after its fade and before the removal (`alert.js:13-18`). But Part 2 row 23 moves both the fade and the removal out of the package: the consumer's `@if` removes the alert in response to `closed`, and a class-form `animate.leave` fades it during that removal. So the transition happens after `closed`, because `closed` is what causes it. When does `closed` fire?
   - **Option A (recommended): on the dismissal.** The close part's click handler moves focus as `alert.js:24-29` does, then the root emits `closed`. The consumer removes the alert, and the leave transition runs. `closed` is a notification of the reader's choice, not a **Completion output**. Approve: it is the only order in which Part 2 row 23's design works. It matches the events spec's own usage example (`(closed)="showAlert.set(false)"`), its user story 8 ("so that I know when to remove it with my own `@if`"), and its rule 7 ("on the choice the user or the platform made"). Ticket 50 decision 3 names the dialog's, dropdown's, and nav's outputs as completion outputs; it does not name the alert's.
   - **Option B: the directive fades the alert itself, awaits the transition by building-blocks 1.6 rule 1, then emits; the consumer removes with no `animate.leave`.** Dismissed: the alert has no Yeti transition to key on, so the directive would have to add a class, an inline style, or a package CSS rule to fade it. ADR 0003 point 3 and building-blocks 1.6 rule 1 forbid the first two, and ADR 0060 point 8 limits package CSS to accessibility rules. It also contradicts Part 2 row 23 ("Removal is the consumer's `@if` with class-form `animate.leave`").
   - **Option C: emit after the leave transition.** Dismissed: circular. The leave starts only when the consumer removes the alert, which waits for `closed`. Angular gives no completion notice for the class form, and the function form, which does, is never used (ADR 0010 point 2; `upstream-bugs.md` A1). The directive has also been destroyed by then, so its output can no longer reach the consumer (inferred).
   - **Option D: two outputs, `closed` on the dismissal and a completion output after the fade.** Dismissed for the reason of C: nothing in the package can observe the end of a class-form leave on a destroyed directive.
   - **Evidence and confidence.** Part 2 row 23, the events spec (sections 2 and 4, user story 8, usage example), ADR 0010, and `alert.js` were all read. Confidence is MEDIUM only because the brief states the opposite. If the orchestrator meant something not in the records, this point needs that record.
   - **To overrule.** For B: add a package-owned fade and a transition wait to `YetiAlert`; amend Part 2 row 23, ADR 0060 point 8 (or ADR 0003 point 3), and architecture-guide P19; remove `animate.leave` and the leave rule from the spec; change layer 2 to assert that `closed` fires after `transitionend` or the fallback timer. In every case, the events spec's row for `yeti:close` on `.alert` should say when `closed` fires. Decided 2026-10-03 in ticket 50, decision 100 (orchestrator, full AFK mode).
2. **The leave class** (spec section 9, usage rule 8; MEDIUM impact, HIGH confidence). Part 2 row 23 says `animate.leave` names "Yeti's transition", but `alert.css` has no transition and Yeti has no exit class (read by search over `Y/src/**/*.css`). Recommendation: the class is the consumer's. It is named `leaving` in every example, after architecture-guide P19. Its one rule, `.alert.leaving { opacity: 0; transition: opacity var(--yeti-duration-fast) var(--yeti-ease); }`, lives in the consumer's stylesheet, as ADR 0010 point 2 allows ("a class whose rule reuses Yeti's tokens"). The package ships no rule (ADR 0060 point 8). Part 2 row 23's wording "naming Yeti's transition" should read "naming a consumer class that reads Yeti's duration token". To overrule: ship the rule in the package's stylesheet, which needs an exception to ADR 0060 point 8, because a fade is not accessibility CSS. Decided 2026-10-03 in ticket 50, decision 101 (orchestrator, full AFK mode).
3. **The parent's one-shot `blur` listener outlives the directive** (spec section 2 Module replaced, section 12, layer 2; MEDIUM impact, MEDIUM confidence). `alert.js:28` removes the temporary `tabindex` on the parent's next `blur`. The package's close part is destroyed as soon as the consumer removes the alert, usually before the parent loses focus. Building-blocks 1.15 says that every `addEventListener` in code is removed in `DestroyRef.onDestroy`. Removing the listener on destroy would leave `tabindex="-1"` on the parent for good. Removing the attribute on destroy instead would make the focused parent unfocusable, and focus would fall to `body` by the focus fixup rule (inferred). Recommendation: keep Yeti's `{ once: true }` listener. It is registered on the parent, owned by no directive, and removes itself when it fires. The spec names it as the one exception to 1.15's rule. Layer 2 asserts that the attribute is gone after the next `blur`, even with the directive destroyed. To overrule: hold the listener in a root service that removes it on application destroy, or accept a permanent `tabindex="-1"` and record it in the spec. Decided 2026-10-03 in ticket 50, decision 102 (orchestrator, full AFK mode).
4. **`event.defaultPrevented` and a veto** (spec section 2 Module replaced, section 4 handler step 1; MEDIUM impact, MEDIUM confidence). `alert.js:6` returns when a page listener has already prevented the click. In Angular, a directive's host listener is registered when the element is created, before the template's own `(click)` on the same element, so it runs first. A consumer's `(click)="$event.preventDefault()"` would then not stop it (inferred from the order of creation, not measured). Recommendation: keep the check as like-for-like, because a capture-phase or ancestor listener can still use it. Add no predicate input: building-blocks 1.4 adds one "where a consumer must veto a close", and a consumer here can decline to remove the alert on `closed`. Usage rule 6 already says to write `yetiAlertClose` only on an alert you remove. Layer 2 tests the capture-phase case. To overrule: add a `closePredicate`-like input after Material's dialog, checked before the focus move. Decided 2026-10-03 in ticket 50, decision 103 (orchestrator, full AFK mode).
5. **No public `close()`** (spec section 4; LOW impact, HIGH confidence). Building-blocks 1.3 gives methods Material's names, and events rule 9 says a public `close()` emits. But no record gives the alert a method, and a consumer can remove an alert through its own state. Recommendation: no public method. The part makes the root emit through `yetiAlertToken` with an internal member. Adding `close()` later is not breaking. To overrule: add `close()` on `YetiAlert` that runs handler steps 2 to 4, and a layer-2 case. Decided 2026-10-03 in ticket 50, decision 104 (orchestrator, full AFK mode).
6. **Announcing an alert inserted with its role** (spec section 7 "Announcement on insertion", usage rule 2, layer 4; MEDIUM impact, MEDIUM confidence). The APG says dynamically rendered alerts are announced by most screen readers (`alert-pattern.html:24`). Material's snack bar avoids live roles and moves its content into the live region after a delay, citing NVDA and JAWS (`snack-bar-container.ts:127-128`, `:357`). So an inserted `role="status"` may not be announced reliably. The records keep the role the consumer's static attribute and refuse `LiveAnnouncer` (Part 2 row 23; ADR 0043 point 4). Recommendation: no code. Keep Yeti's documented form in every example (the role on the inserted alert). Add a manual release check with two screen readers for an inserted `status` and an inserted `alert` (ADR 0015 point 7). If the check fails for `status`, add a ledger row and a usage rule: keep a `role="status"` container rendered and insert the alert inside it. To overrule now: adopt that usage rule from the start. Decided 2026-10-03 in ticket 50, decision 105 (orchestrator, full AFK mode).
7. **`type="button"` on the close button** (usage rule 5; LOW impact, HIGH confidence). Yeti's markup writes it, and no record gives it to a directive. Recommendation: a usage rule only; the directive binds no `type`. To overrule: a static host attribute `type: 'button'` on `YetiAlertClose`, with a layer-3 assertion. Decided 2026-10-03 in ticket 50, decision 106 (orchestrator, full AFK mode).

## Answer

Resolved 2026-10-03 by Claude Opus 5.5. Spec: [specs/alert.md](../specs/alert.md).

Two directives in `ngx-yeti/alert`. The item directive `YetiAlert` on `[yetiAlert]` (`exportAs: 'yetiAlert'`) binds the static class `alert`, the presence attribute `data-ngx-yeti-item-alert`, and `data-variant` and `data-emphasis` from `YetiVariant` and `YetiEmphasis` inputs. It acquires the `alert` item file and declares the `void` output `closed`. The part directive `YetiAlertClose` on `button[yetiAlertClose]` binds the static `data-close`. Its click handler moves focus to the alert's parent with a temporary `tabindex="-1"`, as `alert.js` does, then makes the root emit `closed`. Removal is the consumer's `@if` or `@for` with a class-form `animate.leave`, which replaces `alert.js`'s fade and removal and avoids upstream bug Y1. The live role stays the consumer's, with no `LiveAnnouncer`. No ledger row.

Counts: 54 user stories, 13 usage rules, 10 story ids, 7 open points. Open point 1 has HIGH impact and MEDIUM confidence, so it is in the trap quadrant and is recorded with its options above. It contradicts the brief's "after the transition", because under Part 2 row 23 the transition follows `closed`. No open point blocks the spec: it carries each recommendation as its reading.
