## Question

What is the Angular API of Yeti's `nav` component, and what does its spec say? Its decisions are already made in the records: its row in `building-blocks.md` Part 2 (and the "Aria decisions" section where it applies), its rows in [Decide: how the package maps each of Yeti's `data-*` attributes](26-decide-yeti-data-attributes-mapping.md), its item file under [ADR 0060](../adr/0060-item-styles-are-counted-links-to-the-consumers-yeti-build.md), its ledger rows, and the shared specs it links to.

## How to work it

Write `specs/nav.md` with the `/to-spec` template and the map's Spec shape note, from the records only. The spec decides nothing a record has not decided. Anything it needs and no record settles goes under the ticket's `### Open` for the orchestrator. Append an `## Answer` that links the spec.

### Open

Each point is written into the spec as its best reading and marked "(open: see ticket)". Impact and confidence are rated as the map's trap-quadrant ruling asks. Points 1 and 3 are trap-quadrant points (HIGH impact, MEDIUM confidence) and carry their options records.

1. **`isOpen` against a parent's binding, parent writes, and the methods** (spec section 4, Open state points 2, 4, and 5; HIGH impact, MEDIUM confidence; trap quadrant).
   - **Question.** Part 2 row 34 gives the nav an `isOpen` model, `opened`, and `closed`; the open-state ruling says the state is read once and followed, never bound. No record says which wins at the first render when `[(isOpen)]` disagrees with the list, what a later parent write does, or whether the nav has methods. The same question is the [dialog](../specs/dialog.md) spec's open point 1 ([ticket 81](81-spec-dialog.md)).
   - **Option A (recommended): as the dialog spec reads it.** The element wins at the first render; `isOpenChange` emits only when the read differs from the bound value; `opened` does not emit. Later parent writes are commands (`showPopover()`, `hidePopover()` in an `afterRenderEffect`) with no `isOpenChange`; `opened` and `closed` follow every change. `open()` and `close()` exist, as on the dialog. Approved because it keeps a pre-hydration open (the harm the ruling exists for), keeps the parent's state equal to the list's, and makes the two top-layer items behave alike. ADR 0041 point 1 already speaks of the panel's "close method".
   - **Option B: the parent's initial value wins after the first render.** Dismissed: a list the user opened before hydration under a parent bound `false` would be closed by the package at hydration.
   - **Option C: a read-only signal plus outputs, no model, no methods.** Dismissed: Part 2 rows 32 and 34 and the navigation-close spec's table name an `isOpen` model.
   - **Option D: A without `open()` and `close()`.** Viable, because the model covers programmatic control and adding methods later is not breaking; dismissed only for consistency with the dialog.
   - **Evidence and confidence.** The ruling (map); ticket 34 (a bound `open` undoing a pre-hydration toggle, measured on `details` and `dialog`); `model()` semantics (read). Not measured for a popover; the spec's layer-2 and layer-4 cases measure it. MEDIUM because no record covers the binding case.
   - **To overrule.** For B, change Open state point 2 and add a usage rule that a bound `isOpen` starts `false`; for D, remove the methods from sections 4 and 5 and the `nav--model` story's buttons. Whatever ticket 81 point 1 decides should apply here unchanged. The [dropdown](../specs/dropdown.md) spec, written in parallel, reads a pre-hydration open as emitting no `isOpenChange` at all (its section 10), which is the dialog's option C; the three items should be aligned in one decision. Decided 2026-10-03 in ticket 50, decision 91 (orchestrator, full AFK mode).
2. **Where the popover's open state is read** (Open state point 1; MEDIUM impact, MEDIUM confidence). The dialog reads its `open` attribute at creation. A popover has no attribute: its state is only `:popover-open`, and on the server the list is always closed. Reading `matches(':popover-open')` at construction would run on the server's DOM, whose selector support for the pseudo-class was not checked. Recommendation: the model starts `false`, and the list part reads the live `:popover-open` once in `afterNextRender`; every `toggle` handler reads the live state, never `newState`, so a replayed `toggle` cannot disagree. The [dropdown](../specs/dropdown.md) spec reads it the same way (its section 4 item 7). To overrule: read at construction, after checking that the server DOM accepts the selector, and add a layer-3 case. Decided 2026-10-03 in ticket 50, decision 91 (orchestrator, full AFK mode).
3. **The focus-out boundary: the list and the toggle, or the whole root** (spec section 4, Focus-out close; HIGH impact, MEDIUM confidence; trap quadrant).
   - **Question.** ADR 0016 point 2 fixes the behaviour: a panel closes "when focus moves outside both the panel and its invoker". ADR 0043 point 1 fixes the building block: a `focusout` host listener on the root that closes "when `event.relatedTarget` is outside the root", because the root "contains both the opener and the panel (`.dropdown`, `.nav`)". For the dropdown the two are the same; the nav's root also holds the brand and the actions. Under the root rule, Tab from the last link to an action, or Shift+Tab from the toggle to the brand, leaves a drawer or screen panel open over the control that took focus.
   - **Option A (recommended): listener on the root, condition against the list and the toggle.** Approved: it keeps ADR 0043's building block and ADR 0016's behaviour, matches the APG example, whose region is each disclosure's button and list (`disclosureMenu.js:87-92`), and closes the case A11Y-3b is about.
   - **Option B: the root, literally.** Dismissed: a panel stays over the actions and the brand, which a drawer or a screen covers. It passes WCAG 2.4.11 only through the criterion's note on content the user opened (Escape reveals the control), which A11Y-3b exists not to rely on.
   - **Option C: listeners on the list and the toggle instead of the root.** Dismissed: two listeners and two guards for the same result as A.
   - **Evidence and confidence.** The two records' texts (read); the geometry of `drawer` and `screen` (`nav.css:148-173`, read); ticket 29's variant A closed the nav sheet on focus-out in three engines, but its boundary was not recorded. MEDIUM because the records disagree in wording.
   - **To overrule.** For B, change the condition in section 4, turn the `nav--focus-out` story's actions case to "stays open", and amend A11Y-3b's "What the package adds". Either way, add a dated note to ADR 0043 saying which boundary the nav uses. Decided 2026-10-03 in ticket 50, decision 167 (orchestrator, full AFK mode).
4. **`pointerdown` is replayed** (spec section 10, Event replay; section 4, Focus-out close; MEDIUM impact, HIGH confidence). The coordinator relayed the [dialog](81-spec-dialog.md) spec's finding (ticket 81 point 9): `'pointerdown'` is in `BUBBLE_EVENT_TYPES` at `packages/core/primitives/event-dispatch/src/event_type.ts:335` (re-read here in the Angular clone at `5db6fc4453`), against ADR 0043's note of 2026-10-03, which predicted that a pre-hydration press on panel content closes the panel at replay. Recommendation: keep the guard, and make it a one-shot flag that the next `focusout` consumes and a zero-delay timer clears, not a "same task" check, because replay may dispatch the queued events in one synchronous loop (inferred). The stated residue becomes "the list stays open, as it does live" (inferred). Layer 4 adds two pre-hydration cases in three engines: a press on the panel's padding (stays open) and a press followed by Tab out of the nav (closes). The orchestrator's dated note on ADR 0043 should cover the nav and the dropdown; the [dropdown](../specs/dropdown.md) spec keeps the "same task" form (its section 4 items 2 and 3), so one guard form should be chosen for both. Building-blocks 1.11 clause 5 also calls `pointerover` and `pointerout` non-replayed; both are in the same list (`event_type.ts:339-340`). That is the `dropdown` spec's concern, not the nav's. Decided 2026-10-03 in ticket 50, decision 92 (orchestrator, full AFK mode).
5. **Focus after a navigation close** (section 4, Closing on navigation; MEDIUM impact, MEDIUM confidence). ADR 0041 point 4 has the nav add `focus()` on the opener where `hidePopover()` does not restore it. Recommendation: the close path focuses the toggle only when focus was inside the list and is afterwards on `body` or still inside the hidden list, so the call does nothing where the platform restored focus. Layer 4 first records the platform's behaviour with the call disabled. To overrule: always focus the toggle, or never, if layer 4 shows the platform restores it in all three engines. Decided 2026-10-03 in ticket 50, decision 168 (orchestrator, full AFK mode).
6. **Arrow keys** (section 7, keyboard table; LOW impact, HIGH confidence). ADR 0019's considered options leave "optional arrow-key movement between top-level buttons" to this spec. Recommendation: none in the first milestone. Yeti has none, the APG makes them optional, ticket 29's variant A met the APG pattern without them, and a nav's top level is mostly links, not buttons. Adding them later is not breaking. Decided 2026-10-03 in ticket 50, decision 169 (orchestrator, full AFK mode).
7. **`threshold="2xs"` has no rule in `nav.css`** (section 1; LOW impact, HIGH confidence). The `width` vocabulary has `2xs` (12rem), and `attributes.css:163` maps it, but `nav.css` has `@container` blocks for `xs` to `2xl` only (`:239-280`), so a `2xs` nav keeps its links behind the toggle at every width (read). `card.css` (`:144-264`) and `pagination.css` (`:43-63`) also have no `2xs` block; `cluster` and `grid` have one. Recommendation: keep `YetiWidth` (the contract check requires the manifest's vocabulary), state the behaviour in the input's JSDoc, and add an `upstream-bugs.md` Yeti row with the next free id: "nav, card, and pagination have no `2xs` threshold rule"; verified *read*; no minimal reproduction; not filed (filing needs the user's confirmation). Decided 2026-10-03 in ticket 50, decision 93 (orchestrator, full AFK mode).

A11Y-22 is owned by `sidebar` and shared with `stack` and `shell`; [ticket 50](50-decide-open-points-of-the-specs.md) decision 48 already applies it to "a page-top bar that sticks above the whole shell", which is a sticky nav. Recommendation: add `nav` to the row's sharers (Item cell "sidebar (shared with stack, shell, and nav)"), with usage rule 9 and the layer-4 Shift+Tab walk as in decision 48. No package CSS. Decided 2026-10-03 in ticket 50, decision 170 (orchestrator, full AFK mode).
9. **A11Y-3b's "Verified" cell** (section 7; LOW impact, HIGH confidence). The row says *inferred* ("from the dropdown measurement; not run for nav"). Ticket 29's README measured, in three engines, Yeti's reference nav sheet staying open on focus-out and variant A (this row's shape) closing it. Recommendation: change the cell to *measured* (ticket 29) and "Tested by" to L1, L2, L4. Decided 2026-10-03 in ticket 50, decision 171 (orchestrator, full AFK mode).
10. **Marker parts' injection** (section 3; LOW impact, HIGH confidence). Part 2 row 34 calls `yetiNavBrand`, `yetiNavActions`, and `yetiNavClose` "static". Recommendation: inject `yetiNavToken` with `{ optional: true, skipSelf: true }` and read nothing, as the `breakout` spec's `YetiBreakoutNote` does, so a later in-item check has its link. To overrule: inject nothing; nothing changes at run time. Decided 2026-10-03 in ticket 50, decision 172 (orchestrator, full AFK mode).
11. **`type="button"` on the toggle and the close button** (usage rule 4; LOW impact, HIGH confidence). Yeti's markup writes it and no record gives it to a directive. Recommendation: a usage rule only, as the alert spec's point 7 has it; inside a `form` a toggle without it would submit. To overrule: a static host attribute `type: 'button'` on both parts and a layer-3 assertion. Decided 2026-10-03 in ticket 50, decision 173 (orchestrator, full AFK mode).

## Answer

Resolved 2026-10-03 by Claude Opus 5.5. Spec: [specs/nav.md](../specs/nav.md).

Seven directives in `ngx-yeti/nav` on Yeti's disclosure markup. `YetiNav` on `nav[yetiNav]` binds the class `nav`, the presence attribute, and `data-variant`, `data-threshold`, `data-panel`, `data-gap`, and `data-sticky` from `YetiVariant`, `YetiWidth`, `YetiPanel`, `YetiGap`, and `boolean` inputs. It provides `yetiNavToken`, loads the item file, and owns the `isOpen` model, the void Completion outputs `opened` and `closed`, `open()` and `close()`, the focus-out close (A11Y-3b), and closing on navigation. `YetiNavList` renders the list's `popover` and its `id` through `injectYetiId('nav')`; `YetiNavToggle` and `YetiNavCloseButton` bind `popovertarget` to it; `YetiNavClose`, `YetiNavBrand`, and `YetiNavActions` set the markers. No Aria pattern is hosted (ADR 0019; the user's choice). The spec maps every behaviour of Yeti's module-less nav to the platform or the package, and covers the rendering modes, the hydration constraints, and the four test layers with 12 story ids.

Counts: 60 user stories, 16 usage rules, 12 story ids, 13 open points. Points 1 and 3 have HIGH impact and MEDIUM confidence, so they are in the trap quadrant and carry options records above. Point 4 answers the coordinator's message about the replayed `pointerdown`. No open point blocks the spec: it carries each recommendation as its reading.
