## Notes

### Domain

Yeti (https://github.com/foundation/yeti, `develop` branch; docs at https://www.foundationcss.com/yeti/) is the successor to Foundation for Sites. Its README describes "a CSS-first, native, zero-build layout and styling framework": one stylesheet, no Sass, cascade layers, container queries, runtime `--yeti-*` tokens, and optional JavaScript modules. Its README says it targets Baseline 2025, and its stability guide (`src/guides/stability.md`) lists what `7.0.0-beta` froze. The Angular package wraps Yeti's CSS and attribute contract and replaces or complements its optional JavaScript; which of those it does is decided here.

The user ruled Yeti's FSL-1.1-MIT licence compatible with this package as a free and open-source MIT project ([ADR 0001](adr/0001-yeti-licence-compatible-with-mit-package.md)). Yeti's announcement (foundation/yeti#15554) says of `develop`, "unstable until the beta. Do not build on it yet." The user ruled on readiness, verbatim: "Readiness: We will spec and build against a specific commit of `foundation/yeti`'s `develop` branch." Which commit, how the pin moves, and how the package depends on unpublished Yeti are decided in [Decide: which Yeti version the specs target, and how the package tracks it](issues/12-decide-yeti-version-policy.md).

### Inherited preferences and rulings (decided 2026-10-01, [Decide: which standing preferences and user rulings carry over](issues/07-decide-inherited-preferences-and-rulings.md))

Each record below was triaged from `.scratch/next-foundation-specs/`; that bundle binds nothing, and these lines are what binds. The ticket's table holds the per-record reason and the nine abandoned records. Where a line adapts a user ruling, the ruling's own words are quoted and the adaptation is this map's, not the user's.

- **Directives first.** Every Yeti item is attribute directives on the markup the consumer writes. A component only where a part needs generated structure, or where a `styleUrl` is what makes lazy styles meet the requirements under the user's standing ruling 28 ([ADR 0003](adr/0003-directives-set-yetis-class-attributes-and-markers.md); adapted from the old ADR 0001 (`directive-first-with-named-exceptions`)).
- **Composition over subclassing.** The package reuses and extends behaviour through `hostDirectives` and directives placed beside each other, and never asks a consumer to extend a package class (the user's rule, 2026-09-27, carried over as it reads).
- **Implementation order.** Native platform feature, then `@angular/aria`, then `@angular/cdk`, then custom Angular. Each spec says which level it stopped at and why. Most Yeti items stop at level 1, because Yeti is platform-first; the user's standing ruling 37 sets levels 2 and 3 for what the platform leaves. Where the planning repository's `AGENTS.md` (ngx-foundation-sites-next) puts `@angular/aria` first, this order wins: replacing a working native element with an Aria pattern would change Yeti's semantics.
- **The contract the package manages.** One class per item, bound as a static host class; every `data-*` attribute and marker set from a typed input; every `yeti:*` event an `output()`, because a template cannot bind a colon-named event; state left native, except state that changes before or after hydration, which is Angular's; and the platform's opening attributes (`popovertarget`, `commandfor`, `command`, `popover`) rendered with generated ids so they work before any script. A consumer writes elements and directive attributes, and no Yeti class or attribute ([ADR 0003](adr/0003-directives-set-yetis-class-attributes-and-markers.md); adapted from the old ADR 0039 (`directives-manage-every-foundation-class`), the user's class rule of 2026-09-27).
- **Typed values.** Each input's type is a closed union of its vocabulary's values, from Yeti's frozen `schema/vocabulary.json`; a misspelt value fails to compile. No registry, no declaration merging, no generator, no sync check: Yeti has no setting that generates a value ([ADR 0005](adr/0005-closed-unions-from-yetis-vocabularies.md); adapted from the old ADR 0040 (`variant-input-types`)).
- **Input naming.** From Yeti's attribute and marker names in camelCase (`data-variant` to `variant`). An input named like an HTML presentational attribute keeps that name and its directive owns what the static attribute renders, stated per spec as output, removed, insertion, or inert (carried over from old map ticket 139 (`decide-inputs-named-like-presentational-attributes`)). Every directive and component has an `exportAs` (the user's ruling, 2026-09-29, carried over). A class-name prefix and the camelCase `...Token` form for injection tokens carry; the prefix itself is set with the glossary.
- **State and reactivity.** Signals for state, `model()` for two-way state, `linkedSignal` for derived-but-writable, OnPush, zoneless-safe, SSR-safe.
- **Tokens.** Yeti's `--yeti-*` tokens are a consumer stylesheet surface, not a per-component input contract: each spec names the tokens its item reads and how a consumer sets them, and the package offers no input per token and no theme provider. Two exceptions: a token a Yeti module writes as state becomes a host style binding from a `computed` (`--yeti-range-value`), and a spec may expose one derived token as an input where its API needs it, saying why. The package does not ship or wrap Yeti's theme files ([ADR 0004](adr/0004-yeti-tokens-are-a-consumer-stylesheet-surface.md); adapted from the old map's runtime-theming exclusion).
- **Accessibility.** Every directive and component meets WCAG 2.2 AA, follows the matching WAI-ARIA APG pattern, and is axe-clean on the stated rule set; never a recommendation. Each spec names the criteria its item touches and how each is met. Every gap the package closes that Yeti leaves open is a row in `ledger.md` (the user's standing ruling 36). The package may add CSS of its own where Yeti's CSS is what fails: the user ruled "Accessibility CSS: Yes." on 2026-10-02 (Standing rulings, Package CSS for accessibility), settling ticket 07's `OPEN FOR HUMAN` item.
- **Animation.** No `@angular/animations` and no JavaScript-timed animation. Yeti's own CSS transitions, `@starting-style`, and `enter` utility do the work; `animate.enter` and `animate.leave` where an element enters or leaves the DOM, in the class form only, because a function-form `(animate.leave)` listener anywhere keeps a component's styles loaded (angular/angular#66244).
- **Rendering modes.** Every directive and component is specified for `@defer` with its hydrate triggers, SSR, prerendering, full and incremental hydration, event replay, and `withI18nSupport()`. Each spec states its server output, what it must not touch before hydration, which events replay, and how it behaves in a deferred and a `hydrate never` block.
- **Lazy styles.** A library-wide requirement, carried over from the user's ruling of 2026-10-01: a first-milestone directive or component loads its item's styles when its first instance renders and unloads them after the last. The unit is one of Yeti's 49 item files rather than a Sass export mixin's output, and a library `styleUrl` is no longer ruled out. The mechanism, the exceptions, and what the consumer writes are [Decide: how component styles load and unload](issues/13-decide-style-loading.md)'s.
- **The always-loaded group.** Yeti's layer statement, tokens, reset, base files, and `layouts/attributes.css` are loaded globally and are not specified: they style bare HTML and declare every token, and 40 of the 49 item files render differently without them. No directive manages them; a spec that relies on one of their rules cites it.
- **Testing.** Four layers: story play functions with interaction tests, a browser-level layer, a node-level layer with the SSR smoke, and Playwright e2e. Three additions for Yeti, which the testing decision places: Yeti's own `bin/validate.js` and `bin/frozen.js` against the pinned commit, an attribute-and-value check against the built manifest, and testing at the target's floor browsers ([Research: testing at the browser floor](issues/27-research-testing-at-the-browser-floor.md)).
- **Release policy.** In 0.x (the user's rulings of 2026-10-02, Standing rulings, Version format and Breaking changes in 0.x; [ADR 0017](adr/0017-release-policy-with-a-pinned-yeti.md)'s 2026-10-02 notes): the version is `0.<Angular major><Angular minor, two digits><breaking counter, two digits>.<patch>-yeti.<Yeti version>.g<Yeti commit SHA>`; any release may break, and a breaking release bumps the counter; a removal still needs a `@deprecated` release before it, a changelog entry, and a migration where one can be written, but it does not wait for an Angular major; a pin move that changes only unfrozen defaults may land in any release. Migrations are Nx migrations first, reused for `ng update` (the user's ruling, 2026-09-28, carried over). The carried-over devkit rule (`0.<Angular major><Angular minor, two digits>.<patch>`; breaking changes, removals, and consumer-visible platform upgrades only when the Angular major changes; one Angular major of deprecation before a removal) returns at 1.0. What a Yeti pin move does to the version is settled by [Decide: which ADRs carry over](issues/08-decide-inherited-adrs.md) and [Decide: which Yeti version the specs target, and how the package tracks it](issues/12-decide-yeti-version-policy.md).
- **Milestones.** Every check is specified but planned and implemented in a later milestone of the implementing repository; no other spec depends on one, names one, or links to a deferred spec, and each states the rule a check enforced as documented usage. The user's reasons, 2026-09-29: "all checks should be deferred to a later milestone because at the core of it, this is an issue Angular should correct, not 3rd-party Angular component libraries", and "I want to keep the initial milestone simpler and smaller in scope". Entry points export directive classes and no import arrays (the user's ruling, 2026-09-28). Which checks Yeti leaves worth deferring at all is settled by [Decide: which ADRs carry over](issues/08-decide-inherited-adrs.md) and [Decide: which architecture principles and building-blocks rules carry over](issues/09-decide-inherited-principles-and-building-blocks.md).
- **Scope shape.** Being CSS-only never excludes an item: an Angular directive is the Angular-native way to use a UI component even when all it adds is a class, typed inputs, and generated ids (the user's ruling, 2026-09-27). One spec per item of Yeti's own manifest, which is also its docs page; [Decide: the spec list](issues/11-decide-spec-list.md) reconciles the 49 items against 50 docs pages and 72 sitemap URLs. An item the first milestone leaves out relies on the consumer's loaded stylesheet rather than on a spec, in the shape of the user's later-milestone ruling of 2026-09-30. A mechanism Yeti itself has replaced is out of scope, as the Float and Flex Grids were for Foundation.
- **Design criteria.** Each directive or component is the best combination of: Yeti's CSS, attribute contract, and manifest (its `a11y` and `support` blocks included); the APG, WAI-ARIA, WHATWG HTML, and platform features; Angular Aria and CDK; Material-equivalent accessibility and API shape for the nearest Material component; and modern DI patterns.
- **Spec shape.** A `/to-spec` spec whose Implementation Decisions and Further Notes carry the API-design subsections, with two substitutions: the class mapping becomes a contract mapping (class, each attribute and marker with its input and type, each event with its output, each token the spec names), and the Sass subsection becomes the item file and how it loads. The `foundation-api-design` skill is one input the user called an early sketch; this bundle's ADRs and the user's rulings outrank it. Two further departures from `/to-spec` are deliberate (noted 2026-10-03, audit 0004 L10): Implementation Decisions keep their `file:line` citations and short code, because they are what makes each spec checkable against its sources; and no spec or spec ticket carries the `ready-for-agent` label, which is left to the implementing repository's tracker.
- **Precedence.** `architecture-guide.md` restates these records as testable principles and ranks below all of them; a conflict is settled by the record, never by the guide. The planning repository's `AGENTS.md` (ngx-foundation-sites-next) is one design-criteria input, neither a source nor a constraint, and its component code is not a source either. Spec Kit is not used.
