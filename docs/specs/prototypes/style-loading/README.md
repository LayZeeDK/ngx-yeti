# Prototype: item styles as counted `<link>`s to the consumer's own Yeti build

Ticket: [13. Decide: how component styles load and unload](../../issues/13-decide-style-loading.md). Built and measured 2026-10-02 by Fable 5.1. **Throwaway code.** The decision it supports is [ADR 0060](../../adr/0060-item-styles-are-counted-links-to-the-consumers-yeti-build.md).

Each claim is labelled **measured** (run in a browser or a build here), **read** (from source, with a path), or **inferred** (follows from the measured or read facts, not run).

## Question

Can the package load and unload each Yeti item's CSS lazily **without shipping or inlining Yeti's CSS**, from a build of Yeti the consumer brings at the pin, and still meet the requirements: server HTML and hydration with no unstyled frame, incremental hydration (`hydrate on ...`, `hydrate never`), client-only `@defer`, unloading after a class-form `animate.leave` while a function-form `(animate.leave)` listener is elsewhere on the page (angular/angular#66244), Yeti's tie order inside a layer, relative URLs under a non-root `<base href>`, cache busting, and no consumer TypeScript?

Second question (added by the orchestrator on 2026-10-02): when the package's input types import Yeti's exported vocabulary types from `yeti.d.ts`, what happens in a consumer whose `yeti-css` has no types file?

Production builds, `outputHashing: all`, `outputMode: server`, `provideClientHydration()` (which in 22.2 includes incremental hydration and event replay), zoneless.
- **Library** `projects/yeti-lib` ([`workspace/lib/`](workspace/lib/)): no `styleUrl`, no CSS. `rg 'yeti\.components|\.card\{' dist/yeti-lib/fesm2022/*.mjs` finds nothing (measured).
  - [`yeti-styles.ts`](workspace/lib/yeti-styles.ts): `YetiStyles`, a root service that owns one reference-counted `<link rel="stylesheet">` per item file. `href` is `<url><kind>/<name>/<name>.css?v=<pin>` with `url` defaulting to `yeti-css/`, relative to `<base href>`. Attributes: `data-ngx-yeti-styles="<item>"`, `data-ngx-yeti-app="<APP_ID>"`, `data-beasties-skip`, and `nonce` from `CSP_NONCE` when present. Inserted before the first existing item link that comes later in Yeti's `yeti.css` order (ticket 23's P2). Written on the server; adopted at client bootstrap by attribute. Removed in the animation frame after the last live instance has released it **and** no element carrying `data-ngx-yeti-part="<item>"` is connected; a `MutationObserver` on the document schedules that check. `provideYetiStyles({ url?, preload? })` configures it; `preload` writes `<link rel="preload" as="style">` for the named items (in the probe only when the URL carries `?preload=1`, so one build measures both).
  - [`parts.ts`](workspace/lib/parts.ts): the 49 items, their file paths, and their rank, generated by [`measure/gen-parts.mjs`](measure/gen-parts.mjs) from `yeti-css/css/yeti.css` at the pin.
  - [`directives.ts`](workspace/lib/directives.ts): `[yetiCard]`, `[yetiBadge]`, `[yetiAlert]`, `[yetiStack]`, `[yetiCenter]`. Each sets its Yeti class and `data-ngx-yeti-part="<item>"` as static host attributes, acquires its item in the constructor, and releases it on `DestroyRef`. `YetiStack` has `gap = input<YetiGap>()` with `import type { YetiGap } from 'yeti-css'`, for the types question.
- **App** ([`workspace/app/`](workspace/app/)): `baseHref: "/sub/"`; one `assets` entry `{ "glob": "**/*.css", "input": "node_modules/yeti-css/dist/css", "output": "yeti-css" }` (66 files copied, measured); `styles.css` is Yeti's always-loaded group as 16 `@import 'yeti-css/css/...'` lines plus a probe-only `.leaving` transition; `server.ts` serves the browser folder under `/sub`. The page ([`app.ts`](workspace/app/app.ts)): a permanent `(animate.leave)` function-form listener (L3); an eager card under `@if` with `animate.leave="leaving"` (400 ms); a bare `class="card"` probe without a directive; an eager badge under `@if`, a badge in `@defer (hydrate never)`, a badge in `@defer (hydrate on interaction)`; an alert in a client-only `@defer (on interaction(trigger))`; a center, and a stack with a center inside it under `@if`.

- **Measurement** ([`measure/probe.mjs`](measure/probe.mjs)): per engine, a JavaScript-off load; then a load with every `**/yeti-css/**` response delayed by `CSS_DELAY` ms (300 and 0), an init script that records every `requestAnimationFrame` tick's computed padding for the elements of interest and every `<style>`/`<link>` added or removed, and the steps: hydration, comparison of the card and badge against the same markup under Yeti's full `dist/yeti.css` (every computed longhand of every element and pseudo-element), leave, reload, hold, tie, client-only `@defer`, then the same `@defer` with the preload on. ### Side finding: Angular's inlined critical CSS drops six of Yeti's nine `:root` token blocks (measured)

With the global stylesheet blocked ([`measure/debug-critical3.mjs`](measure/debug-critical3.mjs), [`results/critical-root-blocks.txt`](results/critical-root-blocks.txt)), Chromium and Firefox parse 4 and 3 of the 9 `:root{...}` blocks the inlined critical `<style>` contains as text. The dropped ones start with `--yeti-white`, `--yeti-duration-fast` (twice, inside `@media (prefers-reduced-motion: reduce)`), `--yeti-border-width`, `--yeti-button-radius` (the whole `tokens/components.css` block, `--yeti-card-padding` included), and `--yeti-spinner-duration`. So a server-rendered item paints with its item file applied but its component tokens unset until the async `styles-*.css` arrives: `padding: var(--yeti-card-padding)` computes to 0 px. On localhost Chromium and WebKit painted after the sheet had loaded; Firefox painted first-contentful-paint at 305 ms with the sheet still pending ([`results/firefox-paint.txt`](results/firefox-paint.txt)), which is its 1 to 2 "unstyled" frames above. The cause of the drop (the text looks balanced; it follows blocks holding `oklch(from ...)`, `color-mix()`, and a `url("data:image/svg+xml,...")`) was not pinned down. It is independent of the loading mechanism: a `styleUrl` part reads the same tokens.

## Verdict

A library-owned counted `<link>` per item file, pointing at the consumer's own Yeti build served as an application asset, meets every requirement measured here in three engines, with two costs: a client-only `@defer` block fetches its item's CSS on construct (closed by the consumer's `preload` list, measured at 0 frames), and WebKit refetches a re-inserted link on reload (1 frame from cache). The package ships no Yeti CSS. The consumer writes one `assets` entry and the always-loaded group. The types question is settled: an unresolvable `yeti.d.ts` silently widens every input type to `any`, so the package must not depend on the consumer's build for its types. Nothing here is decided; [ADR 0060](../../adr/0060-item-styles-are-counted-links-to-the-consumers-yeti-build.md) decides.

## Not measured

- `ng serve` and HMR, a strict CSP, two applications on one document, prerendering, Nx's workspace-package symlink under the `assets` glob, Yeti's `enter` utility arriving late, the Baseline 2025 floor browsers, the LCP cost of render-blocking item links on a slow network (ticket 190 measured it for Foundation's bundles), and the cause of the dropped `:root` blocks.
