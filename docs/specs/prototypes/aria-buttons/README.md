# Prototype: Angular Aria Toolbar for the `buttons` group

Ticket: [29. Prototype: Angular Aria for the four items that keep a native pattern](../../issues/29-prototype-aria-for-the-native-pattern-items.md), item `buttons`. Built and measured 2026-10-02 by Claude Opus 5.5. **Throwaway code.** Nothing here is decided.

## Question

If the `buttons` group is built on Aria Toolbar (`ngToolbar` on the group, `ngToolbarWidget` on each `button`) instead of ticket 25 row 27's `role="group"` (ledger A11Y-12), do Yeti's `buttons.css` and `button.css` still apply unchanged with no package CSS? Does anything Aria adds (roving tabindex, arrow keys, wrap, orientation, its host attributes) conflict with Yeti's button states (`aria-pressed` toggles, busy, disabled)? And what does it cost in the rendering modes (ADR 0011) and in accessibility?

Yeti has no buttons module (`buttons/manifest.json` `"js": null`), so point 2 asks what Aria adds, not what it replaces.

## Findings

1. **measured** The toggle set (`aria-pressed`, `data-affix`) and the plain action buttons render identically in (A), (B), and Yeti's example in all three engines: every computed property compared and every `.button`-bearing selector matched the same way. Aria's `role`, `tabindex`, `aria-orientation`, `id`, `data-active`, and `ngtoolbarwidget` attributes change nothing Yeti keys on.
2. **measured** and **read** The one conflict is `aria-disabled`. `ngToolbarWidget` always binds `[attr.aria-disabled]` to its own `disabled` input (`NC/src/aria/toolbar/toolbar-widget.ts:55`), which renders `"false"` when not disabled. A Yeti busy button carries `aria-disabled="true"` (`Y/src/components/button/button.css`, busy comment). Both a static `aria-disabled="true"` and the sketched `yetiButton`'s binding were overwritten to `"false"` in server HTML and after hydration. Consequences, measured: Yeti's disabled rule stops matching (cursor and hover differ), the busy button is announced as enabled, and axe reports `color-contrast` on it. The composition that works is `ngToolbarWidget [disabled]="busy"` with `aria-busy` beside it: the probe's "Aria-disabled busy" member rendered `aria-disabled="true"`, matched Yeti's disabled rule, was `[disabled]` in the tree, and stayed focusable (`softDisabled` defaults to `true`, `NC/src/aria/toolbar/toolbar.ts:84`). So a package `yetiButton` used inside a toolbar would have to route busy through Aria's `disabled` input instead of binding `aria-disabled` itself.
3. **measured** A static `role="group"` written on the `ngToolbar` element wins over Aria's host `role: 'toolbar'` (`toolbar.ts:49`), and Aria still writes `aria-orientation`, which axe flags as not allowed on `group`. A static `tabindex="0"` on a widget is overwritten to `-1` (`toolbar-widget.ts:52`). A consumer moving from (A)'s markup to (B) must remove the `role` they wrote.
4. **measured** and **read** In server HTML every widget and the toolbar have `tabindex="-1"`. The default active item is set by `afterRenderEffect(() => setDefaultStateEffect())` (`toolbar.ts:103`), which never runs on the server, and `getItemTabIndex` returns `0` only for the active item (`NC/src/aria/private/behaviors/list-focus/list-focus.ts:86-94`). So with JavaScript off, before hydration, and inside `@defer (hydrate never)`, the toolbar's buttons cannot be reached from the keyboard at all. (A)'s native buttons stay reachable in all three. This is the rendering-modes cost of (B).
5. **read** Aria handles only arrows, Home, and End (`NC/src/aria/private/toolbar/toolbar.ts:117-121`); Space and Enter remain the native button's, so toggling and submitting are unaffected. It has no notion of `aria-pressed` (no match for `pressed` in `NC/src/aria/toolbar/*.ts` other than the testing harness), so the toggle script Yeti's docs leave to the page is still needed in (B), exactly as in (A). `wrap` defaults to `true` (`toolbar.ts:90`); `orientation` defaults to `horizontal` (`toolbar.ts:78`), with RTL key swapping (`private/toolbar/toolbar.ts:82-94`).
6. **measured, a race** The roving `tabindex` is written by change detection after the keydown, not inside it. In the probe, Shift+Tab pressed right after an arrow key sometimes went to the member the arrow had just left (Chromium in both runs, WebKit in one, Firefox in neither; a separate loop reproduced it in 2 of 4 Chromium runs). A human pressing keys a frame apart is unlikely to hit it; a test runner can.
7. **measured, not about the variants** Yeti's own example shows `cursor: not-allowed` on its busy button, against `button.css`'s comment that busy keeps `progress`: the disabled rule's `:is(..., :has(> input:disabled))` has the higher specificity. Same in (A). Recorded only because it shows in point 1's diff.
8. **inferred** Yeti's segmented control (radios inside `label.button` in a `fieldset`) was not put in a toolbar: native radios already give one Tab stop and arrow keys. Inside `ngToolbar`, Aria's keydown handler on the container would also catch the arrows (`preventDefault: true`, `NC/src/aria/private/behaviors/event-manager/keyboard-event-manager.ts:34`) unless the radios were an `ngToolbarWidgetGroup`. Not measured.

## For the user

- Styles hold: Yeti's CSS applies unchanged to (B) for plain and toggle buttons, with no package CSS; Yeti keys on no attribute Aria writes except `aria-disabled`.
- There is no Yeti module to replace. Aria adds the APG toolbar keyboard (one Tab stop, arrows, wrap, Home and End) but not the `aria-pressed` toggle, which (A) and (B) both still need.
- (B) costs the rendering modes: with JavaScript off, before hydration, and under `hydrate never`, no toolbar button is reachable by Tab, because every server-rendered widget is `tabindex="-1"`. (A) works in all three.
- (B) conflicts with Yeti's busy state: Aria writes `aria-disabled="false"` over Yeti's `aria-disabled="true"`, which breaks the disabled look, the announced state, and axe contrast, unless busy goes through `ngToolbarWidget`'s `disabled` input.
- (A) passes axe with zero violations, as Yeti's example does, but gives a toggle set one Tab stop per button. (B) gives the single Tab stop and arrow keys after hydration, at the costs above.
