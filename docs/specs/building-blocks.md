## Part 1. Cross-cutting decisions

### 1.1 Directive or component

Rule ([ADR 0003](adr/0003-directives-set-yetis-class-attributes-and-markers.md) point 6; map, Directives first): every item becomes attribute directives on the elements Yeti's docs put its class and markers on. The item directive binds the item's one class as a static host class, sets every `data-*` attribute of the item from a typed input ([ADR 0005](adr/0005-closed-unions-from-yetis-vocabularies.md)), and binds the ARIA state it owns; a part directive sets each marker (`data-brand`, `data-close`, `data-track`, `data-slide`, `data-dots`, `data-hint`, `data-error`, and the rest of the 31) on the part that carries an input, a generated id or reference, an output, or behaviour; a child Yeti styles only by element and position gets no directive. The consumer writes no Yeti class or `data-*` attribute, and the platform's relationship attributes (`popover`, `popovertarget`, `commandfor`, `command`) and their ids are rendered by the directives (ADR 0003 point 5). [Decide: how the package maps each of Yeti's `data-*` attributes](issues/26-decide-yeti-data-attributes-mapping.md) makes the per-attribute call, including which attributes stay the consumer's (`aria-label`, `role="list"`, `required`, `name` on `details`).

A component is allowed in two cases: structure the consumer should not hand-write, of which no Yeti item has any (ticket 02: all 49 items are one class plus attributes on consumer markup, and the tooltip is CSS-only), and a `styleUrl` that is what makes lazy styles meet the requirements under the user's standing ruling 28, which [Decide: how component styles load and unload](issues/13-decide-style-loading.md) grants or refuses. On a consumer element it takes an attribute selector.

Consequence: every directive works on server-rendered markup with no DOM creation before hydration (1.11), and because host bindings render on the server, the server HTML is Yeti's documented markup. The consumer keeps the element structure of Yeti's docs and writes directive attributes where the docs write the class, the attributes, and the markers; the deltas each spec lists are the generated ids and the platform attributes the directives render (`popovertarget="menu"` becomes a generated id), and the attributes the spec leaves to the consumer.

Why not the old shape: Foundation had Structural, Variant, and State classes, generated structure in three plugins, and a Sass compile; Yeti has one class per item, attributes from frozen vocabularies, native state, and plain CSS. The old three component cases (one of two markup trees, a wrapper for a height animation, a generated tooltip tip) have no counterpart: `details` grows open by itself, and the tooltip is a CSS sibling (`Y/src/components/tooltip/tooltip.css:1-3`).

### 1.2 Implementation level and the browser target

Order per item: native platform feature, then `@angular/aria`, then `@angular/cdk`, then custom Angular. A spec stops at the first level that covers the behaviour and states the level and the reason; most Yeti items stop at the first, and the user's standing ruling 37 sets levels 2 and 3 for what the platform leaves (map, Implementation order). Where the planning repository's `AGENTS.md` (ngx-foundation-sites-next) puts `@angular/aria` first, the map's order wins.

Browser target ([ADR 0002](adr/0002-browser-target-baseline-2025.md), the user's choice): Yeti's Baseline 2025, Chrome and Edge 141, Firefox 145, Safari and Safari iOS 26.2. Applied from [Research: Angular 22's browser baseline against what Yeti expects](issues/01-research-browser-baseline-vs-yeti.md):

| Usable without a guard (in Baseline 2025) | Yeti guards it in CSS with a stated fallback; the package relies on Yeti's fallback and adds no guard | Not usable; named per spec as the feature to adopt when the target moves |
| --- | --- | --- |
| `<dialog>`, `showModal()`, top layer, `::backdrop`; invoker commands (`commandfor`, `command`); `popover`, `popovertarget`, `:popover-open`, light dismiss; `<details name>`; `@starting-style`; `:has()`; `light-dark()`; cascade layers; container queries and `cq*` units; scroll snap, `scrollIntoView()` with options, `scroll-behavior`; `IntersectionObserver`, `ResizeObserver`; `inert`; `prefers-reduced-motion`; Constraint Validation and `:user-invalid`; `<input type="range">`; `transitionend`, `animationend`; `pow()` and the other math functions Yeti's tokens use; logical properties; `:dir()` (newly available in 2023, inside the set; the package ships no CSS to use it in) | CSS anchor positioning (`anchor-name`, `position-anchor`, `position-area`: the dropdown, the nav sheet, the tooltip; fallback: the user agent centres the panel, the sheet starts at the top of the viewport, `Y/src/components/dropdown/dropdown.css:44-56`, `nav/nav.css:118-138`); scroll-driven animations (the progress bar's scroll mode); `field-sizing`; `interpolate-size`; native masonry (`grid-template-rows: masonry`, `Y/src/layouts/masonry/masonry.css:29`; fallback: multi-column layout, items read down each column; [ticket 50](issues/50-decide-open-points-of-the-specs.md) decision 54) | `interestfor` (the stated end of `hover.js`, `Y/src/components/dropdown/hover.js:11-13`; one engine today); `closedby` on `dialog` (Safari lacks it, `Y/src/components/dialog/dialog.js:5-6`); anything else ticket 01 lists outside Baseline 2025 and unguarded by Yeti (10 cosmetic features, which the specs treat as Yeti does) |

Rules that follow:

- One code path per behaviour in package code, and no package feature detection in the first milestone: Yeti's `@supports` blocks are the fallbacks, and a spec states the fallback it relies on (ADR 0002 consequences). A spec that must detect a feature in JavaScript says why.
- `:has()` and `:popover-open` are inside the target, so a native pseudo-class may be the single source of a state (1.5), which it could not be under the old target.
- CDK is used where it is the smallest correct piece, not as a framework: `_IdGenerator` (1.5; as the token through which Aria's ids reach the package's per-application counter, [ADR 0044](adr/0044-generated-ids-count-per-application-and-are-adopted-at-hydration.md)), `Directionality` (1.5), `hasModifierKey` (1.5), and the `high-contrast` mixin as the model for the package's forced-colours rules (the user's ruling of 2026-10-02, 1.13). Ticket 25 considered and did not use, per item in Part 2: `FocusMonitor` (a `focusout` host listener closes a panel when focus leaves, [ADR 0043](adr/0043-light-dismiss-additions-are-host-listeners-not-cdk-services.md)), `LiveAnnouncer` and `FocusKeyManager` (the carousel has no auto-rotation and the APG's grouped picker keeps every control in the Tab sequence), `AriaDescriber` (the tooltip's bubble is Yeti's markup), `InteractivityChecker` (the dialog focusing steps and Aria's own panel `tabindex` cover the two cases), and `FocusTrap` (the native modal keeps focus out of the page; Tab reaching the browser's own UI in Chromium and WebKit is inferred, ticket 17, and the dialog spec may reopen it with a measurement). `MediaMatcher` and `BreakpointObserver` are not used (1.7). CDK Overlay, Dialog, Menu, Accordion, and Listbox are not used: `popover`, `dialog`, and `details` are the platform's and Yeti's, and a CDK container would move the element out of Yeti's markup. Sources: `NC/src/cdk/a11y/id-generator.ts:22`, `focus-monitor/focus-monitor.ts:87`, `live-announcer/live-announcer.ts:37`, `aria-describer/aria-describer.ts:41`, `interactivity-checker/interactivity-checker.ts:31`, `focus-trap/focus-trap.ts:38`, `_index.scss:48` (checked).
- Aria is used for Tabs (`Tabs`, `TabList`, `Tab`, `TabPanel`, with a `hidden` binding beside Aria's `inert`, 1.9). Aria is also used for the `buttons` group: `yetiButtons` hosts `Toolbar`, the group's part directive `yetiButtonsItem` hosts `ToolbarWidget`, and until Aria is live every member keeps its native Tab stop (Part 2 row 27; "Aria decisions" row 27; [ticket 50](issues/50-decide-open-points-of-the-specs.md) decisions 113 and 117). It is not used for the accordion (`details` is the pattern), the nav and the dropdown (a bar of links and a disclosure, which Aria's `Menu` would mis-role), the dialog, the tooltip, or the carousel (no Aria pattern exists). Source: ticket 03 section 4.3 and ticket 17 Answer. Each row where an Aria pattern could plausibly apply and is not used was listed for the user's confirmation in ticket 25's `### Triage`, as the planning repository's `AGENTS.md` (ngx-foundation-sites-next) asks. Note of 2026-10-03: the user has decided those rows, and `buttons` now hosts Aria Toolbar by composition, with `ngToolbar` on `yetiButtons` and `ngToolbarWidget` on the group's part directive `yetiButtonsItem` ("Aria decisions (2026-10-03)" at the end of this file, which wins over this bullet).
- Images in specs (the planning repository's `AGENTS.md` (ngx-foundation-sites-next) rule): every static `<img>` in a spec's examples, stories, and fixtures uses `NgOptimizedImage` beside any package directive on the same `<img>`; a plain `<img>` remains only where `NgOptimizedImage` cannot be used (the `<img>` of an art-directed `<picture>`, a `data:` or `blob:` URL).

### 1.3 Naming

- Selector prefix: `yeti` ([ADR 0080](adr/0080-yeti-prefix-ngx-yeti-runtime-names-ngxyeti-on-collision.md) point 1), in camelCase for directives (`[yetiCard]`) and dash-case for components (`yeti-...`). Attribute-selector components keep the directive form.
- Class names: the prefix plus the PascalCase of the item's manifest name (`card` to `YetiCard`, `nav` to `YetiNav`, `buttons` to `YetiButtons`, `toc` to `YetiToc`). A part directive is the item plus the part, from its marker or its role (`YetiNavToggle` for `> button[popovertarget]`, `YetiNavList` for `> ul[popover]`, `YetiNavClose` for `[data-close]`, `YetiFieldHint` for `[data-hint]`, `YetiFieldError` for `[data-error]`, `YetiCarouselTrack`, `YetiCarouselSlide`, `YetiCarouselDots`, `YetiCarouselDot`, `YetiTab`, `YetiTabPanel`). A name that equals one Yeti's `yeti.d.ts` exports takes `NgxYeti` instead: today `NgxYetiColumns`, `NgxYetiAttention`, `NgxYetiEnter`, `NgxYetiLift`, and `NgxYetiPrint` (ADR 0080 point 4). The prefix is kept, against the v20 style guide's bare names, because the package hosts Aria's bare `Tabs`, `Tab`, and `TabPanel`.
- 2026-10-03 ([ticket 50](issues/50-decide-open-points-of-the-specs.md) decisions 10 and 11, the orchestrator's): the collision test covers every exported TypeScript name, not only item classes, against all 46 names `yeti.d.ts` exports at the pin (listed in ADR 0080's note of that date). A sixth collision follows: the `[yetiPaint]` marker directive's class is `NgxYetiPaint`. An any-element marker directive's class is `Yeti` plus the PascalCase of its selector without the prefix (`YetiShow`, `YetiHide`, `YetiBorder`, `YetiText`, `YetiNumeric`), and `NgxYeti` on a collision.
- Files: v20 suffix-less kebab-case, one folder per item as a secondary entry point (`nav/nav.ts`, `nav/nav-toggle.ts`, `nav/nav-tokens.ts`, `nav/nav.spec.ts`, `nav/nav.stories.ts`). Entry point `ngx-yeti/<item>` so a consumer's `@defer` block can split per item (1.11), and so a item file travels with its directives (1.13).
- Tokens: camelCase with the `Token` suffix (`yetiNavToken`, `yetiFieldToken`), the planning repository's `AGENTS.md` (ngx-foundation-sites-next) form, carried from the old bundle's rule.
- Inputs: Yeti's attribute and marker names in camelCase (`data-variant` to `variant`, `data-threshold` to `threshold`, `data-raised` to `raised`); types are Yeti's own vocabulary types (`YetiVariant`, `YetiWidth`, `YetiGap`, `YetiPanel`), imported from `yeti-css` in package source and, in the published declarations, from the generated `yeti-types.ts` that [ADR 0060](adr/0060-item-styles-are-counted-links-to-the-consumers-yeti-build.md) point 10 requires, re-exported by name, never redeclared; an attribute with its own value list takes a package type `Yeti<Item><Input>` (ADR 0080 point 5). A marker that is a part's identity (`data-brand`) is the part directive's selector, not an input, unless ticket 26 says otherwise.
- Outputs and methods: each `yeti:*` event becomes an output named by its verb without the prefix, one form per spec, chosen so the model's `xChange` and the completion output do not collide: `yeti:select` to `select` or `selected`, `yeti:slide` to `slide`, `yeti:current` to `current`, `yeti:invalid` to `invalid`, `yeti:open` and `yeti:close` to `opened` and `closed`. Methods take Material's vocabulary (`open()`, `close()`, `toggle()`, `select()`), never `show()` and `hide()`, which collide with `HTMLDialogElement.show()` and `showPopover()`'s family; never an `on` prefix. A boolean state signal whose verb would collide is `isX` (`isOpen` beside `open()`).
- Story ids: `<item>--<story>` in kebab case, named in each spec's Testing Decisions so play functions and Playwright open the same artifact; `<item>` is the entry point folder name, pinned by `meta.id`.
- `exportAs`: every directive and component has one, the class name with a lowercase first letter (`yetiNav`, `yetiTab`), as Aria gives every public directive one, input-only parts included (`NC/src/aria/tabs/tab.ts:40`, `tab-panel.ts:44`; checked). The user's ruling of 2026-09-29, carried over (map, Input naming).

### 1.4 Inputs and outputs

- Every `data-*` attribute of the item's manifest becomes `input()` under its camelCase name: an enum attribute is typed by the closed union of its vocabulary or of its own `values` ([ADR 0005](adr/0005-closed-unions-from-yetis-vocabularies.md)); a boolean attribute or marker takes `booleanAttribute`, so `<article yetiCard raised>` works; a count takes `numberAttribute`. Defaults are the manifest's (`data-threshold` default `md`), and an input left unset binds no attribute, so Yeti's own default applies from its CSS; the spec lists any default it changes and why (an APG or Aria requirement). Exceptions, attribute by attribute, are ticket 26's: an attribute left to the consumer, an attribute that is a part's identity, an attribute that is Angular-owned state.
- Inputs named like HTML attributes (carried from old ticket 139; map, Input naming): a static input attribute stays on the element and HTML lowercases it, so an input whose lowercased name is an HTML attribute (`width`, `height`, `align`, `size`, `span`, `type`, `role`, `aria-*`) also renders that attribute. The declaring directive owns what the static attribute renders, and the spec's input table states one kind per such input, from what the attribute does on each host the spec allows: `output` (bound from the input, `null` when off), `removed` (`'[attr.<name>]': 'null'`, as Material's `MatHint` does for `align`), `insertion` (`'[attr.autofocus]': 'null'` plus the usage rule that it is never written statically on a host that can take focus), or `inert` (no binding). A `removed` or `insertion` binding carries a source comment naming the effect it prevents, and the spec's SSR smoke writes the static form and asserts that the attribute is absent.
- Shared vocabularies: two items that read one vocabulary share its exported type, so two directives a consumer composes on one element never declare one input name with different types (`gap` on 21 items, `align` on 8, `threshold` on `nav` and `columns`; ticket 02). Two package directives written on one element must not declare one input name with different types, because Angular sets a template binding on every directive that declares it.
- `model()` for state Yeti exposes as both an attribute and an event: the tabs root's selection (`aria-selected` and `yeti:select`), the dialog's `open` (`open` and `yeti:open`, `yeti:close`), the toc's current link (`aria-current` and `yeti:current`). The carousel's index is not a model: Yeti exposes no attribute for it, so the root has a read-only `current` signal beside the `slide` output ([ticket 50](issues/50-decide-open-points-of-the-specs.md) decision 121). The accordion's open state is not a model either: a read-only `isOpen` signal and an `isOpenChange` output, because a model input would clash with the static `open` attribute (decision 96). Yeti's events mark a choice, not an arrival (`carousel.js:38-41`: "the event is about the choice, not the arrival"), so the model's `xChange` fires on the choice and a completion output, where a spec has one, after the transition (1.6).
- Initial state is bound, never read from a static attribute, and an attribute a person or a Yeti module could change before hydration is Angular-owned state (ADR 0003 point 4; ticket 18, measured: a static `open` reopens a closed `details`, a static `aria-selected="true"` leaves two tabs selected, a restored `data-once` stops the arrival). A directive may still read the consumer's own attributes it does not own (`required`, `disabled`, `name`). One exception, by the user's open-state choice of 2026-10-03, "Never bind; read once (Recommended)" (map, Standing rulings; [ADR 0021](adr/0021-dialog-is-a-directive-on-the-native-dialog.md)): no directive binds `open` on a `details` or a `dialog`, as a property or an attribute. It reads the element's open state once, when it is created, then follows the native `toggle` and `close` events; a dialog opens only through `command` or `showModal()`.
- `linkedSignal` for derived-but-writable state (Aria's `TabList` keeps its selected pattern this way), including the `set` write-back form when a part writes into a parent model.
- Outputs: each `yeti:*` event the item would have dispatched is an `output()` typed by the event's frozen `detail` keys (`{tab, panel}`, `{index, slide}`, `{link, heading}`, `{controls}`; `Y/src/guides/stability.md:21-22`), on the directive that replaces the module ([ADR 0040](adr/0040-package-replaces-yetis-optional-modules.md)). The directive does not also dispatch the DOM event. No event-manager plugin alias and no `yeti:*` to `yeti-*` re-dispatcher: `(yeti:select)` is a compile error, so a plugin never sees the name; the alias and the re-dispatcher work but type `detail` only through global augmentation or not at all, and the re-dispatcher costs one event per Yeti event on every page; none of the three replays ([Research: binding Yeti's `yeti:*` events in Angular templates](issues/16-research-yeti-events-in-angular-templates.md), measured in Chromium). A part-level output is `void`; a root-level output carries the part.
- Where a consumer must veto a close, the spec adds a predicate input (Material's `closePredicate`), beside the platform's own `cancel` event on a dialog, never a cancelable output.
- Removed options: none of the old categories exists in Yeti (no jQuery options, HTML-string options, class-name options, or timing options; Yeti's timings are tokens that stay the consumer's under [ADR 0004](adr/0004-yeti-tokens-are-a-consumer-stylesheet-surface.md)). What a spec leaves to the consumer is a row in ticket 26 with its reason.
- Defaults tokens: none by default. Yeti's defaults are the manifest's and its tokens are the theme; an item whose spec wants an application-wide default for a package-owned option (a dialog's `closeOnBackdrop`) declares an optional `yetiXDefaultsToken` and says why. No umbrella `provideYeti()`.

### 1.5 State, reactivity, DOM access

- All state is signals read from `host` bindings or templates; OnPush is the default and zoneless is required (map, Standing rulings, item 43). Anything driven by a timer, observer, or native listener writes into a signal; no `markForCheck`. Measured: a plain field written from a `yeti:slide` listener refreshes under zone.js but not zoneless, while a signal does (ticket 18).
- `computed` for derived read-only state; `effect` never writes the DOM, `history`, or a timer, and never copies one signal into another. One exception: the reverse-link registration of a reference input with its target (an opener with its dialog) runs in an `effect` whose cleanup unregisters, because the reference can change at runtime; it writes only the target's registry signal, so it is safe on the server, and it is Aria's own shape (`MenuTrigger` sets `menu.parent` from an `effect`). The old rendered-state rule, which existed for breakpoint-driven mode swaps, has nothing to apply to (1.7); a spec that introduces a JavaScript-driven swap of its own reinstates it in its decision log.
- DOM reads and writes that need layout run in `afterRenderEffect` with explicit `earlyRead`, `write`, and `read` phases, or in the callback of a `ResizeObserver` or `IntersectionObserver` created in `afterNextRender`; never in `ngAfterViewChecked`, never at construction. `afterRenderEffect` is `NGP/core/src/render3/reactivity/after_render_effect.ts:318` (checked).
- Host bindings do the class and attribute work (`[attr.aria-selected]`, `[attr.hidden]`, `[attr.popovertarget]`, `[style.--yeti-range-value]`); `Renderer2` and `ElementRef.nativeElement` writes are limited to imperative calls (`showModal()`, `showPopover()`, `hidePopover()`, `scrollTo()`, `focus()`), every one of them in a render callback or a handler after hydration, so none carries first-paint state. The package binds no state class and writes no state attribute of its own (ADR 0003 point 3).
- `DOCUMENT` from `@angular/core`; `window` only inside render callbacks; `history` and `location` only after first render (1.11). No `matchMedia` for a breakpoint (1.7); a capability query (`(hover: hover) and (pointer: fine)`, as `hover.js:14` reads at event time) is read in a handler, never at construction.
- Services are warranted only for state shared across instances. Ticket 25 placed one: the fragment-links spec's root service holding the one document `click` listener (Part 2 row 51). Closing on navigation is not a service: each open panel subscribes to `NavigationStart` itself ([ADR 0041](adr/0041-closing-on-navigation-is-a-per-instance-subscription.md)). An item-internal service for the same reason is allowed, internal to its entry point and not public API. Everything else is directive-local state plus DI links (1.9). Services use `@Service()` (`NGP/core/src/di/service.ts:76`, checked).
- Ids: the consumer's `id` wins ([ADR 0042](adr/0042-generated-ids-come-from-cdk-idgenerator-through-one-helper.md) point 2); otherwise `injectYetiId(item)` adopts the host's server-rendered id at hydration or takes the next number of a per-application counter seeded on the client through `TransferState`, with an item prefix (`ngx-yeti-nav-`); `provideYetiAriaIds()` puts Aria-hosted elements on the same counter with Aria's own prefixes ([ADR 0044](adr/0044-generated-ids-count-per-application-and-are-adopted-at-hydration.md)). Generated ids are therefore equal on the server and the client, and every reference to one (`popovertarget`, `commandfor`, `aria-controls`, `aria-labelledby`, `aria-describedby`, `for`) is a host binding that hydration leaves unchanged (measured, ticket 35). Anything addressed from outside the application (a fragment link to a slide or a heading, a `details name` group) requires a consumer-supplied value; each such spec states it as a usage rule.
- RTL: `Directionality.valueSignal` from `@angular/cdk/bidi` (`NC/src/cdk/bidi/directionality.ts:43`, checked), never `html[dir]` reads. One exception, a read of the rendered layout: a directive that scrolls a track takes the track's computed `direction` in its client handler, as `carousel.js:31-33` does, because scroll geometry follows CSS direction. The package ships no CSS, so it has no logical-properties rule to keep; Yeti's CSS is already logical.
- Keyboard: `event.key` comparisons and `hasModifierKey` from `@angular/cdk/keycodes`; no `keyCode`. Aria owns the keyboard where it is hosted (Tabs); the carousel and the dropdown implement their APG key tables directly. Every package key handler changes state first and calls `preventDefault()` last, because `preventDefault()` throws during event replay and skips everything after it (1.11).
- Effects run on the server, so an effect never writes the DOM.
- Note of 2026-10-03 ([ticket 50](issues/50-decide-open-points-of-the-specs.md) decision 143): `demo` makes two layout touches outside this list. Its grip reads the preview box's minimum and maximum by writing `0px` and `100000px` to the box's inline size and restoring it in the same task, as `demo.js:88-96` does, only in handlers and observer callbacks after hydration, because the caps are `calc()` and `min()` over the container, which a computed style does not resolve to pixels. And its keys and drag mirror by the box's computed `direction` rather than `Directionality`, under the RTL bullet's exception for geometry.

### 1.6 Animation mechanics

User rule (map, Animation): no `@angular/animations`, no JavaScript-timed animation; Yeti's CSS and `animate.enter` and `animate.leave` in the class form. The shared mechanics:

1. Elements that stay in the DOM and change state (a dialog, a popover, a `details`, a tab panel) animate through Yeti's own CSS keyed on native state: `:popover-open` with `@starting-style` (`Y/src/components/dropdown/dropdown.css:57-58`), `[open]`, the `enter` utility. The directive adds no class and no inline style for it. Where a directive must act after a transition (focus after a panel closes, a completion output), it awaits `transitionend` or `animationend` on its host filtered by `event.target`, with a fallback timer of the duration read from the host's computed `transition-duration` or `animation-duration` once the state is set, plus 100 ms, a measured zero completing at once. It never parses a token's text: a production build writes `--yeti-duration-fast` as `.15s`, which `parseFloat` reads as 0.15 (`upstream-bugs.md` Y1, measured).
2. Elements the package or the consumer inserts or removes: `animate.enter="<classes>"` and `animate.leave="<classes>"` in the class form, as host bindings or in templates, with Yeti's own classes (`enter`) or the consumer's. The function form is never used anywhere in the package or its stories: a permanent function-form `(animate.leave)` anywhere kept `badge.css` loaded, the class form did not (`upstream-bugs.md` A1; ticket 18, measured). An alert the consumer removes with `@if` takes `animate.leave` with Yeti's transition, which replaces `alert.js`'s `Element.animate` fade (ticket 18: removed after 153 to 192 ms).
3. `animate.enter` plays at hydration on a server-rendered element (old bundle, measured with 22.2; `NGP/core/src/animation/` has no hydration guard, checked by search), so it is used only for elements that are never server-rendered in their animated state. It does not replace Yeti's `data-once` arrival, which is viewport-driven: a `.enter[data-once]` inserted after load never arrives without the `enter` directive's observer (ticket 18, measured), and the directive owns `data-once` as Angular state because hydration restores it (ADR 0003 point 4).
4. Reduced motion is Yeti's: its tokens collapse every animation under `prefers-reduced-motion` (ticket 17: "Reduced motion collapses every animation measured"), and the carousel's scroll takes the track's `scroll-behavior`, which reads the collapsed token (`carousel.js:28-30`). The package has no `reducedMotion()` signal and no animations token; a directive that awaits a transition completes at once when the measured duration is zero. Tests emulate `prefers-reduced-motion` through Playwright where a case needs it.
5. `MAX_ANIMATION_TIMEOUT` is left at Angular's default (4 s; `NGP/core/src/animation/interfaces.ts:40-46`, checked); no Yeti transition exceeds it.
6. The old Motion name types, the `nfs-motion` mixin, and the Motion UI mapping have no counterpart and are abandoned with Foundation's Sass.

### 1.7 Breakpoints

Abandoned, and replaced by the platform. Yeti has no viewport breakpoint in JavaScript and no breakpoint map: every size-dependent change is a container query in CSS, keyed on the element's own width. `data-show` and `data-hide` are `@container (inline-size ...)` rules in the always-loaded `layouts/attributes.css` (`Y/src/layouts/attributes.css:368-387`, checked); `data-threshold` on `nav` and `columns` is decided by the container's width: a container query on `nav` ("its own width, not the screen's", `Y/src/components/nav/docs.md`), flex-basis arithmetic on `columns` (`flex-basis: calc((var(--_yeti-threshold) - 100%) * 999)`; `columns.css` has no `@container`; corrected 2026-10-03, [ticket 50](issues/50-decide-open-points-of-the-specs.md) decision 33); the card, the pagination, and the nav change shape by `@container`. No Yeti module reads `matchMedia` for a size or `innerWidth` (checked across the ten modules; `hover.js:14` reads a pointer capability).

Rules that follow:

- The package has no breakpoint service, no breakpoint token, no server breakpoint, no rule-string parser, no `MediaMatcher`, and no `BreakpointObserver`. A spec never adds a viewport-keyed input (`hideFor`, `showFor`, `revealOn`).
- A directive that needs its own size (none is known today) observes its element with `ResizeObserver` from `afterNextRender` and says why in its decision log.
- Because no mode swaps on the client at first render, the old server-breakpoint problem and the rendered-state rule do not arise (1.5).
- Stories and e2e tests that show a size-dependent change resize the container, not only the viewport, because that is what Yeti's CSS reads.

### 1.8 Openers

Replaces the old Triggers section. Foundation's `data-open`, `data-close`, and `data-toggle` had no platform counterpart in the old target; Yeti's openers are the platform's attributes, and the package renders them (ADR 0003 point 5):

- A dropdown and a nav are `popover` panels opened by `popovertarget` on a `button`; the dialog is opened by `commandfor` plus `command="show-modal"`; a close button inside a nav panel is `popovertargetaction="hide"`, and inside a dialog a `form method="dialog"` button; an accordion panel is `details` with `summary`. The directive of the parent or the opener generates the ids and binds both ends (1.9), and the consumer's own id wins. Opening, the top layer, light dismiss, Escape, the toggle's `aria-expanded`, focus containment, and the `::backdrop` are the platform's; the directive observes `toggle`, `command`, and `close` and adds state (`opened` and `closed` outputs, an `open` model) rather than owning activation with a `click` handler. Measured: with JavaScript off the dialog opens by invoker commands, the dropdown by `popover`, the accordion by `details`, while a click handler waits for replay (ticket 18).
- An opener anywhere on the page (a dialog's button) is a free directive written beside the button's own item directive (`<button yetiButton [yetiDialogOpener]="confirm">`) and takes a template reference; an opener that is a part of its item (the nav's toggle) is a part directive that reads the parent's token. No `Openable` interface and no nearest-ancestor resolution: the platform relates the two by id.
- What the package adds over the platform is what Yeti's modules added or the APG asks for: the backdrop click and the focus return to the opener (`dialog.js:1-9`, `:52-58`; the platform restores focus to whatever had it, and in WebKit a clicked button never has it), hover intent for `data-trigger="hover"` with the delays read from `--yeti-dropdown-open-delay` and `--yeti-dropdown-close-delay` through computed style, in a per-instance directive rather than `hover.js`'s document delegation (`hover.js`; its stated end is `interestfor`, outside the target, 1.2), closing when focus leaves a dropdown or a nav panel (ticket 17, APG disclosure navigation; a `focusout` host listener with a `pointerdown` guard, [ADR 0043](adr/0043-light-dismiss-additions-are-host-listeners-not-cdk-services.md)), and closing on navigation (1.15; [ADR 0041](adr/0041-closing-on-navigation-is-a-per-instance-subscription.md)). Each is a `ledger.md` row where it is more than Yeti's module did.
- Placement is Yeti's CSS: anchor positioning behind Yeti's `@supports` guard, with Yeti's fallback (1.2). The package has no positioner, no light-dismiss registry, and no measured placement; CDK Overlay is not used.
- Not used before they reach the target: `closedby="any"` (Safari lacks it; `dialog.js:5-6`), `interestfor`, `dialog.requestClose()`. Each spec names the one it adopts when the target moves. Correction of 2026-10-03 ([ticket 50](issues/50-decide-open-points-of-the-specs.md) decision 154): `dialog.requestClose()` is inside the target (`@mdn/browser-compat-data` 8.1.4: Chrome 134, Firefox 139, Safari 18.4). It is not adopted in the first milestone, because the Backdrop press keeps `dialog.js`'s `close()` like for like and `closePredicate` already covers it; a later record may route the press through `requestClose()` so that `cancel` is the single veto point.

### 1.9 DI patterns

- Parent handle: `InjectionToken<Parent>` in `<item>-tokens.ts` with `import type`, parent `providers: [{provide: yetiXToken, useExisting: YetiX}]`, part `inject(yetiXToken)` required when the part cannot exist alone (a tab inside a tabs root, a nav toggle inside a nav), `{optional: true}` when the part may stand alone (a dropdown inside or outside a nav), where it degrades as its spec documents.
- Composition, never subclassing (map, Composition over subclassing): package directives are not extension points. An Angular subclass inherits host bindings, inputs, outputs, host directives, and lifecycle hooks, but not `providers`, its selector, or `exportAs`, and a directive injected by class matches its exact type only.
- Hosting an item directive: a directive whose element is always another item's element hosts that item's directive through `hostDirectives` and exposes its inputs under their own names. Since Angular 22.0 a directive reached several times through host directives on one element is created once with the exposed input maps merged, and a template match of the same directive discards its host-directive matches (`CHANGELOG.md:937`, 22.0.0 "de-duplicate host directives"; the old bundle measured it with 22.2.0). Two items a consumer composes on one element (`center box`) are written beside each other; whether any Yeti item always sits on another's element is ticket 25's per-item call.
- Ancestry that projection can hide: a directive that must know at first paint that it sits inside another package element injects that element's lightweight token optionally at construction, which is right on the server for everything declared inside it; where content projection from another template can hide the provider, it may walk the DOM once in its first render callback, only when the token is absent.
- Imports (map, Milestones, the user's ruling of 2026-09-28): entry points export their directive classes and no import arrays, and a component lists in its `imports` every directive class whose attribute its template writes. A forgotten one renders the element without its class, attributes, and behaviour, with no report, unless a bound input or a template reference makes the compiler report it (NG8002, NG8003); each spec's usage examples import every directive they use. A parent token's description is its name.
- Same-element siblings: `inject(X, {self: true, optional: true})` (a field control directive reading `FORM_FIELD` from `@angular/forms/signals`, then `NgControl`).
- Ordered parts: parent-owned registration (`register()` in `ngOnInit`, `unregister()` on destroy) with DOM-order sorting from a `MutationObserver` started in `afterNextRender`, Aria's `SortedCollection` shape, rather than `contentChildren`, because it survives `@for`, `@defer`, and projection. `contentChildren` only where a directive must write a default during the server render that a collection sorted after the first render cannot give (the tabs' first-tab default). A part linked by a reference input registers from an `effect` with cleanup instead (1.5).
- Links between non-nested elements: template references on inputs (`[yetiDialogOpener]="confirm"`) or Aria's value pairing (`yetiTab value="x"` with `yetiTabPanel value="x"`).
- Aria composition: a Yeti-classed directive hosts the Aria directive through `hostDirectives`, exposes only the Aria inputs it wants, aliased to Yeti's names where Yeti has one, adds the item class in `host`, and reaches the Aria instance with `inject(AriaDirective)`. A host binding on an attribute the Aria directive also binds holds only when its value never changes after the wrapper's last write, or equals Aria's whenever it changes, or changes in every pass in which Aria's does, which a binding computed from the same public Aria signal guarantees: the tab panel's `hidden`, which Yeti's CSS and `tabs.js` key on, derived from `TabPanel.visible()` beside Aria's own `inert` (`NC/src/aria/tabs/tab-panel.ts:49`, `:84`, checked). An Aria input whose default differs from Yeti's documented behaviour is not exposed; the wrapper declares its own input and enforces it through Aria's models and methods. Aria-hosting containers carry the replay guard, a `keydown` listener that stops propagation of the keys Aria handles so a replayed key is not handled again by an outer widget.
- Platform guard: never `isPlatformBrowser` in templates; browser-only work in render callbacks; platform-specific providers via `app.config.server.ts`.
- Lazy services: `injectAsync` (`NGP/core/src/di/inject_async.ts:50`, checked) is the pattern for a service needed only after a client interaction; each spec that owns such a piece decides eager or `injectAsync` in its decision log.
- Restore any global the directive touched in `DestroyRef.onDestroy`: an open popover or dialog is closed, a `NavigationStart` subscription removed, a `--yeti-sticky-offset` or `--yeti-toc-scroll` the directive set on an ancestor removed. A fragment the user navigated to is the user's state and outlives the directive that wrote it.

### 1.10 Accessibility baseline

Shared by every spec (map, Accessibility; the user's standing rulings 36 and 37):

- WCAG 2.2 AA is a requirement for every directive and component. Each spec carries a criteria subsection naming the 2.2 AA criteria its item touches and how each is met. Yeti's own examples measure clean: axe-core 4.13.0 with the WCAG 2.2 AA tags found 0 violations on all 49 docs examples in Chromium, Firefox, and WebKit, the Nu Html Checker found no errors, and every Tab stop had a 2 px focus ring ([Research: Yeti against WHATWG, WAI-ARIA, the APG, and Angular Aria, CDK, and Material patterns](issues/17-research-yeti-accessibility-and-standards.md)); five items (timeline, layer, breakout, media, lede) left `color-contrast` incomplete and need a manual check, which their specs carry. So the gate guards the package's own additions and the behaviour deviations below; there are no Sass settings to require and no Library mixin rules to emit.
- The APG pattern named per item is the contract; "a role is a promise": no role without its full keyboard table. The nav is a bar of links with a disclosure toggle, never `menu` or `menubar`; the dropdown is a disclosure; the dialog is Dialog (Modal); the tabs are Tabs, with automatic activation by default (Yeti's behaviour and the APG's recommendation) and manual activation through `selectionMode="explicit"` ([ticket 50](issues/50-decide-open-points-of-the-specs.md) decision 204); the carousel is Carousel; the accordion is `details`, which the APG's accordion pattern does not govern (the spec states the platform's behaviour instead).
- Native elements first: triggers are `<button type="button">`, dialogs are `<dialog>`, ranges are `<input type="range">`, switches are `<input type="checkbox" role="switch">`, links stay `<a href>`, as Yeti's examples write them (1.2).
- The deviations the package closes, each a `ledger.md` row with its building block (ticket 17; ticket 25 seeds the ledger): the tooltip cannot be dismissed with Escape (the directive sets `hidden`, through Yeti's own `[hidden]` rule, WCAG 1.4.13); dropdown and nav panels stay open when focus leaves (a `focusout` host listener, ADR 0043); the carousel has no previous and next buttons, no slide `group` with `aria-roledescription="slide"`, and no current-slide marker (part directives on consumer-written buttons, two static bindings on the slide, `IntersectionObserver`; Part 2 row 29); the demo grip has no `aria-controls` (`_IdGenerator`); the vertical tabs have no `aria-orientation` (Aria `TabList`); the field's required `*` ends up in the accessible name (one rule with CSS alternative text in the package's stylesheet); the modal dialog's Tab passes through the browser's own UI in Chromium and WebKit (inferred; no `FocusTrap` in the first milestone, the dialog spec may reopen it). Yeti ships no `forced-colors` rules; the package may add CSS for them by the user's ruling of 2026-10-02 ("Accessibility CSS: Yes.", map, Standing rulings), one rule per gap in `@layer ngx-yeti` (1.13), each a ledger row owned by its item's spec.
- Hidden content that stays in the DOM: `hidden` where Yeti's CSS keys on it (the tabs' panels, the tooltip), Aria's `inert` where Aria adds it (the hosted tab panel carries both from one signal, 1.9); `aria-hidden` is not used for hiding. A `dialog` and a popover manage their own inertness.
- Names: on an element the consumer writes, the name is the consumer's own `aria-labelledby` or `aria-label`, as Yeti's docs ask (`aria-label` on the `nav`, on the toggle, on the `tablist`; `aria-labelledby` on the dialog), stated as a usage rule, and the directive declares no name input for it. `aria-label` is never added to elements named from content. A spec that requires text in content counts it as accessible-name computation does.
- Current page: a nav link, a pagination item, and a breadcrumb step mark the current page with `aria-current`, written by the consumer or by `RouterLinkActive` with `ariaCurrentWhenActive="page"`, never a class; Yeti's CSS styles `a[aria-current]` (`Y/src/components/nav/nav.css:85`). The toc's `aria-current="true"` is the directive's, from its observer (`toc.js` replaced).
- Focus: one tab stop per composite (roving `tabindex` from Aria for the tabs; the carousel's dots stay one Tab stop each, as the APG's grouped picker has them, Part 2 row 29); focus moves into a dialog by the platform and returns to the opener on close by the directive (`dialog.js:52-58`'s behaviour kept), never focus on the `dialog` element itself; a nav panel's close returns focus to the toggle (the platform's, `nav/docs.md` Accessibility).
- Disabled: `:disabled`, or `aria-disabled="true"` on a link acting as a button, as Yeti's state table has it (`Y/src/guides/components.md:89`); Aria's `softDisabled` for composite items the package hosts.
- Escape closes a popover and a dialog natively and the tooltip through the directive; moving focus out of a dropdown or nav panel closes it through the directive (WCAG 1.4.13, 2.4.11).
- Reduced motion is Yeti's (1.6). Auto-rotating content does not exist: Yeti's carousel has no autoplay.
- Target size and non-text contrast (WCAG 2.2 AA 2.5.8, 1.4.11): Yeti's examples pass axe, which has no 1.4.11 rule; a spec whose item draws a state by colour alone against a neighbour (a selected tab, a current page) asserts the ratio between the two states in its play function, from the exact WCAG formula on the painted colours; `center` overflows the page width by 2 px at 320 px (ticket 17, WCAG 1.4.10), a ledger row for ticket 25.
- Gate: every story runs axe through `@storybook/addon-a11y` with `parameters.a11y.test = 'error'` and `runOnly` set to `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa`, `best-practice`; no story silences a rule or lowers the level for a Yeti default.
- Strings and direction: the package renders no human-readable string of its own; every label, role description, and message comes from consumer markup, a consumer function, the browser's own `validationMessage`, or the author's message per rule. Direction from `Directionality.valueSignal` (1.5).

### 1.11 Rendering modes

User rule (map, Rendering modes; the user's standing ruling on `withEventReplay()`, `provideClientHydration()`, incremental hydration, and `withI18nSupport()`): every directive and component is specified for `@defer` with its hydrate triggers, SSR, prerendering, full and incremental hydration, event replay, and `withI18nSupport()`. Facts come from [Prototype: Yeti under SSR, hydration, `@defer`, event replay, and `animate.enter` and `animate.leave`](issues/18-prototype-yeti-rendering-modes.md) (eight production SSR builds, Chromium, Firefox, WebKit) and the old bundle's `research/angular-rendering-modes.md` (evidence only). Old ADR 0008's record is ticket 08's.

Facts that shape the design:

- `provideClientHydration()` alone turns on incremental hydration and, through it, event replay; "without replay" needs `withNoIncrementalHydration()` (`NGP/platform-browser/src/hydration.ts:159`, checked). With replay, early clicks, `input`, and the `toggle` of `details` and popovers reach Angular; without hydration the server DOM is replaced and every early-opened dialog, popover, `details`, and selection is lost.
- Hydration matches nodes by type and tag name only, and writes every static template attribute again (`setupStaticAttributes`), so an attribute a person or a module can change before load must be Angular-owned state (1.4; ADR 0003 point 4).
- With JavaScript off, every item renders styled; the dialog opens by invoker commands, the dropdown by `popover`, the accordion by `details`, and carousel dots follow fragments; tabs show every panel, which is Yeti's no-script state. Prerender matched SSR and hydrated with 0 removals.
- Without `withI18nSupport()`, a component with `i18n` blocks is serialised `ngSkipHydration` and re-rendered destructively, even in a source-locale build; with it, a Danish build hydrated with 0 removals and replayed the click.
- All seven client `@defer` triggers insert content no module ever set up, so the directives own setup (ADR 0040); every `hydrate on ...` block is server-rendered and hydrates on its trigger; `hydrate on interaction` replays the click; `hydrate never` stays inert to Angular while native features work, and a `styleUrl`'s styles are removed when the last live instance leaves while the dehydrated markup stays (`upstream-bugs.md` A2).
- Event replay covers only listeners declared in templates or `host` metadata for a fixed list of native events; not replayed: `yeti:*` events and the outputs that replace them (ticket 16), a `dialog`'s `close` (`upstream-bugs.md` A3), `pointerenter` and `pointerleave`, `animation*`, `transition*`, listeners added in code, and `document:` and `window:` host listeners. `preventDefault()` throws during replay and skips the rest of the handler.
- `ngSkipHydration` is valid only on component hosts, so every directive must be hydration-clean by construction; the package never uses it and never uses Shadow DOM encapsulation.

Decisions:

1. Server output is the first paint. Every state visible at first paint is a host binding on signal state (the item class, the `data-*` attributes, the platform's relationship attributes and ids, ARIA, `hidden`, `open`, `--yeti-range-value`). No template branches on the platform.
2. Open-at-first-paint content renders on the server: a `details` the page ships open, a dialog or popover open at first paint, the selected tab's panel. Panel content is projected, never placed in Aria's `ng-template` content directives, because Aria's `DeferredContent` creates views in `afterRenderEffect` and an open Aria panel is empty in server HTML; lazy panel content stays an opt-in a spec may offer, saying it is client-only.
3. Nothing before hydration outside templates: no node creation, `Renderer2` writes, `window`, `getBoundingClientRect`, `focus()`, `showModal()`, observers, `history`, or `location` outside `afterNextRender` and `afterRenderEffect`, the package's only platform check.
4. Timers (hover intent, fallback timers) start only inside render callbacks or handlers, never during server render.
5. The platform opens; the directive observes. `popovertarget`, `commandfor`, `command`, and `popover` are in the server HTML with generated ids, and the directive listens for `toggle`, `command`, and `close` in `host` metadata and reads the element's state (1.8). A directive that does handle a replayable native event changes state first and calls `preventDefault()` last. Hover opening uses non-replayed `pointerenter` and `pointerleave`, read at event time. (Corrected 2026-10-03, [ticket 50](issues/50-decide-open-points-of-the-specs.md) decision 92: this clause named `pointerover` and `pointerout`, which are in Angular's replayed list, as is `pointerdown`; only `pointerenter`, `pointerleave`, `mouseenter`, and `mouseleave` are skipped.) Document-level handlers do not replay, which is correct: nothing the package opened is open before hydration.
6. Hydration boundaries: a composite widget's root and parts, and an opener with its panel, belong inside one hydration boundary. The reason is behaviour, not ids, which ADR 0044 made equal: parts register with their root, and the listeners and outputs sit on one end ([ticket 50](issues/50-decide-open-points-of-the-specs.md) decision 227). Every spec documents that a consumer `@defer` wraps the whole widget, never part of it. The toc's headings are the exception: they are observed from the DOM, not registered, so they may sit in any boundary.
7. `@defer`: package templates contain no `@defer`; each item is a secondary entry point so a consumer can defer per item. Inside a dehydrated block a directive is its server HTML: Yeti's CSS and the platform carry the closed and open states. Inside `hydrate never` an item works as far as the platform does (the dialog opens, the dropdown opens, the `details` opens, the carousel scrolls, every tab panel shows), and each spec states that residue; a `styleUrl`-loaded item file is removed when the last live instance leaves, so ticket 13 says what a `hydrate never` consumer does.
8. Fragment links (carousel dots, toc links, tab deep links) apply after hydration because the server never sees the fragment, and they require consumer-supplied ids (1.5); under `<base href>` they go through the package's fragment handling (1.15).
9. `animate.enter` plays at hydration, so it is used only for client-inserted content (1.6).
10. Prerendering is SSR at build time with `REQUEST` null; nothing in the package reads request tokens.
11. `i18n`: every spec's fixture includes one `i18n` text so the SSR smoke runs with `withI18nSupport()` and the e2e fixture app provides it.

### 1.13 Styles, tokens, and item files

Replaces the old Sass and theming section. Yeti ships no Sass; its tokens are runtime custom properties; its CSS is 49 item files over an always-loaded group, each part in a `yeti.*` layer ([Research: Yeti's styling model, and loading component styles lazily](issues/04-research-yeti-styles-and-lazy-loading.md); [Research: Yeti's cascade layers and stylesheet order](issues/23-research-yeti-layers-and-import-order.md)).

- The always-loaded group (map, The always-loaded group): `layers.css`, `tokens/*`, `base/*`, and `layouts/attributes.css` are the consumer's global stylesheet, loaded in Yeti's order with `layers.css` first (`Y/src/guides/install.md:92-97`), and not specified. 40 of the 49 item files render differently without `layouts/attributes.css`; a part placed before `layers.css` broke 65 of 98 pages (tickets 04 and 23, measured in three engines). A spec that relies on a rule of the group cites it.
- Item files (map, Lazy styles): each first-milestone item's item file loads when its first instance renders and unloads after the last, by the mechanism, with the exceptions, and with the consumer's one line that [Decide: how component styles load and unload](issues/13-decide-style-loading.md) decides from ticket 23's options (where the order is declared: L1 to L3; where parts are inserted: P1 to P4; cross-part rules: X1 to X3). Measured constraints the decision must honour: `stack` and `center`, and `shell` and `center`, tie inside `yeti.layouts`, so a lazy `stack` appended after `center` un-centres a center in a stack unless inserted in Yeti's order; `spinner.css` holds a busy button's ring and `toc.css` the nav's smooth scrolling, so removing either changes another item; Angular's leave-animation guard (`upstream-bugs.md` A1) and the dehydrated-instance gap (A2) remain; a few pages in Chromium and WebKit keep stale computed styles after any insertion method until the element is replaced (O2).
- No package CSS: the package re-implements no Yeti style and ships none of Yeti's CSS; its own CSS is the accessibility rules the user allowed on 2026-10-02 (map, Standing rulings). No directive carries styles; a component carries a `styleUrl` only where ticket 13 makes that the mechanism, with `ViewEncapsulation.None` and the item file imported as is (measured: inlined by ng-packagr with its layer and container queries intact, one `<style ng-app-id>` in the server HTML, 0 style mutations at hydration, ticket 04).
- Tokens ([ADR 0004](adr/0004-yeti-tokens-are-a-consumer-stylesheet-surface.md)): a consumer stylesheet surface. Each spec has a Tokens subsection: the tokens its item reads (from its manifest's `tokens` array), which of them the package writes (none, in most items), and how a consumer sets the rest (a `:root` block in any stylesheet, a theme file after Yeti, a runtime `setProperty`; hues, chroma, and the scale only on `:root`, derived tokens on any element, `Y/src/guides/theming.md:38`). Two exceptions: a token a module wrote as state is a host style binding from a `computed` (`--yeti-range-value`), and one derived token as an input where a spec says why. Private `--_yeti-*` tokens are never read or written. The package ships, wraps, and generates no theme; a spec may cite Yeti's `soft` and `sharp` themes as examples. A theme's element rules go in `@layer yeti.theme`, whose validator refuses class, id, and attribute selectors (`theming.md:94-96`); a component's skin is token-only (`theming.md:115`).
- Colour scheme: the consumer's `color-scheme` declaration, which works on any element (`theming.md:52`); no directive offers a scheme input.
- Tailwind v4 beside the package ([Prototype: the package beside Tailwind v4 in one Angular application](issues/24-prototype-ngx-yeti-with-tailwind-v4.md), measured in three engines): with Tailwind first every `yeti` layer sits above `utilities`, so utilities lose on Yeti components; with Yeti first, preflight beats all of Yeti and 63 elements change. One shared statement in the consumer's global stylesheet, `@layer theme, base, yeti, components, utilities;` before both imports, keeps Yeti above preflight and utilities above Yeti, and still needs `@source not inline('container');`, because Tailwind otherwise generates `.container` over Yeti's; leaving out preflight (`@layer theme, yeti, utilities;` with the two layered Tailwind imports) gives Yeti markup identical to Yeti alone. Lazy loading and unloading behaved in every order. The statement lives in the consumer's global stylesheet, which component styles cannot set; the package documents the two forms (C1 with preflight, C2 without) in a consumer guide, and whether an `ng add` writes it is a later decision. Each spec whose item has a name Tailwind also generates (`container`, `grid`, `table`, `hidden`) notes it.
- Every item spec's Further Notes carries a "Styles" subsection: (1) the item file it loads and the mechanism's one line for the consumer (ticket 13); (2) the always-loaded rules it relies on; (3) the cross-part rules that touch it (a spinner in a button, a dropdown in a nav); (4) the tokens it reads and writes (the Tokens subsection); (5) what visibly breaks when the item file is missing; (6) the Tailwind name collision, if any.

### 1.14 Spec shape

A `/to-spec` spec keeps the template's top-level sections in order: Problem Statement, Solution, User Stories, Implementation Decisions, Testing Decisions, Out of Scope, Further Notes. The API-design material goes in as subsections (map, Spec shape, with its two substitutions):

Implementation Decisions:
1. Yeti contract: the item's manifest entry (class, attributes with vocabularies and defaults, markers, `children`, `tokens`, `a11y` and `support` blocks, module and events), and the attributes left to the consumer with their reasons (ticket 26).
2. Contract mapping: one row per class, attribute, marker, event, and token: the directive that binds the class; each attribute with its input, type, default, and the kind of its static form where its name is an HTML attribute (1.4); each marker with its part directive; each event with its output and `detail` type; each token the spec names with who sets it. A "Module replaced" subsection for an item with a module: each behaviour of the module kept, changed, or removed ([ADR 0040](adr/0040-package-replaces-yetis-optional-modules.md)).
3. Hierarchy and DI shape (tokens, host directives, parent discovery, generated ids and the platform's relationship attributes).
4. API per directive or component: inputs with Yeti's defaults and deltas, models, outputs, methods, `exportAs`.
5. Material comparison table (the nearest Material component's accessibility and API shape).
6. Implementation level and primitives, with the level's reason and the Aria or CDK building block with its `file:line` (1.2).
7. ARIA and keyboard tables (APG pattern, roles, states, keys, focus rules), and the ledger rows the item adds (1.10).
8. Rendered HTML: consumer markup and the resulting DOM, closed and open, server and hydrated.
9. Animation: Yeti's native-state transitions the item uses, any `animate.enter` or `animate.leave`, completion, reduced motion (1.6).
10. Rendering modes: server output, pre-hydration rules, what the platform does with no script, what never replays, behaviour inside `@defer` and hydrate blocks, `withI18nSupport()` (1.11).
11. Single-page application: what the item does on navigation and with fragment links (1.15).

Testing Decisions: the four layers from 1.12 by name, each with its story ids and cases, plus the manifest attribute-and-value check's coverage of the item.

Further Notes: usage examples, the design decisions table, the Styles subsection (1.13), platform features to adopt when the target moves (1.2), and the single-page-application pieces it relies on.

### 1.15 Single-page application behaviour

New for Yeti, from [Prototype: Yeti's modules in a single-page Angular app](issues/20-prototype-yeti-in-single-page-apps.md) (measured in three engines, production build under `<base href="/sub/">`) and [ADR 0040](adr/0040-package-replaces-yetis-optional-modules.md):

- Setup for Angular-rendered DOM is the directive's: a tabs root selects its first or bound tab when created, in any rendering mode, which `tabs.js` did only at load; the toc and the `enter` utility create their `IntersectionObserver` per instance in `afterNextRender` and disconnect on destroy.
- Closing on navigation: a popover or a modal dialog in the persistent shell stays open over the new route after a `routerLink` inside it, and the dialog leaves the page inert; the package closes open top-layer panels on `NavigationStart` with focus back on the opener (about 15 lines, measured). Whether this is one shared service or each item's own subscription is ticket 25's; either way it is removed on destroy (1.9). A panel inside a destroyed route is closed by its removal and needs nothing.
- Fragment links under `<base href>`: a bare `href="#id"` on `/sub/tabs` reloads the document to `/sub/#id`. A carousel dot, a toc link, and a tab deep link therefore go through the package: the carousel dot's directive scrolls the track and fires `slide` as `carousel.js` did, with no history entry; a toc link and a tab deep link set `location.hash` (which keeps the platform's `:target` and the browser's scroll) or navigate with the Router's `fragment`, and the spec states which and why, with ticket 20's finding that `routerLink` fires no `hashchange`. The user ruled that only `baseHref` is supported, never `deployUrl` (map, Standing rulings).
- Listeners: the package leaves none behind (Yeti as loaded left none either, measured); every `addEventListener` in code has its removal in `DestroyRef.onDestroy`.
- Each spec's Implementation Decisions item 11 states the item's behaviour on navigation and with fragment links, or "none".

The four shared-utility specs of ticket 11 are rows 50 to 53 above, decided 2026-10-02: the navigation closer is one function with no service (ADR 0041), because more than one item needs it (dialog, dropdown, nav, and through them shell) and no state is shared between instances; the fragment-link handling is one function plus one root service holding the document listener (row 51), because the toc, the carousel, and the tabs each need it; the events spec is types and rules; and id generation is a helper over CDK's `_IdGenerator` (ADR 0042).

A fifth shared spec, `setup`, was added by the user's choice of 2026-10-02, "Add a `setup` spec (Recommended)" (map, Standing rulings, Ticket 25's open items), after Part 2 was written, so it has no row above (noted 2026-10-03, audit 0003 M1). It owns the consumer-facing setup: the cascade-layer statement, the `assets` entry for the consumer's Yeti build, `provideYetiStyles()` ([ADR 0060](adr/0060-item-styles-are-counted-links-to-the-consumers-yeti-build.md)), the package's accessibility stylesheet (below), and `provideYetiFragmentLinks()` (row 51). Its building blocks are Angular providers and documented consumer files, custom Angular (4). The spec list is 54.

Shared pieces that have no spec of their own:

- **The package's accessibility stylesheet** (`@layer ngx-yeti`, ADR 0060 point 8): one small global file the consumer imports after the always-loaded group. Each rule belongs to the item spec whose ledger row it closes (A11Y-1a to A11Y-1f, A11Y-6), and the first spec to write a rule creates the file. The consumer-facing setup it is part of (the layer statement, the `assets` entry, `provideYetiStyles()`) is owned by the `setup` spec (above); the item specs own the rules, and `setup` owns how the file is loaded.
- **Keyboard:** Aria owns the keys where it is hosted (row 40); every other key handler compares `event.key` and uses `hasModifierKey` (1.5).
- **Focus-out, Escape, and focus return** are host listeners on the item (ADR 0043); no CDK a11y service is injected in the first milestone.

## Hydration constraints (2026-10-03)

The user required compliance with Angular's hydration constraints (map, Standing rulings). [Research: the decided records against Angular's hydration constraints](issues/33-research-decided-records-against-hydration-constraints.md) found these items for the owning specs:

- `accordion`: a `details` that ships open loses a toggle made before hydration; its `open` model is never bound to `[open]` (row 21).
- `demo`: writing `srcdoc` again with the same value reloads the frame in three engines (measured), so the spec builds the frame from the `code` input and decides how to avoid the second load.
- `table`: a usage rule requires an explicit `<tbody>`, because the browser inserts one and the DOM would differ from the server's.
- Every spec: a consumer writes no static attribute on an attribute a directive binds, because hydration writes static attributes again before the binding wins (tickets 18 and 30).
- Generated ids: equal on the server and the client by [ADR 0044](adr/0044-generated-ids-count-per-application-and-are-adopted-at-hydration.md), which replaces [ADR 0042](adr/0042-generated-ids-come-from-cdk-idgenerator-through-one-helper.md) points 1, 3, and 4.
