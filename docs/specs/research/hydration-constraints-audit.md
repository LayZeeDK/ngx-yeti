# Research: the decided records against Angular's hydration constraints

Ticket: [33. Research: the decided records against Angular's hydration constraints](../issues/33-research-decided-records-against-hydration-constraints.md). Written 2026-10-03 by Claude Opus 5.5. Records change only through the orchestrator's dated notes; this file proposes the changes and decides nothing.

## Sources

- Angular's hydration guide, `NG/adev/src/content/guide/hydration.md` at `5db6fc4453` (`NG` = `github.com/angular/angular`): the same DOM on both ends `:99`, server HTML not altered `:101`, direct DOM manipulation `:105-111`, valid HTML `:113-123` (`<table>` without `<tbody>` `:119`), `preserveWhitespaces` `:127-135`, no `isPlatformBrowser` branching `:216`, third-party scripts after hydration `:222-224`.
- Angular source at the same commit: `NG/packages/core/src/hydration/annotate.ts:243-262` (the server annotates only `appRef._views`, so `<head>` is outside the hydrated tree); `NG/packages/core/src/render3/instructions/shared.ts:596-599` with `NG/packages/core/src/render3/dom_node_manipulation.ts:141-155` (every static attribute of a claimed element is written again); `shared.ts:530-535` (a `null` binding calls `removeAttribute`); `NG/packages/core/src/render3/instructions/element.ts:349` and `text.ts:88` (the node-mismatch check runs only under `ngDevMode`); `NG/packages/core/primitives/event-dispatch/src/event_type.ts:295-364` (the replayed event list, which has no `command` and no `close`); `NG/packages/core/src/hydration/event_replay.ts:163` (replay starts at `whenStable`); `NG/packages/router/src/provide_router.ts:274-287` (the initial navigation starts in the bootstrap listener).
- Angular components at `708d4c6e2` (`NC` = `github.com/angular/components`): `NC/src/cdk/a11y/id-generator.ts:18` (counters in module state), `:24` (random infix per process), `:38-47` (`getId`); Aria asks for the infix (`NC/src/aria/tabs/tab.ts:62`, `tab-panel.ts:73`, `menu/menu-item.ts:65`, `accordion/accordion-panel.ts:71`, all with `true`).
- Prototypes: ticket 18 ([yeti-rendering-modes](../prototypes/yeti-rendering-modes/README.md), production builds), ticket 13 ([style-loading](../prototypes/style-loading/README.md), production builds), ticket 29 ([aria-carousel](../prototypes/aria-carousel/README.md), development build; [aria-accordion](../prototypes/aria-accordion/README.md)), ticket 30 ([aria-composition-roving](../prototypes/aria-composition-roving/README.md), development build).
- Two checks run for this audit, both read-only on the prototype workspaces:
  - **C1, `NG05xx` on the style-loading app.** Ticket 13's app (`D:/tmp/ngx-yeti-13/app`) built with `--configuration development` into this session's scratchpad (the workspace's own `dist/` untouched), served on port 4533 with `NG_ALLOWED_HOSTS=localhost`, loaded in Chromium 153, Firefox 155, and WebKit 26.6, every button clicked (which hydrates the `hydrate on interaction` block and opens the client-only `@defer`). Console in all three engines: "Angular hydrated 1 component(s) and 44 node(s), 0 component(s) were skipped. 2 defer block(s) were configured to use incremental hydration." No `NG05xx`, no warning, no page error. Item links in `<head>` afterwards: `stack`, `center`, `badge`, `alert`. Server stopped.
  - **C2, a same-value `srcdoc` write.** A plain page with an `<iframe srcdoc>`, then `setAttribute('srcdoc', <same value>)`, as hydration's write does. In all three engines the frame loaded a second time (`load` 1 to 2, its script ran 1 to 2 times) and a mark set in the frame's document was gone.
- Evidence weight: ticket 18's and ticket 13's runs were production builds, where Angular does not check node matching (`element.ts:349`, `text.ts:88`). Their "0 console errors" is not evidence that no mismatch happened. The development-build evidence is ticket 29's carousel, ticket 30, and C1.

## Audit

Verdicts: **complies**, **at risk** (complies as written but a likely reading or a gap breaks a constraint), **breaks** (the record prescribes something that breaks a constraint). Evidence: **measured** (with the prototype), **read** (with `file:line`), or **inferred**.

### Breaks and at risk

| # | Record or behaviour | Constraint at stake | Verdict | Evidence | What the record would need |
| --- | --- | --- | --- | --- | --- |
| 1 | `architecture-guide.md:193` P11 Preferred: "`[open]` bound from an `open` model on a dialog the page may ship open" | Server HTML not altered between server and client (`hydration.md:101`): state a person changed before hydration must survive it | **breaks** | **measured**, ticket 18 (`README.md:58`, the `[open]` row): an `[open]` bound to a signal closed a `details` the user opened before hydration, three engines. For `dialog`, the same binding mechanism is inferred, and an `open` attribute opens a dialog non-modally, against [ADR 0021](../adr/0021-dialog-is-a-directive-on-the-native-dialog.md) point 1 | Remove the example. Replace it with ADR 0021's form: `isOpen` is never bound to `open`; it is read from the element (the replayed `toggle`, or `dialog.open` in a render callback) and written only through `showModal()` and `close()` after hydration. |
| 2 | `architecture-guide.md:189` P11: "a `details` a page ships open" is the consumer's to set, and "Initial state is bound" (also `building-blocks.md:54`) | Same as row 1 | **breaks** | **measured**, ticket 18 (`README.md:57`, `:73`): a static `open` reopened a `details` the user closed before hydration; a bound `[open]` reset it too (row 1). **Read:** a static attribute is written again before the directives are created (`shared.ts:596-599`), and a binding's first client pass always writes | No template form keeps a pre-hydration toggle of a page-shipped-open `details` today. The record has to choose: (a) document that such a toggle is undone at hydration; or (b) seed the accordion item's model from the claimed element's `open` before the first binding pass, which is a read before the render callbacks that P12 does not allow and needs its own measurement. Until then, remove "Initial state is bound" for `open` and keep it for state no person can change before hydration (`aria-selected` once `tabs.js` is gone, `data-once`). |
| 3 | `building-blocks.md` row 21, `details[yetiAccordionItem]` with an `open` model written from a `toggle` host listener | Same as row 1 | **at risk** | **measured**, ticket 29 accordion (A): with the model written only from `toggle`, an early open stays open and the replayed `toggle` sets the model (`aria-accordion/README.md:43`). **Measured**, ticket 18: binding the model to `[open]` closes it again | Say the model is never bound to `[open]`; a programmatic change writes `open` only from a change made after hydration (inferred: an `afterRenderEffect` that skips its first run). | 4 | [ADR 0042](../adr/0042-generated-ids-come-from-cdk-idgenerator-through-one-helper.md) points 1, 3, 4, and `building-blocks.md:69` ("Generated ids differ between server and client, which is harmless") | Same DOM on both ends (`hydration.md:99`) and server HTML not altered (`:101`) | **at risk** (resolved by ADR 0044, 2026-10-03) | **measured**, ticket 30 (`aria-composition-roving/README.md:78`): Aria's ids change at hydration (`ng-toolbar-widget-a72575-*` on the server, `-a17645-*` live; `ng-tab-*` and the `aria-controls` and `aria-labelledby` pointing at them likewise), because Aria passes `true` for the random infix (`id-generator.ts:24`, `:47`; `tab.ts:62`). No `NG05xx` results, because hydration does not check attribute values, but every generated id and every reference to one is rewritten at hydration | Replace "may differ" and "harmless" with the requirement that the server and the client render the same ids. Concretely: (1) point 1's helper counts per application (a root `@Service()` is created per request on the server), not in CDK's module-level map; then a fully hydrated tree gets the same ids at both ends because construction order is the same (inferred, to be measured in the generated-ids spec). (2) Point 4 is reversed: an Aria-hosted element receives the package's id through Aria's `id` input, as ticket 30's `tabs` did, instead of keeping Aria's random-infix id. (3) Inside a `hydrate on ...` block, construction order differs between the server and the client, so a part there needs a consumer `id` or accepts a rewritten id (ADR 0011 clause 7 stays). |
| 5 | Static attributes re-applied at hydration (ticket 18; [ADR 0003](../adr/0003-directives-set-yetis-class-attributes-and-markers.md) point 4; [ADR 0011](../adr/0011-rendering-modes-contract-for-yeti.md) clause 1), including a consumer's static attribute that a directive overrides by binding | Server HTML not altered (`hydration.md:101`) | **at risk** | **measured**, ticket 18 (`README.md:73`): every static attribute of every claimed element is written again; `open`, `aria-selected`, and `data-once` came back. **Measured**, ticket 30 (`README.md:74`): a consumer's static `role="group"` on `yetiButtons` was written back during hydration (`toolbar -> group -> toolbar`, three engines) before the package's `[attr.role]` restored `toolbar`. **Read:** `shared.ts:599`, `dom_node_manipulation.ts:141-145` | ADR 0003 point 4 already forbids a static template attribute for state a person or a module can change. Add the second case: a consumer never writes a static attribute that a directive on the same element binds (`role` on `yetiButtons`, any of ADR 0070's owned `data-*`), because hydration writes the static value back for one pass. The `buttons` spec either takes `role` as an input or states the rule. Static host attributes a directive never changes (ADR 0070's P markers, `data-ngx-yeti-item`) are safe: the rewrite is the same value. |
| 6 | [ADR 0070](../adr/0070-where-a-yeti-attribute-sits-decides-its-mapping.md) rule 1 and its last paragraph: an unset input removes a consumer's static attribute (`setElementAttribute` calls `removeAttribute` for `null`) | Server HTML not altered (`hydration.md:101`) | **at risk** | **read:** the server writes the static attribute, then the binding removes it, so the server HTML has none; at hydration `shared.ts:596-599` writes it back and the first update pass removes it again (`shared.ts:530-535`). **Inferred** that both happen before a paint; the same pattern measured as a flip in ticket 30 (row 5) | The record already says a consumer writes no Yeti `data-*` attribute. Give the hydration reason beside the existing one, and name the `$any` binding as the only escape hatch for an owned attribute (it already does). A development-mode check for a static owned attribute is a later-milestone check (ADR 0018). |
| 7 | `building-blocks.md` row 30, the `demo` component's `srcdoc` iframe | Server HTML not altered (`hydration.md:101`); no direct DOM reads before hydration (`:105-107`); consistent rendering (`:216`) | **at risk** | **measured**, C2: writing `srcdoc` with the same value reloads the frame in Chromium, Firefox, and WebKit (its script runs again, its document state is lost). **Read:** hydration writes a static attribute again (`shared.ts:599`), and a bound one is written on the first client pass (ticket 30 measured such same-value writes at hydration, `README.md:73`). So the frame loads once from the server HTML and again at hydration (inferred for the Angular build; not measured in an Angular app). **Inferred:** building `srcdoc` from a projected `<pre>` needs a DOM read, which P12 puts in a render callback, so the server HTML would have no `srcdoc` and the client would add it, which is rendering that differs by platform | The `demo` spec takes the code from the `code` input, not the projected `<pre>`, so `srcdoc` is the same on both ends. It then measures the reload at hydration in an Angular build and either documents it (a docs-only item) or renders the frame after hydration and says so for no-JavaScript readers. The `ResizeObserver` in `afterNextRender` complies. |
| 8 | `building-blocks.md` row 39, the `table` item's markup | Valid HTML: no `<table>` without `<tbody>` (`hydration.md:119`, `:123`) | **at risk** | **read:** the directives sit on the consumer's `<table>`, `<tr>`, `<th>`, `<td>`; no record requires `<tbody>`. Every table in Yeti's docs and examples has one (14 of 14 counted in `docs/`, `src/components/table/`, and `src/guides/` of the `f52d1e8b9` export at `D:/tmp/ngx-yeti-18/yeti`). **Inferred:** a consumer template with `<tr>` straight under `<table>` renders that way on the server and gets a parser-made `<tbody>` in the browser, a node mismatch | The `table` spec states "always write `<thead>`/`<tbody>` as Yeti's markup does" as a usage rule, and its SSR smoke test uses a `<tbody>`. The directive cannot repair consumer markup. |
| 9 | [ADR 0041](../adr/0041-closing-on-navigation-is-a-per-instance-subscription.md), close on `NavigationStart` | Server HTML (and the state a person set before hydration) not altered (`hydration.md:101`) | **at risk** | **read:** the initial navigation starts in the Router's bootstrap listener, after the root view is hydrated (`provide_router.ts:274-287`), and replay starts only at `whenStable` (`event_replay.ts:163`); `command` and `close` are not replayed (`event_type.ts:295-364`). **Inferred:** a panel whose open state comes from a replayed `toggle` is not open yet when the initial `NavigationStart` fires, so it survives; but a panel whose directive learns it is open by reading the element in a render callback (the dialog has no replayed event to learn it from) may subscribe before that `NavigationStart` and close a dialog the user opened before hydration | Point 1 ignores the application's initial navigation (the function subscribes only after the first `NavigationEnd`, or skips the first `NavigationStart`). The navigation-close spec's e2e layer adds one case: open the shell dialog before hydration, release the bundle, assert it is still open. |
