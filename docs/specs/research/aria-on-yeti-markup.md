## Question 54: Aria's selectors are attribute selectors, its host bindings are not markup-free

**Read.** Of Aria's 29 public directives, 24 have a bare attribute selector and can sit on any element. The other five require `ng-template`, because each creates its view as lazy content through Aria's `DeferredContent`: `ng-template[ngAccordionContent]` (`accordion/accordion-content.ts:31`), `ng-template[ngTabContent]` (`tabs/tab-content.ts:30`), `ng-template[ngMenuContent]` (`menu/menu-content.ts:31`), `ng-template[ngComboboxPopup]` (`combobox/combobox-popup.ts:30`), and `ng-template[ngTreeItemGroup]` (`tree/tree-item-group.ts:43`). So the user's reading is right: Aria does not choose Yeti's elements. Ticket 29's accordion lost 13 of 14 Yeti selectors because it used Aria's documented markup, not because Aria needs that markup.

What Aria does impose is its host bindings. These are the ones that can meet Yeti's markup on the five patterns that bear on a ledger gap (read):

Three behaviours sit outside the bindings and recur below (read):

- Aria sets its roving `tabindex` and its first active item in `afterRenderEffect`, which never runs on the server (`toolbar.ts:103`, `tab-list.ts:137-153`, `menu.ts:191`, `menu-bar.ts:124`). That is upstream bug candidate A5. A menu opened from a trigger never gets a default active item before it is opened (`private/menu/menu.ts:214-221`).
- Aria's keyboard handler calls `preventDefault()` and `stopPropagation()` on every key it handles (`private/behaviors/event-manager/keyboard-event-manager.ts:31-35`). That stops a `summary`'s own Enter and Space and a link's own Enter.
- Every generated id asks `_IdGenerator` for the random infix (`true` at each line cited in the table), so it changes at hydration unless the package passes an `id` in (ticket 30, measured; ticket 33 row 4).

## M1: Aria Accordion on `summary` with its `role` and `inert` overridden

Ticket 30 left two accordion conflicts open: `role="button"` on `summary` (not allowed by ARIA in HTML, read there), and Aria's `inert`, which a constant override removed only until the first toggle (measured there). It inferred that a binding that changes whenever Aria's does would hold. That changes this ticket's accordion row, so it was measured.

**Setup.** Ticket 29's accordion workspace `D:/tmp/ngx-yeti-29-accordion/ws`, one new route `/c32` (`src/app/pages/pages-32.ts`, and one line in `app.routes.ts`). It is ticket 30's variant C (same `yetiAccordion` and `details[yetiAccordionItem]` directives, content projected, `[attr.open]` kept in sync) with two changes:

```ts
// summary[yetiAccordionTrigger32], hosting AccordionTrigger
host: { '[attr.role]': 'null' },
// [yetiAccordionPanel32], hosting AccordionPanel
host: { '[attr.inert]': 'aria.visible() ? null : undefined' },
```

The panel's value changes in every pass where Aria's `visible()` changes, and both `null` and `undefined` remove the attribute (`NG/packages/core/src/render3/instructions/shared.ts:530`; a binding writes when `Object.is` says the value changed, `NG/packages/core/src/render3/bindings.ts:54`). Host-directive bindings run first, so the package's write is last in the same pass. Development build (`ngDevMode` on, so Angular checks node matching), served on port 4632, stopped afterwards. Playwright 1.63.0 (Chromium, Firefox, WebKit) and axe 4.13.0 from that workspace. The probe script and its JSON output were kept in this session's scratchpad only.

**Results (measured, the same in all three engines unless stated):**

- Server HTML: no `role` on any `summary`, no `inert` on any panel, in the hydrated copy and inside `@defer (hydrate never)`. Panels keep `role="region"` and `aria-labelledby`.
- JavaScript off: a fragment link to the closed second panel opens it, and the panel is visible and not inert. Inside `hydrate never` nothing is inert.
- At hydration: `role="button"` is written back to each `summary` and removed again by the package's binding in the same pass (the `toolbar -> group -> toolbar` shape ticket 30 measured on `buttons`). Each trigger's generated id changes (server `ng-accordion-trigger-a89605-*`, live `-a83561-*` in Chromium), so the panels' `aria-labelledby` is rewritten too.
- After hydration: open item 1, open item 2 (which closes item 1), close item 2. After every step no panel has `inert`. The observer records Aria writing `inert="true"` and the package removing it in the same pass each time, and the attribute is never present when read afterwards. `window.find()` then finds the closed second item's text in Chromium, Firefox, and WebKit, where ticket 30's C did not find it in Chromium and Firefox. (The item's `open` was read in the same task, so whether Firefox then opened it, as ticket 30's (A) did, was not compared.)
- Keyboard after hydration: Enter opens item 1 through Aria with `open` kept in sync, ArrowDown moves focus to item 2, and Space opens item 2 and closes item 1. Removing the role does not stop Aria's keys.
- A click on item 2 before hydration stays open after hydration, and the model reads `false,true` (ticket 30's constructor read of `open` is still in the item directive).
- Chromium's own tree (CDP): each `summary` is `DisclosureTriangleGrouped`, the native role, not `button`; the open panel is `region "Can I use my own class names?"`. axe: 0 violations in all three engines.
- Console: no `NG05xx` error and no hydration warning. Aria's development warning "ngAccordionPanel must have an ngAccordionContent to render." once per hydrated panel, as in ticket 30.

Not re-measured here, and still open from ticket 30 because the `details` directive is unchanged: a fragment link followed before hydration ends shut in Chromium and WebKit, and an item the server rendered open and the visitor closed before hydration would reopen (inferred there).

### Notes per row

- **Row 1.** M1 moves the role and `inert` conflicts from inferred to measured. What is left is the `open` sync. It exists only because Aria's keydown handler cancels the `summary`'s own Enter and Space, so Aria has to own the open state and `open` has to follow it. An imperative `open` write after hydration in place of the binding was not tried. Aria's arrow, Home, and End keys are optional in the APG. Yeti's docs already advise a heading inside `summary` (`accordion/docs.md:36`), and ticket 30 measured it in Chromium and Firefox.
- **Row 2.** Part 2's row 27 and ledger A11Y-12 describe a consumer composition. Ticket 30's fit needs the package's directives to host Aria's, because the `tabindex` override relies on host-directive bindings running before the host's.
- **Row 3.** A11Y-4's slide `role="group"` with `aria-roledescription="slide"` and the Tabs pattern's `role="tabpanel"` want the same element. The APG's tabbed carousel uses `tabpanel` with the slide role description. That changes ledger A11Y-4, so it is the user's call if Tabs is ever reconsidered.
- **Rows 4 to 6.** Aria Tree was read in ticket 29 and not built. Its child group must be `ng-template[ngTreeItemGroup]`, which is lazy content and replaces the nested `div[popover]` (`tree-item-group.ts:43`). It has no focus-out closing for a sheet, so it addresses no ledger gap.
- **Row 7.** With JavaScript off, ticket 30's composition draws one tab as selected and gives one Tab stop, where Yeti's no-script page has none selected and every tab reachable (measured). That is the A11Y-17 feature itself, not a conflict.

## Items where no Aria pattern fits any gap

Aria's eight patterns are Accordion, Combobox, Grid, Listbox, Menu (with Menubar), Tabs, Toolbar, and Tree (`NC/src/aria/`, listed). None addresses these ledger gaps (read):

- **Forced colours**: `button` (A11Y-1a), `buttons` (A11Y-1b, as well as row 2's A11Y-12), `tabs` (A11Y-1c), `field` (A11Y-1d), `progress` (A11Y-1e), `pagination` (A11Y-1f). These are CSS rules, and Aria ships no CSS.
- **`tooltip`** (A11Y-2, Escape dismissal): Aria has no tooltip pattern.
- **`demo`** (A11Y-7, the window splitter's `aria-controls` and Enter): Aria has no splitter.
- **`dialog`** (A11Y-8, Tab leaving into browser UI): Aria has no dialog. The candidate is CDK's `FocusTrap` (row 31).
- **`center`** (A11Y-9, reflow) and **`timeline`, `layer`, `breakout`, `media`, `lede`** (A11Y-10a to 10e, contrast): CSS and test checks.
- **`spinner`** (A11Y-13): accepted under WCAG 2.2.2's exception, no behaviour to add.
- **`field`** (A11Y-6, A11Y-14, A11Y-19): the required marker is CSS. `aria-invalid`, `aria-describedby`, and the ready signal come from Angular forms state. Listbox and Combobox are composite widgets, and Yeti's controls are native `input`, `select`, and `textarea`.
- **`navigation-close`** (A11Y-15) and **`fragment-links`** (A11Y-16): Router and URL behaviour. No widget pattern applies.

The other items have no ledger gap, so the user's rule gives no reason to reach for Aria there. Patterns that could look applicable: Grid for `grid` and `table` (a layout and a static table, not a composite; rows 9 and 39), Listbox or Combobox for `field`'s `select`, Toolbar for `pagination` or `breadcrumbs` (link lists with `aria-current`, met by Yeti's markup), and Tree for `toc` and `nav`.

## Where the findings differ from building-blocks Part 2 today

- **`buttons` (row 27):** the rule leads to Aria Toolbar hosted by the package. Part 2 says the consumer writes `ngToolbar` and the package does not host it, and that form fails the server-HTML contract (ticket 29, measured).
- **`tabs` (row 40):** the same level (Aria). The row's shape needs the `tabindex` hand-over, the `id` input, and no `hidden` or `inert` in the server HTML, and the last of these contradicts ledger A11Y-17's layer-3 assertion.
- **`accordion` (row 21):** the level stays native unless the user wants Aria's `aria-controls` and `region` without Aria. Then two custom bindings would be added (inferred, not built), and A11Y-11 would read differently from its current "None".
- `carousel`, `dropdown`, and `nav` (rows 29, 32, 34): the same outcome as Part 2.
