# Rendering-modes contract for every directive and component over Yeti

Adapted from ADR 0008 (`rendering-modes-contract`) of `.scratch/next-foundation-specs/`, with one clause lifted from the consequences of its old map ADR 0011 (`button-listener-free-disabled-contract`), by [Decide: which ADRs carry over](../issues/08-decide-inherited-adrs.md). Those records bound nothing here. The requirement itself, that every directive and component supports `@defer` with hydrate triggers, SSR, prerendering, full and incremental hydration, event replay, and `withI18nSupport()`, is this map's "Rendering modes" note: the user's decision in the old bundle, restated for this map in the user's standing ruling ("We must not forget about support for `withEventReplay()`, `provideClientHydration()`, [incremental hydration](https://angular.dev/guide/incremental-hydration), and `withI18nSupport()`."). This record is the contract that meets it; its wording is this map's.

In Angular 22.2 `provideClientHydration()` alone already includes incremental hydration and, through it, event replay ([Prototype: Yeti under SSR, hydration, `@defer`, event replay, and `animate.enter` and `animate.leave`](../issues/18-prototype-yeti-rendering-modes.md), read and measured). The old contract's facts about hydration, replay, `ngSkipHydration`, and generated ids are in the old bundle's `research/angular-rendering-modes.md`; ticket 18 measured what is new with Yeti.

We decided, clause by clause:

1. **First-paint state is a host binding on signal state** (carried). Server HTML is the consumer's markup plus host bindings, so crawlers, no-JavaScript users, and dehydrated blocks see Yeti's documented markup and Yeti's CSS styles the first paint. State a person or a Yeti module can change before hydration is Angular-owned, never a static template attribute, because hydration writes every static attribute again ([ADR 0003](0003-directives-set-yetis-class-attributes-and-markers.md) point 4, measured in ticket 18).
2. **The platform's opening mechanism stays in the server HTML** (new, replacing the old clause "primary activation is a `click`/`keydown` host listener"). `commandfor` and `command`, `popovertarget`, `popover`, and `<details>` act before hydration and with no script, measured in ticket 18; the directive renders them and observes `command`, `toggle`, and `close` ([ADR 0003](0003-directives-set-yetis-class-attributes-and-markers.md) point 5). Where the package does own activation (a tab selection, a carousel control), the host listener changes state before any `preventDefault()`, as the old clause required, because replay reaches only template and `host` listeners on native events.
3. **No host `click` listener on an `<a>` whose navigation must stay native inside a deferred region** (lifted from old ADR 0011's consequences). Angular's dispatcher calls `preventDefault()` on a click whose action element is an `<a>` carrying `jsaction` while it dispatches it (`packages/core/primitives/event-dispatch/src/dispatcher.ts:127-140`, read in the 22.2.x clone), so such a listener cancels the link's navigation inside a still-dehydrated block. This touches Yeti's breadcrumbs, pagination, nav, and toc links; the specs that own fragment links decide their own handling (ticket 20 measured an interceptor for them).
4. **Browser-only work lives in render callbacks** (carried). Every DOM read, write, observer, `matchMedia`, timer, and focus call runs in `afterNextRender` or `afterRenderEffect`. Under zone.js, timers and observers start outside the Angular zone; under zoneless change detection, which every spec must support (the user's standing ruling 43), any value they write that a template reads is a signal, because a plain field written from a listener does not refresh the view zoneless (measured in ticket 18).
5. **No directive relies on a Yeti module's load-time setup** (new). Client-rendered `@defer` content, `@if`, and routed views miss the setup Yeti's modules perform once at load (measured: [ticket 18](../issues/18-prototype-yeti-rendering-modes.md) for `@defer`, [Prototype: Yeti's modules in a single-page Angular app](../issues/20-prototype-yeti-in-single-page-apps.md) for routes). [ADR 0040](0040-package-replaces-yetis-optional-modules.md) has since decided that the package replaces every module and that none is loaded beside it; this clause is the rendering-modes reason for that.
6. **Hover opening uses `pointerenter`, which is not replayed** (carried, for any item whose spec keeps a hover trigger, such as Yeti's dropdown `data-trigger="hover"`).
7. **A composite widget, and a part with the element its id attributes name, share one hydration boundary** (carried, with a new reason). The package's generated ids come from counters held in module state (`_IdGenerator`, `src/cdk/a11y/id-generator.ts:18`, read), so the server's ids and the client's can differ; both ends get the client's id when they hydrate in the same pass, but a `commandfor`, `popovertarget`, `aria-describedby`, `aria-controls`, or `aria-labelledby` whose two ends hydrate at different times points at a stale id between the two hydrations (inferred, not measured). A consumer's static `id` avoids it and is what a deep link needs anyway ([ADR 0013](0013-parts-name-their-targets-by-reference.md)).
8. **Deep links need consumer ids** (carried).
9. **Content is projected by default** (carried). An open panel's content is in the server HTML; Aria's `ng-template` content directives are an opt-in lazy mode where a spec offers one.
10. **The package's templates contain no `@defer`, and each item is its own entry point** (carried), so a consumer's `@defer` block splits per item. The same split is what puts a part's `styleUrl` styles into the item's own lazy chunk ([Research: Yeti's styling model](../issues/04-research-yeti-styles-and-lazy-loading.md), measured); the loading mechanism itself is [Decide: how component styles load and unload](../issues/13-decide-style-loading.md)'s.
11. **The package never uses `ngSkipHydration` or Shadow DOM encapsulation** (carried). A component with `i18n` blocks is serialised with `ngSkipHydration` and re-rendered destructively unless the application provides `withI18nSupport()`, even in a source-locale build (measured in ticket 18), so the package's documented setup includes `withI18nSupport()` wherever the application uses `i18n`.
12. **A persistent server-rendered element never takes `animate.enter`**, because it plays at hydration ([ADR 0010](0010-animation-is-yetis-css-with-class-form-enter-and-leave.md) point 3).

## Considered options

- **Angular click handlers as the primary activation, as the old contract had it.** Rejected for Yeti's opening items on the measurement in clause 2: the platform's attributes work before hydration and with no script, while a handler waits for replay, and `dialog` `close` is never replayed.
- **The old contract's breakpoint clauses** (render the Server breakpoint's mode on the server and state the post-hydration swap; express a breakpoint-gated hidden state in Foundation's visibility classes). Abandoned: Yeti has no breakpoint and nothing that asks the window how wide an element is (`src/guides/migrating.md:111`); its thresholds are container queries and flex-basis arithmetic, which render correctly from the server HTML with no script.
- **Detecting replay with the internal `eventPhase` constant.** Not adopted, as in the old record: the constant is not public.
- **One entry point for the whole package.** Rejected, as in the old record: a consumer's `@defer` could not split per item.

## Consequences

- Each spec carries a Rendering modes subsection: server output, what it must not touch before hydration, which events replay, its hydration boundary, and its behaviour inside a client `@defer` block, a `hydrate on ...` block, and a `hydrate never` block. Each has an SSR smoke test in the node-level layer ([ADR 0014](0014-testing-stack-for-yeti.md)).
- A `hydrate never` block keeps native behaviour and loses Angular's; ticket 18 measured that it also loses a `styleUrl`'s styles when the last live instance leaves, which [ticket 13](../issues/13-decide-style-loading.md) must answer.
- Yeti `yeti:*` events are not replayed by any mechanism ([Research: binding Yeti's `yeti:*` events](../issues/16-research-yeti-events-in-angular-templates.md), measured), so a spec that maps one to an `output()` states that it does not fire for activity before hydration.
- 2026-10-03: the user ruled on JavaScript off (map, Standing rulings): "#55 For JavaScript off, consider both Angular SSR/hydration and prerendering/SSG: Option 1." With SSR and hydration, and with prerendering, the package guarantees that every item stays readable and its native controls keep working with JavaScript off. Each spec lists what is lost, and e2e tests run the SSR and the prerendered builds with JavaScript disabled. A client-only application gets no such promise.
- 2026-10-03: two rulings refine this contract (map, Standing rulings). First, no directive binds `open`: the state is read once from the element and then follows native events, so a toggle made before hydration survives ([Prototype: subclassing Aria's directives, and `[open]` against `[attr.open]`](../issues/34-prototype-subclassing-aria-and-open-binding-forms.md)). Second, where the package fits Aria, it does so by composition, giving one Tab-reachable item and no `inert` in the server HTML. `tabs` shows every panel with JavaScript off.
- 2026-10-03 (audit 0003 L8): clause 7's "inferred, not measured" is now measured for Aria's ids: [ticket 30](../issues/30-prototype-fitting-aria-by-directive-composition.md) found that Aria's generated ids differ between the server HTML and the hydrated page, and [ticket 33](../issues/33-research-decided-records-against-hydration-constraints.md) rated the id rewrite at risk under the hydration ruling. See the 2026-10-03 note on [ADR 0042](0042-generated-ids-come-from-cdk-idgenerator-through-one-helper.md); [Decide: hydration-safe generated ids](../issues/35-decide-hydration-safe-generated-ids.md) settled it in [ADR 0044](0044-generated-ids-count-per-application-and-are-adopted-at-hydration.md).
- 2026-10-03: [ADR 0044](0044-generated-ids-count-per-application-and-are-adopted-at-hydration.md) makes generated ids equal on the server and the client (measured in Chromium, Firefox, and WebKit under full hydration, `hydrate on`, `hydrate never`, a client-only `@defer`, and a growing `@for`). Clause 7's reason, that the ids can differ, no longer holds. A consumer's static `id` is still what a deep link needs.
- 2026-10-03 ([ticket 50](../issues/50-decide-open-points-of-the-specs.md), decision 113; the orchestrator's, not the user's): for `buttons`, "one Tab-reachable item" above holds only once Aria is live. Until then, with JavaScript off, before hydration, and inside `hydrate never`, every member of a toolbar keeps its native Tab stop: `yetiButtonsItem` binds `[attr.tabindex]` to `null` while no member is `active()`. Aria's arrow keys need the client, so a first-member-only Tab stop would leave members 2 to n out of keyboard reach, against this record's JavaScript-off guarantee. Once live, members 2 to n take `tabindex="-1"`: a state change after hydration, as `tabs` adds `hidden` once live. `tabs` keeps one Tab stop, the selected tab, because a tablist's keyboard model differs and every panel shows with JavaScript off.
- 2026-10-03 ([ticket 50](../issues/50-decide-open-points-of-the-specs.md), decision 227; the orchestrator's, not the user's; audit 0004 M17): clause 7's rule stays, with a new reason. Its id reason is retired by [ADR 0044](0044-generated-ids-count-per-application-and-are-adopted-at-hydration.md), which measured equal ids across hydration boundaries. The rule now rests on behaviour: a part registers with its root through a token or a template reference, the listeners that carry the item's behaviour (the dialog's Backdrop press, focus return, outputs, and closing on navigation; the dropdown's and the nav's focus-out on the root) sit on one end, and a pre-hydration event replays only when the boundary holding its listener hydrates. So a widget split across two boundaries keeps its platform links but loses or delays that behaviour. This is the orchestrator's reading of the sources, not measured; decision 227 holds the options and how to overrule it.
