# Directives set Yeti's class, attributes, and markers from typed inputs; the consumer writes none, and state stays native

Adapted from old map ADR 0039 (`directives-manage-every-foundation-class`) and ADR 0001 (`directive-first-with-named-exceptions`) of `.scratch/next-foundation-specs/`, by [Decide: which standing preferences and user rulings carry over](../issues/07-decide-inherited-preferences-and-rulings.md). Those records bind nothing here; this one does. The old class rule came from the user's own words of 2026-09-27, recorded there: "Generally, consumers should not write any CSS classes for any of our components/directives. All Foundation for Sites and NFS classes are managed by the Angular components/directives." The adaptation below is the orchestrator's and this map's, not the user's.

Yeti's contract is not Foundation's. Each of the 49 items declares exactly one class and an empty `classes` array (`src/components/card/manifest.json`, `src/components/button/manifest.json`); its looks come from `data-*` attributes drawn from 32 frozen vocabularies, not from variant classes; its parts are marked by 31 markers; and its state is taken from the element or from ARIA, by design -- "No component invents a state attribute" (`src/guides/components.md`, "State is native"), with `:hover`, `:focus-visible`, `:disabled`, `[aria-pressed]`, `[aria-busy]`, `:checked`, and `:user-invalid` as the seven hooks. Class names, attribute names and their value lists, vocabularies, and marker names are frozen from `7.0.0-beta` (`src/guides/stability.md:15-18`).

We decided the contract rule for this package:

1. **The class.** Each item's directive binds its one class as a static host class. A consumer writes the element and the directive attribute (`<article nfsCard>`), never `class="card"`.
2. **Attributes and markers.** Every `data-*` attribute and marker the item declares is set from a typed input, named from the attribute in camelCase and typed by its vocabulary ([ADR 0005](0005-closed-unions-from-yetis-vocabularies.md)). A consumer writes no `data-*` attribute of Yeti's. [Decide: how the package maps each of Yeti's `data-*` attributes](../issues/26-decide-yeti-data-attributes-mapping.md) makes the per-attribute call and names the exceptions.
3. **State stays native.** The package binds no state class, because Yeti has none. Where the state is the consumer's (`role="status"` on an alert, `required` on a control, a `<details>` a page ships open), the consumer sets it. Where a directive owns the state, it binds the ARIA attribute Yeti's CSS reads (`aria-pressed`, `aria-busy`, `aria-current`, `aria-invalid`, `aria-selected`, `hidden`).
4. **Pre-hydration state is Angular's.** An attribute a person or a Yeti module can change before hydration is Angular-owned state, not a static template attribute, because hydration writes every static attribute again ([Prototype: Yeti under SSR, hydration, `@defer`, event replay, and `animate.enter` and `animate.leave`](../issues/18-prototype-yeti-rendering-modes.md), measured in three engines: a static `open` reopens a closed `details`, a static `aria-selected="true"` leaves two tabs selected after `tabs.js` moved the selection, and a restored `data-once` stops the arrival from ever playing).
5. **The platform's opening attributes stay in the markup.** `popovertarget`, `popover`, `commandfor`, and `command` are rendered by the directive, with generated ids, and the directive observes `command`, `toggle`, and `close` rather than owning activation with a click handler. Measured: with JavaScript off the dialog opens by invoker commands, the dropdown by `popover`, and the accordion by `details` ([ticket 18](../issues/18-prototype-yeti-rendering-modes.md)), while a click handler waits for replay. Angular's DOM schema has no property for any of them ([Research: Yeti's JavaScript modules and what Angular adds](../issues/03-research-yeti-javascript-and-angular.md) 4.1), so they are attribute writes.
6. **Directives first.** Attribute directives on the consumer's markup. A component only where a part needs structure the consumer should not hand-write, or where a `styleUrl` is what makes lazy styles meet the requirements under the user's standing ruling 28 (map, Standing rulings); [Decide: how component styles load and unload](../issues/13-decide-style-loading.md) decides whether that condition is ever met.

## Considered options

- **The consumer writes Yeti's classes and attributes, and a directive adds behaviour to them**, which is what the old ADR 0001 (`directive-first-with-named-exceptions`) held before the user's class rule. Rejected: the user's ruling behind ADR 0039 was about the consumer never writing the framework's classes, and the same reasoning covers an attribute whose value list the package can type. It would also leave a misspelt `data-varaint` or `data-variant="prmary"` silent, which a typed input turns into a compile error.
- **Classes bound by directives, attributes left to the consumer.** Rejected: in Yeti the attributes are what the variant classes were in Foundation, so the split would carry the old rule's letter and not its point.
- **The directive owns native state too**, binding `disabled`, `required`, and `checked` from inputs. Rejected: those are the element's own attributes, Angular Forms selects its value accessors by `type`, and the old map measured the hazard of a package owning what the platform already owns. The package binds only state it computes.
- **Angular click handlers in place of invoker commands and `popover`.** Rejected on the measurement in point 5: it would lose the no-script and pre-hydration behaviour that is Yeti's strongest property.

## Consequences

- Every spec's contract mapping has a row per class, attribute, marker, event, and token, replacing the old map's CSS class mapping.
- A consumer's markup keeps Yeti's element structure and carries directive attributes where Yeti's docs carry classes and `data-*` attributes. Host bindings render on the server, so the server HTML is still Yeti's documented markup and Yeti's CSS styles the first paint.
- No copied-class problem exists, and no development check for one is needed.
- Where Yeti's docs ask the author for ARIA the markup must carry (`aria-label` on a nav, `role="status"` on an alert, `aria-labelledby` on a dialog), the spec says whether the directive generates it, requires it, or leaves it, and the accessibility ledger records what the package adds.
- The frozen surface is what the inputs are named after, so a Yeti pin move inside `7.x` adds values rather than renaming them ([Decide: which Yeti version the specs target](../issues/12-decide-yeti-version-policy.md) sets the pin policy).
