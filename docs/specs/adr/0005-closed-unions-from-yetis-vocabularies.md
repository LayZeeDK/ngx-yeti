# Every typed input is a closed union of its Yeti vocabulary's values

Adapted from ADR 0040 (`variant-input-types`) of `.scratch/next-foundation-specs/`, by [Decide: which standing preferences and user rulings carry over](../issues/07-decide-inherited-preferences-and-rulings.md). That record bound nothing here. It was decided by a panel under the user's rulings of 2026-09-27, whose requirement carries: typed inputs for every look, and, in the user's own words relayed in Decide: typed Variant inputs over open Sass maps (old map ticket 81, `decide-typed-variant-inputs-open-sass-maps`), "Ideally, a misspelt palette or size name fails to compile." The mechanism below is this map's, not the user's.

ADR 0040 built registries, consumer-side declaration merging, a generator from the consumer's Sass, an Nx sync generator, and a CI sync check, because Foundation's value lists were open Sass maps a consumer could extend or shrink. Yeti's are not. Its 32 vocabularies are closed lists in `schema/vocabulary.json`, frozen from `7.0.0-beta` so that a value may be added and none removed or renamed (`src/guides/stability.md:16-17`), and no Yeti setting generates a class or a value, because every input is a runtime custom property ([Research: Yeti's styling model, and loading component styles lazily](../issues/04-research-yeti-styles-and-lazy-loading.md) 4.3).

We decided that each typed input's type is a closed union of its vocabulary's values, exported from the package and nothing more: no registry interface, no declaration merging, no generator, no sync generator, no CI sync check, and no runtime value check. An attribute that declares its own `values` rather than a vocabulary takes a union of those values. A boolean attribute or marker takes a boolean input with `booleanAttribute`. The union's source is the built manifest and `schema/vocabulary.json` at the pinned commit, so the types move with the pin, and [Decide: which Yeti version the specs target](../issues/12-decide-yeti-version-policy.md) says how.

## Considered options

- **Carry ADR 0040's registries and generator over.** Rejected: there is nothing for a consumer to extend. A consumer who wants a look Yeti does not ship writes their own class on their own element, which every version of the class rule has allowed, and which cannot be typed as a Yeti value without claiming Yeti renders it.
- **An open union (`'primary' | (string & {})`).** Rejected: measured in the old bundle to accept typos, and it fails the user's stated ideal for no gain here, since the value list is closed.
- **A closed union plus a development-mode runtime check for a bound value.** Not in the first milestone, under the carried-over Milestones ruling: every check is specified but implemented in a later milestone. A literal value is caught at compile time; a value computed at run time is a rule the spec states as documented usage.
- **Generating the unions at build time from `yeti-css/manifest`.** Not now: the package would gain a build step for value lists that are frozen against removal and renaming, and the types would differ between a consumer's installed Yeti and the package's pin. The unions are written into the package's source against the pin. This is worth revisiting if a pin move ever adds many values at once.

## Consequences

- A misspelt value and a value Yeti does not have fail to compile under Angular's strict template type checking, which is what the user asked for.
- A value added by a later Yeti release is not available until the package's pin moves and its unions are updated, which is a package release under its release policy. A consumer who needs it first writes the attribute themselves on the element, which still works because the directive binds its inputs and leaves unknown attributes alone.
- The types carry the vocabulary's name, so several items that read the same vocabulary share one type (21 items read `data-gap`, 8 read `data-align`, 7 read `data-threshold`; [Research: inventory of Yeti's components, layouts, recipes, utilities, and contract](../issues/02-research-yeti-inventory.md)).
- The package publishes about 32 small type aliases instead of 26 registry interfaces, a manifest, a generator, a schematic, a sync generator, and a builder. [Decide: which ADRs carry over](../issues/08-decide-inherited-adrs.md) records that the old map's Variant declaration tooling has no successor here.
- An input named like an HTML presentational attribute keeps its name and states what the static attribute renders, under the rule carried over from old map ticket 139 (`decide-inputs-named-like-presentational-attributes`). Yeti's `data-width`, `data-height`, `data-align`, and `data-size` make this a live case.
- 2026-10-02: two later findings amend this record. First, the user's prefix ruling (map, Standing rulings) has input value types reuse Yeti's own exported vocabulary types from `yeti.d.ts` (`YetiGap`, `YetiWidth`, and so on) rather than redeclaring them, as recorded by [Decide: the glossary](../issues/10-decide-glossary.md). The unions are therefore imported, not written into the package's source. They are still closed and still move with the pin. Second, [Decide: how the package maps each of Yeti's `data-*` attributes](../issues/26-decide-yeti-data-attributes-mapping.md) found that the second consequence does not hold as written (read in Angular's source, not run). A directive that binds `[attr.data-*]` from an unset input removes a static attribute the consumer wrote on the same element. So a consumer who needs a value newer than the pin binds it through the input with `$any('new-value')` rather than writing the attribute.
