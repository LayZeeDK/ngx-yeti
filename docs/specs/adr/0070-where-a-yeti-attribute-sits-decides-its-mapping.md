# Where a Yeti attribute or marker sits decides how the package maps it

Recorded by [Decide: how the package maps each of Yeti's `data-*` attributes](../issues/26-decide-yeti-data-attributes-mapping.md). New for Yeti: no record of `.scratch/next-foundation-specs/` covers it. It applies [ADR 0003](0003-directives-set-yetis-class-attributes-and-markers.md) point 2 ("Every `data-*` attribute and marker the item declares is set from a typed input") to each of the 168 declarations in Yeti's built manifest at `f52d1e8b9` (132 attributes and 36 markers), and decides the cases that point does not cover. The per-declaration table is in the ticket's Answer.

The manifest already says where each declaration sits: an attribute has no `on` and belongs on the item's own element, and a marker has an `on` selector. Yeti's CSS scopes each child marker to its parent (`.columns > [data-span]`, `.cover > [data-center]`, `.breakout > [data-bleed]`, read in `dist/yeti.css`), while the six `on: "*"` markers work on any element through the always-loaded `attributes.css`. So the place decides the mapping. We decided:

- **R. An attribute of the item's own element** (no `on`): a typed input on the item's root directive, named from the attribute in camelCase without `data-` (`data-gap-inline` is `gapInline`), bound as `[attr.data-*]`.
- **C. A marker that changes a child** (Yeti's description says what to do to the element: "Stretches", "Pins", "Centers", "How many shares"): a typed input on the item's child directive, one per item and element role (`[yetiStackChild]` with `split`, `space`, and `sticky`; the glossary names each one). The child finds its parent through `inject(<token>, {optional: true, skipSelf: true})`, as [ADR 0013](0013-parts-name-their-targets-by-reference.md) point 1 has parts do.
- **P. A marker that names a part** (Yeti's description names the element: "The close button", "One slide", "Help text", "A margin note"): the part directive is the marker. It binds the marker as a static host attribute (`host: {'data-track': ''}`) and takes no input for it, because the marker never changes and the directive usually owns more of the part (ids, the close, the slide index). `demo`'s string marker `data-preview` is rendered by the `demo` component's template from a `preview` input.
- **G. A marker that works on any element** (`on: "*"`: `data-border`, `data-paint`, `data-text`, `data-show`, `data-hide`, `data-numeric`): its own directive, which binds no class, whose input has the selector's name (`<span yetiPaint="primary">`, `<td yetiNumeric>`). No item directive declares an input for it as well, so one element has one owner per attribute.
- **U. A utility attribute named as its item** (`data-attention`, `data-enter`, `data-lift`, `data-print`): the utility's root directive takes the selector's name as its input (`<p yetiEnter="rise">`), typed as the vocabulary plus `''`, where `''` (the bare selector) renders no attribute and Yeti's default applies. The utility's other attributes (`side`, `stagger`, `view`, `once`) follow R.
- **S. An attribute that changes after render is Angular-owned state.** Of all Yeti's modules, only `enter.js` writes a `data-*` attribute: it removes `data-once` when the element nears the viewport (`dist/js/enter.js:26`; the others write only `aria-*`, `tabindex`, `hidden`, and `role`, checked with `rg` over `dist/js/`). The enter directive renders `data-once` from a `computed` of its `once` input and a signal, and its own `IntersectionObserver`, started in `afterNextRender`, sets that signal, which removes the attribute. Hydration then has no static `data-once` to restore ([ticket 18](../issues/18-prototype-yeti-rendering-modes.md) measured that one), and no person can change any `data-*` attribute before hydration.

Four rules apply to all six kinds:

1. **Unset means absent.** An input defaults to `undefined` (or `false` for a boolean), which renders no attribute, so Yeti's CSS applies its own default. The package never writes Yeti's default value, because Yeti's public defaults are not frozen (`src/guides/stability.md`), and server HTML stays Yeti's minimal documented markup. A directive whose behaviour depends on the effective value (the tabs' arrow keys, the dropdown's hover) computes it from the manifest's default at the pin.
2. **Types reuse Yeti's.** A vocabulary attribute is typed by Yeti's exported type (`YetiGap` for vocabulary `gap`; all 32 exist in `dist/yeti.d.ts`, the `types` of `yeti-css`'s `.` export). An attribute with its own value list is an `Extract` of the vocabulary that holds the values (`Extract<YetiJustify, 'start' | 'center' | 'end'>` for the scroller's `data-justify`). A boolean is `boolean` with `booleanAttribute`; a string is `string`. A static attribute type-checks as a string literal (`translateInput` quotes it, `packages/compiler/src/typecheck/ops/inputs.ts:34-37`, read in the 22.2.x clone), so `columns="3"` compiles and `columns="7"` does not.
3. **Every declared attribute is rendered, even one only a module reads.** `data-slide`, `data-stylesheet`, and `data-trigger` match no rule in `yeti.css` (checked: 76 of the 79 distinct names do), but rendering them keeps server HTML equal to Yeti's markup, lets the manifest check of the testing record pass, and keeps `data-trigger="hover"` ready for `interestfor` ([ADR 0040](0040-package-replaces-yetis-optional-modules.md)).
4. **Everything is zoneless-safe.** Inputs are `input()` signals, host bindings read signals or `computed`s, P markers never change, and the one value written outside a binding (`data-once`) is a signal, the form [ticket 18](../issues/18-prototype-yeti-rendering-modes.md) measured refreshing zoneless.

A consumer writes no `data-*` attribute of Yeti's, as ADR 0003 says. Two cases stay with the consumer, because no directive can reach them: markup outside an Angular template (`index.html`, `[innerHTML]` content), written as Yeti documents it; and a value newer than the pin, bound as `[variant]="$any('new')"`. A static `data-variant` would not work there, because the directive's unset binding removes it (`setElementAttribute` calls `removeAttribute` for `null`, `packages/core/src/render3/instructions/shared.ts:530-535`, read, not run).

## Considered options

- **Any-element directives for the child markers too** (`<div yetiSplit>`, one `[yetiSpan]` shared by columns, grid, and hero). Shorter markup. Rejected: Yeti's CSS applies each one only under its parent, so it would compile anywhere and do nothing outside a stack; the parent's injection token and per-item types (grid's `start` exists only on a tracks grid) would be lost; and Angular Aria and Material name parts per pattern (`ngTab`, `matSuffix`).
- **Part markers as boolean inputs on the child directive** (`<div yetiCarouselChild track>`). Rejected: track, slide, and dots are different parts with different behaviour, so they are different directives, and a part that is always marked needs no input.
- **Inputs that default to Yeti's default value.** Rejected for rule 1's reasons, and because two directives on one element that declare the same attribute (`center` and `box` share `data-gap`; `media` and `enter` share `data-side`) receive one static attribute and bind the same value only if neither invents a default.
- **Plain camelCase inputs for G and U, as the map's Input naming record reads** (`<span yetiPaint paint="primary">`, `<p yetiEnter enter="rise">`). Not adopted: a directive whose only purpose is one attribute would need the attribute twice, and an un-prefixed input on an any-element directive receives the value meant for any same-named input of another directive on the element, the package's (`border` on the table) or a third party's (`text`, `show`). The old ADR 0044 (`utility-directive-rule`) (abandoned for its unit by [ticket 08](../issues/08-decide-inherited-adrs.md)) made the same choice for the same reason. This deviates from the letter of the map's record. On 2026-10-02 the user chose "Selector name (Recommended)" (map, Standing rulings), so the selector-named form is decided.
- **The consumer writes the any-element markers as plain attributes.** Rejected: ADR 0003 point 2, and a misspelt `data-paint="primray"` would stay silent.

## Consequences

- Each spec's contract mapping copies its item's rows from ticket 26 and adds the presentational-attribute kind (old map ticket 139 (`decide-inputs-named-like-presentational-attributes`)'s rule, carried over by ticket 07) where the input's name is an HTML attribute: `align` everywhere, `border` on a table, `nowrap` on a cell, `start` on an `ol` child, and the inert `width`, `height`, `size`, `span`, `rows`, `max`, `min`, and `fill`.
- The child and part directive selectors in ticket 26 are provisional; [Decide: the glossary](../issues/10-decide-glossary.md) names them, and the input names stay.
- ADR 0005's consequence that a consumer can write a newer value as a static attribute holds only for an attribute no directive on the element declares; for an owned attribute the escape hatch is the `$any` binding above.
- The package's type declarations import Yeti's types, so a consumer's compiler must resolve them; if it cannot, every union becomes `any` under `skipLibCheck`. How the package depends on Yeti is [ADR 0006](0006-yeti-pinned-develop-commit-vendored-and-gated.md)'s, and it must keep `yeti.d.ts` reachable.
- A Yeti pin move that adds an attribute adds an input, and one that adds a marker adds an input or a part directive by the same rule, so the table can be regenerated from the manifest.
- 2026-10-03: [Research: the decided records against Angular's hydration constraints](../issues/33-research-decided-records-against-hydration-constraints.md) reads that an unset input's removal of a consumer's static attribute is undone and redone at hydration. So the consumer writes no static `data-*` attribute that a directive declares; the value goes through the input.
