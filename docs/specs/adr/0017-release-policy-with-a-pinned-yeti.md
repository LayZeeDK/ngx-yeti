# The package follows the Angular devkit's version scheme, and a Yeti pin move is classed like any other change

Adapted from ADR 0045 (`release-policy-devkit-version-scheme`) of `.scratch/next-foundation-specs/`, by [Decide: which ADRs carry over](../issues/08-decide-inherited-adrs.md). That record bound nothing here. Its policy was the user's ruling of 2026-09-28, refined the same day (recorded in the old Decide: the directive and component architecture guide (ticket 141, `decide-directive-component-architecture-guide`), where the user chose its option (a) and then the devkit scheme), and [Decide: which standing preferences and user rulings carry over](../issues/07-decide-inherited-preferences-and-rulings.md) carried it as this map's "Release policy" note. What is new here is a second upstream: the package builds against one pinned commit of Yeti's `develop` (the user's readiness ruling, map Notes), and Yeti freezes its surface only from `7.0.0-beta` (`src/guides/stability.md`). The classing of a pin move below is this map's reading of the carried policy, not the user's words.

Carried as the policy reads:

- Version `0.<Angular major><Angular minor, two digits>.<patch>`; the patch counts the package's own releases on that Angular minor. The first published release is `0.22<mm>.0` for Angular 22's current minor.
- Breaking changes, removals, and platform-feature upgrades that change what consumers see land only when the Angular major changes (`0.22xx` to `0.23xx`). A release for a new Angular minor carries fixes and additive API only.
- A public API is removed only after it has been deprecated for at least one Angular major: it keeps working, annotated `@deprecated` with its replacement, the changelog gives the update path, and a migration rewrites it where one can be written.
- Migrations are written as Nx migrations first and reused as `ng update` migrations.
- The Angular packages are peers from the minor a release names (`^22.2.0` for `0.2202.x`), and the policy starts with the first published release: a change before it needs no deprecation.

Abandoned: `foundation-sites` as a peer at `^6.9.0`. How the package depends on Yeti is [ADR 0006](0006-yeti-pinned-develop-commit-vendored-and-gated.md)'s (vendored at the pin, no `yeti-css` dependency entry while Yeti is unpublished), under [ADR 0001](0001-yeti-licence-compatible-with-mit-package.md).

We decided how a pin move is classed:

1. **Every release names its Yeti commit** in its changelog, and a pin move is a changelog entry of its own.
2. **A pin move that breaks Yeti's frozen surface is a breaking change.** The test is the pin-move check of [ADR 0006](0006-yeti-pinned-develop-commit-vendored-and-gated.md) point 4: Yeti's own `bin/frozen.js` comparison of the old pin with the new one, which reports a break when a class, attribute or marker name, value list, vocabulary, public token name, module file name, or event name present at the old ref is gone or changed (`bin/frozen.js:1-12`, read at `f52d1e8b9`), together with that record's diff of what `frozen.js` does not read (event `detail` keys, the schemas, the `exports` map). Such a move, and any move that would remove or rename a public input, union member, or output of the package, lands only in a release for a new Angular major, after the affected API was deprecated for at least one Angular major. Where Yeti removes a value outright, the deprecation names the value's replacement or says there is none.
3. **A pin move whose check finds additions only** (new values, items, tokens, events) is additive and may land in any release. The package's unions take the new values in that release ([ADR 0005](0005-closed-unions-from-yetis-vocabularies.md)).
4. **A pin move that raises Yeti's browser target** reopens [ADR 0002](0002-browser-target-baseline-2025.md) and lands only in a release for a new Angular major, as Angular itself sets its browser support per major (`adev/src/content/reference/versions.md:75-77`, read in the 22.2.x clone).
5. **A pin move that changes only what Yeti leaves unfrozen** (public token defaults, private tokens, generated file text, `bin/`) and thereby what consumers' pages look like is not classed here: it is `OPEN FOR HUMAN` (ticket 08, `### Triage`). Until the user answers, no pin move of that kind is planned into a release.

When the pin moves, what gates it, and how the package records it are [ADR 0006](0006-yeti-pinned-develop-commit-vendored-and-gated.md)'s, from [ticket 12](../issues/12-decide-yeti-version-policy.md); this record only says what a move does to the package's version. ADR 0006's check already shows a change of public token defaults in the move's diff, which is where point 5 would be applied once answered.

## Considered options

- **A pin move is always a patch**, as a dependency update. Rejected: a frozen-surface break removes or renames the package's public inputs or values, which the carried policy reserves for an Angular major.
- **Put Yeti's version in the package's version.** Rejected: the scheme has no free number, and the user chose the devkit scheme over the other shapes in the old bundle; a changelog line carries the pin.
- **Hold every pin move to an Angular major.** Not adopted: an additive move breaks nobody, and the closed unions would otherwise lag Yeti by up to six months for no consumer's benefit.

## Consequences

- Yeti's alpha churn costs nothing before the first published release, because the policy starts there.
- Once published, a pin move that breaks the frozen surface waits for the next Angular major that follows a release carrying its deprecations; ADR 0006 already holds the pin in place until then. Before Yeti's beta the freeze is not in force (ADR 0006 found three public tokens removed on `develop` on 2026-09-24), so such breaks are likely while Yeti is in alpha.
- Each spec's "when the target moves" note names the upgrades that wait for an Angular major, and a spec that adopts one says which.
- Breaking under this policy is decided by the frozen surface and the package's API, never by whether Yeti calls its own release breaking.

- 2026-10-02: the user ruled on the open item of [Decide: which ADRs carry over](../issues/08-decide-inherited-adrs.md). Asked whether a pin move that changes only what Yeti leaves unfrozen (token defaults, private tokens, generated text) waits for an Angular major, the user chose "(a) Any release (Recommended)". Such a move may land in any release, with a changelog entry naming the visible change; a consumer keeps any default by setting the token (ADR 0004).
- 2026-10-02: the user set the version format (quoted in the map's Standing rulings): `0.<Angular major><Angular minor, two digits><breaking counter, two digits>.<patch>+yeti.<Yeti version>.<Yeti commit SHA>`, for example `0.220200.0+yeti.7.0.0-alpha.0.f52d1e8`. This replaces the devkit's `0.<Angular major><Angular minor>.<patch>` above. A release that breaks anything compared to the previous release bumps the two-digit counter and resets the patch. npm's `^0.220200.0` does not match `0.220201.0` (measured with `semver`), so npm itself enforces the signal. The counter resets on each Angular minor, which allows 99 breaking releases per Angular minor. The build metadata names the pinned Yeti and is valid for every SHA, including an all-digit one, and semver ignores it for precedence. `npm pack` keeps it (measured with npm 11.16), but whether the registry keeps it on publish is checked by [Research: whether the npm registry keeps a version's build metadata](../issues/28-research-npm-build-metadata.md). The user asked for a version that shows "whether the release contains breaking changes compared to the previous release". This replaces, for 0.x releases, the carried-over rule above that breaking changes wait for an Angular major. That reading is the orchestrator's and has been put to the user, together with whether the one-Angular-major deprecation period still applies to a removal.
- 2026-10-02, later the same day: [Research: whether the npm registry keeps a version's build metadata](../issues/28-research-npm-build-metadata.md) found that `npm publish` removes the `+` suffix. The user then chose "Prerelease tag (Recommended)" (quoted in the map's Standing rulings). The format is `0.<Angular major><Angular minor, two digits><breaking counter, two digits>.<patch>-yeti.<Yeti version>.g<Yeti commit SHA>`, for example `0.220200.0-yeti.7.0.0-alpha.0.gf52d1e8`; the `g` keeps an all-digit SHA valid. Every publish uses `npm publish --tag latest` (accepted in a dry run with npm 11.16), and consumers pin exact versions. Asked whether the counter replaces the carried-over rule that breaking changes wait for an Angular major, the user chose "Counter replaces it in 0.x (Recommended)": any 0.x release may break and bumps the counter; a removal still needs a `@deprecated` release before it and a migration where one can be written, without waiting a whole Angular major; the old rule returns at 1.0. This settles the open reading of the note above.
