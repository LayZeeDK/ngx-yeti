# `yeti` for Angular-side names, `ngx-yeti` for runtime names, and `NgxYeti` where a TypeScript name collides with Yeti's typings

Recorded by [Decide: the glossary](../issues/10-decide-glossary.md), which [ADR 0012](0012-class-prefix-and-token-naming.md) named as the record that follows the user's prefix ruling. ADR 0012 fixed the shapes (a class prefix, camelCase `...Token` injection tokens, `Nfs` and `nfs` abandoned, no class name equal to a Yeti type) and left the letters to the user.

The user's words, verbatim and in order (map, Standing rulings, Package name and Prefix): "Our new package name, replacing "ngx-foundation-sites" will be "ngx-yeti"". Then: "The project shorthand/prefix should no longer be "nfs" which was short for "ngx-foundation-sites". We need something else. I considered "yeti" but it might clash with the actual Yeti. I'm open to suggestions." Then, on 2026-10-02, asked where a plain `yeti` prefix would clash: "Prefix: Approve recommendation. Use an `NgxYeti` TypeScript naming prefix where collisions cannot be avoided." The recommendation the user approved is recorded in the map's Prefix bullet; its wording, and the wording below, are the orchestrator's and this map's, not the user's.

We decided:

1. **Angular-side names take `yeti`**: directive selectors in camelCase (`[yetiCard]`, `[yetiNavToggle]`), component selectors in dash-case (`<yeti-demo>`), `exportAs` (`yetiCard`), injection tokens (`yetiNavToken`, an optional `yetiDialogDefaultsToken`), provider functions (`provideYeti()`, if one is ever needed), and entry points under the package name (`ngx-yeti/card`). These live in Angular's namespaces, where Yeti declares nothing.
2. **Runtime names take `ngx-yeti`**: anything the package writes into the page at run time where Yeti already writes `yeti` names: custom properties (`--ngx-yeti-*`), cascade layers (`@layer ngx-yeti`, after Yeti's), and data attributes (`data-ngx-yeti-*`). The package dispatches no DOM event of its own, because Yeti owns `yeti:*`. Two names the ruling's list did not mention follow the same line, as this map's reading: **generated ids** take `ngx-yeti-<item>-` (`ngx-yeti-nav-1`), because an id is a page-wide runtime name, and **any CSS class the package's own CSS defines** would take `ngx-yeti-` (none is planned: the accessibility rules target state hooks).
3. **TypeScript names take `Yeti`**: `Yeti` plus the PascalCase of the item name, and of the part for a part directive (`YetiCard`, `YetiNav`, `YetiNavToggle`, `YetiFieldError`, `YetiTab`, `YetiTabPanel`).
4. **`NgxYeti` where a `Yeti` name collides** with a name Yeti's `yeti.d.ts` exports, which ADR 0012 point 4 forbids. Checked against Yeti's built `dist/yeti.d.ts` at the pin `f52d1e8b93de5bbde322480ba77d5be26c49b0ef`: it exports 46 names (32 vocabulary types, `YetiComponentName`, `YetiKind`, `YetiAttributeType`, and 11 manifest and token interfaces), and the PascalCase of exactly five of the 49 item names is among them. So today five classes take `NgxYeti`:
   - `NgxYetiColumns` (`columns` layout; Yeti exports `YetiColumns`, the `columns` vocabulary)
   - `NgxYetiAttention` (`attention` utility; `YetiAttention`)
   - `NgxYetiEnter` (`enter` utility; `YetiEnter`)
   - `NgxYetiLift` (`lift` utility; `YetiLift`)
   - `NgxYetiPrint` (`print` utility; `YetiPrint`)

   Only the colliding name changes: the selector and `exportAs` of each keep `yeti` (`[yetiColumns]`, `exportAs: 'yetiColumns'`), because Yeti's typings do not reach Angular's namespaces. A part directive of a colliding item keeps `Yeti` unless its own name collides (`YetiColumnsSpan` would not). The same test applies to every TypeScript name the package exports, not only item classes, and each spec runs it at the pin; each pin move runs it again, because a new vocabulary can turn a free name into a colliding one.
5. **Input value types reuse Yeti's vocabulary types**, as the approved recommendation says, rather than redeclaring them: an input that takes the `gap` vocabulary is typed `YetiGap`, imported as a type from `yeti-css`, and the package re-exports the 32 types by name from its primary entry point so that consumers write `import type {YetiGap} from 'ngx-yeti'`. An attribute with its own value list and no vocabulary has no Yeti type, so the package declares one, named `Yeti<Item><Input>` and checked by point 4.

## Considered options

- **`yeti` everywhere, including runtime names.** Rejected by the approved recommendation: `--yeti-*`, `@layer yeti`, `data-*` attribute names, and `yeti:*` are Yeti's own namespaces, and a package name there could equal one Yeti adds in a later pin.
- **`ngx-yeti` or `NgxYeti` everywhere.** Not chosen: the user preferred "yeti" where no clash is possible or probable, and Angular-side names cannot clash with Yeti.
- **A suffix instead of `NgxYeti` for the five** (`YetiColumnsDirective`). Rejected by the user's ruling, which names `NgxYeti`; a suffix would also break the one-rule naming of ADR 0012 point 1.
- **Package-declared vocabulary types** (ADR 0005's "written into the package's source against the pin"). Superseded for vocabularies by point 5: a package `YetiGap` would itself collide with Yeti's and need `NgxYetiGap`, 32 times over.

## Consequences

- Point 5 departs from two earlier records, which this record does not edit: [ADR 0006](0006-yeti-pinned-develop-commit-vendored-and-gated.md) point 7 ("Package code reads only `yeti-css/manifest` and `yeti-css/tokens`, never the types file") and [ADR 0005](0005-closed-unions-from-yetis-vocabularies.md)'s unions written into the package's source. Reading this record with them: a type-only import of the vocabulary types from `yeti-css` is the one exception to ADR 0006 point 7, and those unions are Yeti's. The exception carries ADR 0006's own risk: the types file's text is not frozen (`src/guides/stability.md`, Not frozen), while the vocabulary names it is generated from are (`bin/gen-types.js:18`), so each pin move checks that the 32 names still resolve.
- How `yeti-css` resolves in the published package's typings depends on how the consumer brings Yeti, which [Decide: how component styles load and unload](../issues/13-decide-style-loading.md) decides under the user's vendoring ruling. If the consumer's Yeti cannot be resolved as `yeti-css`, the package carries Yeti's `yeti.d.ts` from the pin (redistribution is allowed: "Vendoring: Yes") and re-exports from that copy. Either way no type is redeclared.
- ADR 0012's Considered options and point 4 stand; its "the specs write `<Prefix>` and `<prefix>`" no longer applies. `architecture-guide.md` and `building-blocks.md` replace their `pfx` stand-in with these names (ticket 10's Answer lists each replacement).
- Story ids, file names, and folder names carry no prefix (`nav--default`, `nav/nav-toggle.ts`), as building-blocks 1.3 says.
- 2026-10-02, recorded 2026-10-03 (audit 0003 L9): [ADR 0060](0060-item-styles-are-counted-links-to-the-consumers-yeti-build.md) point 10 settled where point 5's types come from. The published declarations must not `import type ... from 'yeti-css'`, because a missing `yeti.d.ts` turns every such input into `any` with no error (measured there). The package build copies `yeti.d.ts` at the pin into a generated `yeti-types.ts`, re-exported from the entry point, and every input type imports from it. Point 5's "imported as a type from `yeti-css`" now reads "imported from the package's generated `yeti-types.ts`"; the names, the re-export, and the no-redeclaring rule stand.
- 2026-10-03 ([Decide: the open points of the specs](../issues/50-decide-open-points-of-the-specs.md), decisions 10 and 11; the orchestrator's, not the user's): point 4's list counts item classes only, while its rule covers every TypeScript name the package exports. The full list to test against is the 46 names `yeti.d.ts` exports at the pin: YetiA YetiAlign YetiAttention YetiAttribute YetiAttributeType YetiChild YetiColumns YetiComponent YetiComponentName YetiEdge YetiEmphasis YetiEnter YetiEvent YetiFit YetiGap YetiHeight YetiJustify YetiKind YetiLift YetiManifest YetiMarker YetiModule YetiOrientation YetiPaint YetiPanel YetiPlacement YetiPrint YetiRatio YetiResize YetiRows YetiSelf YetiShape YetiSide YetiSizeControl YetiSlides YetiSpan YetiStart YetiSurface YetiToken YetiTokenCatalogue YetiTokenEntry YetiTracks YetiTrigger YetiVariant YetiWidth YetiWidthOrNone.
  - A sixth collision today: the `[yetiPaint]` marker directive's class is `NgxYetiPaint`, because `YetiPaint` is Yeti's `paint` vocabulary type.
  - Names a part directive or a package type could reach and that Yeti already exports include `YetiSpan`, `YetiSlides`, `YetiTrigger`, `YetiPanel`, `YetiStart`, `YetiChild`, and `YetiEvent`; each takes `NgxYeti` if a spec names it.
  - Marker class naming: an any-element marker directive's class is `Yeti` plus the PascalCase of its selector without the prefix (`YetiShow`, `YetiHide`, `YetiBorder`, `YetiText`, `YetiNumeric`), and `NgxYeti` on a collision (`NgxYetiPaint`). Point 3 names classes for items and parts only.
- 2026-10-03 ([ticket 50](../issues/50-decide-open-points-of-the-specs.md), decisions 136 and 223; the orchestrator's, not the user's): point 1's component example `<yeti-demo>` is out of date. The demo is an attribute-selector component, `figure[yetiDemo]`, class `YetiDemo`, `exportAs: 'yetiDemo'`, as is `YetiFieldError` (decision 159). The rule stands for any element-selector component the package adds later; today it has none.
