# Each item's CSS is a library-owned counted `<link>` to the consumer's own Yeti build; the package ships no Yeti CSS

The user ruled, verbatim (2026-10-02): "Vendoring: Yes, but if possible don't bundle Yeti's CSS in our package. Try to find a way to let the consumer" and then "Vendoring: Try to find a way to let the consumer bring a build." The map's "Lazy styles" requirement, carried over from the user's ruling of 2026-10-01, asks that each first-milestone directive load its item's styles when its first instance renders and unload them after the last, with the unit being one of Yeti's 49 per-item files. The user's standing ruling 28 allows a component with `styleUrl` where that is what makes lazy styles meet the requirements. Decided in [Decide: how component styles load and unload](../issues/13-decide-style-loading.md), measured in [Prototype: item styles as counted `<link>`s to the consumer's own Yeti build](../prototypes/style-loading/README.md) on Angular 22.2 SSR in Chromium, Firefox, and WebKit, on the evidence of tickets [04](../issues/04-research-yeti-styles-and-lazy-loading.md), [18](../issues/18-prototype-yeti-rendering-modes.md), [23](../issues/23-research-yeti-layers-and-import-order.md), and [24](../issues/24-prototype-ngx-yeti-with-tailwind-v4.md), and the old map's tickets 184 to 198.

We decided:

1. **The loading unit is the item file**: the one CSS file of a Yeti item, `yeti-css/css/<kind>/<name>/<name>.css` with `kind` one of `layouts`, `recipes`, `components`, `utilities`, 49 in all. Yeti's install guide calls it a part (`src/guides/install.md:97` at `f52d1e8b9`); this bundle says item file, because "part" already names a sub-directive of a multi-part item ([ADR 0012](0012-class-prefix-and-token-naming.md), [ADR 0013](0013-parts-name-their-targets-by-reference.md)).
2. **The consumer brings Yeti's build at the pin, and the package loads each item file from it by URL.** The package ships and inlines no Yeti CSS. A root service owns one reference-counted `<link rel="stylesheet">` per item, `href` `<url><kind>/<name>/<name>.css?v=<pin>`, where `url` defaults to `yeti-css/` and is relative to `<base href>` (the only URL root the package supports, the user's standing ruling 29). The link carries `data-ngx-yeti-styles="<item>"`, `data-ngx-yeti-app="<APP_ID>"`, `data-beasties-skip`, and the `CSP_NONCE` when one is provided. Every directive and component sets `data-ngx-yeti-item="<item>"` on its host and acquires its item in its constructor, on the server too; it releases it on destroy.
3. **Insertion follows Yeti's order.** A link is inserted before the first existing item link that comes later in `yeti-css/css/yeti.css`, from a rank table generated at package build from that file at the pin. This keeps Yeti's tie order inside a layer (a stack loaded after a center still lets the center keep its auto margins, measured; ticket 23 measured the append order losing it). Yeti's layer statement comes first because the consumer's global stylesheet carries it (point 7).
4. **Removal waits for the DOM, not for Angular.** A link is removed in the animation frame after its live count reached zero and no element with `data-ngx-yeti-item="<item>"` is connected; a `MutationObserver` on the document triggers the check. So a host leaving under a class-form `animate.leave` keeps its styles until Angular removes it (measured: 0 unstyled frames while leaving; link gone afterwards), a dehydrated host (`hydrate never`, or `hydrate on ...` before its trigger) holds the link for as long as it is on the page (measured), and a function-form `(animate.leave)` listener anywhere on the page changes nothing, because Angular's renderer never owns these links (angular/angular#66244 does not apply; measured with a permanent listener on the page).
5. **Server HTML and hydration.** The server writes the links into `<head>` in Yeti's order; the client adopts them by `data-ngx-yeti-styles` and `data-ngx-yeti-app` at bootstrap. Measured: styled with JavaScript off, 0 style mutations after `DOMContentLoaded`, 0 unstyled frames at hydration in Chromium and WebKit, and 0 computed differences from Yeti's full stylesheet. Two applications on one document each own their links by `APP_ID` (inferred from the old map's ticket 198, not measured).
6. **A client-only `@defer` block fetches its item on construct.** Measured: 18 to 20 unstyled frames with the CSS delayed 300 ms, 1 to 2 with no delay, the gap tickets 189 and 192 called structural for any fetch-on-construct loader. The consumer closes it per item with `provideYetiStyles({ preload: ['alert'] })`, which writes `<link rel="preload" as="style">` for each named item on the server and the client: 0 unstyled frames in all three engines (measured). Each spec's Rendering modes subsection says so for its item, and a spec whose item animates entry with a class from an item file (Yeti's `enter` utility) says the file must be present before insertion, by server rendering or by the preload list, because Angular removes an `animate.enter` class after one frame (read in ticket 189).
7. **Cascade layers.** The consumer's global stylesheet declares `@layer yeti, ngx-yeti;` first, then Yeti's always-loaded group in Yeti's order with `layers.css` first (map, "The always-loaded group"), then the package's own stylesheet. With Tailwind v4 the statement is the one shared statement of ticket 24 with `ngx-yeti` after `yeti`: `@layer theme, base, yeti, ngx-yeti, components, utilities;` (or without `base` when preflight is left out), plus `@source not inline('container');`. Item links only add rules to layers the global sheet has already placed (ticket 23, measured), so no load order moves a layer.
8. **The package's own CSS is one small global stylesheet** in `@layer ngx-yeti`, holding the accessibility rules the user allowed (2026-10-02, "Accessibility CSS: Yes."), imported by the consumer after the always-loaded group. It is the package's CSS, not Yeti's, so shipping it is within the ruling. It is not loaded per item: ticket 17 counted eight behaviour gaps, each rule is a line or two, and a second element kind per item would double the server and hydration surface for a few hundred bytes.
9. **Cross-item rules.** A directive acquires every item file whose rules its item depends on, and its spec names them. Known today: the button item acquires `spinner` while a button is busy, because the busy ring lives in `spinner.css` (ticket 23, measured). The smooth scrolling that `toc.css` gives nav fragment links is documented, not loaded by the nav item; the fragment-links shared-utility spec owns in-page scrolling.
10. **Types come from the package, not from the consumer's build.** The package's input types reuse Yeti's exported vocabulary types ([ADR 0005](0005-closed-unions-from-yetis-vocabularies.md), 2026-10-02 note), but its published declarations must not `import type ... from 'yeti-css'`: measured, with `yeti-css/dist/yeti.d.ts` absent and Angular's default `skipLibCheck: true`, a wrong input value compiles with no error and no warning, every such input having become `any`. So the package build copies `yeti.d.ts` at the pin into a generated source module (`yeti-types.ts`, re-exported from the package's entry point) and every input type imports from it. The consumer's TypeScript never resolves `yeti-css`; a consumer's build at the wrong commit affects CSS only. When `yeti-css` is published on npm and the package can declare a peer dependency on it, the copy goes and the import points at `yeti-css` again; that reopens this point.
11. **What the consumer writes**, all of it build configuration or generated:
    - a build of Yeti at the pin under the specifier `yeti-css`: in an Nx workspace, the vendored workspace package with the cached `yeti-build` target ([ADR 0006](0006-yeti-pinned-develop-commit-vendored-and-gated.md), [ticket 22](../issues/22-prototype-building-and-consuming-yeti-with-nx.md)); elsewhere, a clone at the pin with `npm ci && npm run build` and a `file:` or tarball dependency ([ticket 21](../issues/21-prototype-yeti-as-github-dependency.md));
    - one `assets` entry in the application's build options: `{ "glob": "**/*.css", "input": "node_modules/yeti-css/dist/css", "output": "yeti-css" }` (66 files, measured);
    - the global stylesheet of point 7: the layer statement, 16 `@import 'yeti-css/css/...'` lines, and the package's stylesheet;
    - optionally `provideYetiStyles({ url, preload })`.

    A generator may write the last three; whether the first milestone ships one is the `setup` spec's call (named 2026-10-03; see the note below). No consumer TypeScript per item, no carrier component, and no Yeti class or attribute written by hand ([ADR 0003](0003-directives-set-yetis-class-attributes-and-markers.md)).

## Considered options

- **A library `styleUrl` per item, inlining Yeti's file at library build** (ticket 04's S1; the user's ruling 28 allows it "where applicable"). Rejected: it ships Yeti's CSS, which the ruling allows only where nothing else meets the requirements; and it meets fewer of them. It leaks while any function-form `(animate.leave)` listener is on the page, which a consumer can add anywhere (tickets 04 and 18, measured); a `hydrate never` instance loses its styles when the last live instance leaves (ticket 18, measured); and `SharedStylesHost` appends, so Yeti's tie order is lost (ticket 23, measured). Ruling 28 therefore triggers nowhere: every item stays directives, as [Decide: the spec list](../issues/11-decide-spec-list.md) has it.
- **A library-owned `<style>` from a CSS string generated at package build** (ticket 04's S2, the old map's 188 and 192 A). It would close the client-only `@defer` gap without a preload (0 frames, measured in the old map's 192 and 193) and is otherwise this record's runtime with a string instead of a URL. Rejected by the ruling: the string is Yeti's CSS inside the package. It is the fallback if the preload list is ever judged insufficient.
- **Angular's own external styles** (`RendererType2.getExternalStyles`, `ɵɵExternalStylesFeature`): Angular's `SharedStylesHost` can count a `<link>` per URL (`packages/platform-browser/src/dom/shared_styles_host.ts:139-144`, read in the 22.2.x clone). Rejected: the removal sits behind the same leave guard (`dom_renderer.ts:683`), dehydrated instances are not counted, the feature is a private compiler instruction, and server links are adopted by the last path segment of the `href` alone (`shared_styles_host.ts:76-80`), which conflates Yeti's `base/media.css` and `recipes/media/media.css`.
- **Consumer-written carrier components with `styleUrl`**, generated or by hand. Rejected: TypeScript per item in the consumer's project, the user's objection in the old map's ticket 189, and the carrier is Angular-counted, with the guard and the dehydrated gap above.
- **`inject: false` global style entries per item** (the old map's 189 shape). Rejected: five lines of build configuration per item, 245 for 49, for the same runtime; Angular's CSS optimiser is the only gain, and the files gzip to the same order either way.
- **Everything global** (ticket 04's S4; `dist/yeti.min.css` is 138 kB raw and 19.5 kB gzipped, against the always-loaded group's 6.55 kB transfer, measured). Rejected by the "Lazy styles" requirement. See the consequences for what lazy loading buys.
- **A paint gate** that hides the fetch gap (`visibility: hidden` until the sheet loads; the old map's 197 D). Rejected: it breaks `focus()` and empties the accessibility tree during the gap (197, measured).
- **An unload grace period** (197 G) or `sheet.disabled` instead of removal, against WebKit's refetch of a re-inserted link. Not adopted for the first milestone: the measured cost is one frame from the cache; a grace period keeps stale styles on the page.
- **Making the tie-sensitive items (`stack`, `center`, `shell`) global** (ticket 23's P3). Unnecessary once insertion follows Yeti's order.
- **Yeti's layer statement atop each item** (ticket 23's L2) and **a development-mode order check** (L3). The loader cannot prepend to a file it does not own; the consumer's global sheet carries the statement. A development check is a later-milestone check under the map's Milestones note.

## Consequences

- Every spec's Rendering modes subsection states: its host attribute, the item files it acquires, that a client-only `@defer` instance needs the preload list for a flash-free first paint, and any item file an entry animation needs before insertion.
- The glossary gains **item file** (this record's point 1) and the host and link attributes; "part file" and "family" are avoided names.
- Item links are render-blocking in `<head>` and get no critical copy (point 2's `data-beasties-skip`). The old map's ticket 190 measured that render-blocking family links cost LCP on a slow network for Foundation's bundles; the same cost applies here and was not re-measured. The alternative, letting Angular inline a critical copy, is not available: in 22.2 the SSR engine inlines only from build-time plans for the application's own global stylesheets, and logs a warning for every other link (measured).
- What lazy loading buys is bounded: all of Yeti minified is 19.5 kB gzipped and the always-loaded group alone is 6.55 kB, so per-item loading saves at most about 13 kB of CSS transfer on a page, at the price of one request per item in use and this record's machinery (sizes measured; the saving is inferred from them). The requirement is the user's; the ticket's Triage records it.
- Angular's inlined critical copy of the always-loaded group drops six of Yeti's nine `:root` token blocks, the component tokens among them, so a server-rendered item can paint with its rules but without its tokens until the async global stylesheet arrives (measured in Chromium and Firefox, cause not pinned). It belongs to the always-loaded group and to [upstream-bugs.md](../upstream-bugs.md), and it is the same for every loading mechanism.
- [ADR 0006](0006-yeti-pinned-develop-commit-vendored-and-gated.md) point 7 gains two build-time reads besides the manifest and the tokens: `yeti-css/css/yeti.css` for the rank table and `yeti.d.ts` for the generated types module. Runtime code still reads neither.
- A pin move changes the `?v=` query on every item URL and regenerates the rank table and the types module; the consumer rebuilds Yeti at the new pin. A consumer who builds Yeti at another commit gets that commit's CSS under the package's pin query, which is documented as unsupported.
- The `MutationObserver` runs for the life of the application and the sweep queries the document once per item at most once per frame; the old map's ticket 198 measured observer callbacks at 31 ms in total for 5,000 hosts. An implementation may connect the observer only while some item has a zero live count.
- The old map's requirements that remain unmet for Yeti: none. Its "cache busting" is met by the pin query; its "no consumer code" by point 11.
- 2026-10-02: told that per-item loading saves at most about 13 kB gzipped of CSS per page, the user chose "Keep per-item loading (Recommended)" (map, Standing rulings). The lazy-styles requirement and this record stand.
- 2026-10-02, recorded 2026-10-03 (audit 0003 M1): asked whether the consumer-facing setup gets its own spec, the user chose "Add a `setup` spec (Recommended)" (map, Standing rulings, Ticket 25's open items). The `setup` spec, the fifth shared spec, owns what point 11 lists: the layer statement and global stylesheet of point 7, the `assets` entry, `provideYetiStyles()`, the package's accessibility stylesheet of point 8, `provideYetiFragmentLinks()` (as the map lists it), and whether a generator writes them. Point 11's "shared-setup spec" is that spec.
- 2026-10-03: [ADR 0045](0045-each-item-marks-its-host-with-its-own-attribute.md) replaces point 2's single `data-ngx-yeti-item="<item>"` with one presence attribute per item, `data-ngx-yeti-item-<item>`, and point 4's check queries it. Two items on one element (`card` with `lift`) otherwise leave one value in the DOM.
- 2026-10-03 ([Decide: the open points of the specs](../issues/50-decide-open-points-of-the-specs.md), decisions 6, 7, and 34; the orchestrator's, not the user's): point 2's "every directive and component" reads as every item's root directive. Part and child directives, and the any-element marker directives, set no presence attribute and acquire nothing ([ADR 0045](0045-each-item-marks-its-host-with-its-own-attribute.md)'s scope note). Point 3's insertion in Yeti's order also decides one more tie: `.cover > *` sets `margin: 0` and `.center` sets `margin-inline: auto` at equal specificity, so a `center` inside a `cover` keeps its inline centring only because `center.css` is inserted after `cover.css` (read in `yeti.css`, not measured). The `cover` spec's layer-4 case covers it.
- 2026-10-03 ([ticket 50](../issues/50-decide-open-points-of-the-specs.md), decision 109; the orchestrator's, not the user's): point 9's "while a button is busy" now reads "always". `YetiButton` acquires `spinner` with `button` in its constructor and releases both on destroy, because `aria-busy` stays the consumer's attribute, which no directive input sees, and a `busy` input or a `MutationObserver` per button costs more than one small request (`spinner.css` is about 1.4 kB of source, ticket 23). The button host carries no `spinner` presence attribute, so a busy button that never hydrates loses its ring once every live button and spinner has left; the button spec documents it (decision 110).
